# 리뷰 방법론

이 문서는 Phase 5(리뷰)에서 Reviewer가 따르는 방법론을 정의한다.
autonomous-dev v2→v3 버전업 과정에서 7라운드 리뷰를 통해 검증된 방법론이다.

---

## 핵심 원칙: "왜 없는지 먼저 분석"

### 문제 상황
코드 리뷰 중 "이게 빠져있다"를 발견했을 때, 즉시 이슈로 보고하면:
- 의도적 설계를 "버그"로 잘못 판단할 수 있다
- 역할이 다른 두 곳을 무분별하게 동기화할 수 있다
- 불필요한 수정이 스킬의 다른 부분을 깨뜨릴 수 있다

### 올바른 접근법

빠진 것을 발견했을 때 **3단계 분석**을 먼저 수행:

#### Step 1: 이전 버전 확인
```
Q: v{N-1} 백업에도 없었는가?
→ Yes: 의도적 설계 가능성 높음 (처음부터 없었으니까)
→ No: 이번 수정에서 실수로 삭제됐을 수 있음 (이슈 가능성 높음)
```

#### Step 2: 역할/목적 분석
```
Q: 이 파일/섹션의 목적상 필요한 내용인가?
→ 이 파일이 누구를 위한 것인지 확인
→ 빠진 내용이 다른 파일의 책임이 아닌지 확인

예시: 리더 체크리스트(7항목)와 문서 에이전트 체크리스트(6항목)
→ 역할이 다르므로 항목이 달라도 정상
→ "7항목이 아니라 6항목이다"는 이슈가 아님
```

#### Step 3: 교차 참조 확인
```
Q: 다른 파일에서 이 내용을 참조하고 있는가?
→ Yes: 존재해야 함 (참조가 깨짐 = 확실한 이슈)
→ No: 독립적, 있어도 없어도 되는 것일 수 있음
```

### 판정 매트릭스

| Step 1 | Step 2 | Step 3 | 판정 |
|--------|--------|--------|------|
| 이전에도 없음 | 목적상 불필요 | 참조 없음 | ✅ 정상 — 이슈 아님 |
| 이전에도 없음 | 목적상 필요 | 참조 있음 | 🟡 검토 필요 — 원래부터 빠진 것일 수 있음 |
| 이전에도 없음 | 목적상 필요 | 참조 없음 | 🟡 판단 유보 — 추가 정보 필요 |
| 이번에 삭제됨 | 목적상 필요 | 참조 있음 | 🔴 확실한 이슈 — 수정 필요 |
| 이번에 삭제됨 | 목적상 불필요 | 참조 없음 | 🟡 의도적 삭제인지 확인 필요 |

**→ 3단계 모두 "있어야 한다"일 때만 🔴 이슈로 보고**

## 실전 교훈 (autonomous-dev v3 리뷰에서)

### 사례 1: 잘못된 동기화 (Issue 7)

**상황**: phase-details.md의 Phase 4 체크리스트(7항목)와 agent-roles.md의 문서 에이전트 템플릿 C 체크리스트(6항목)가 다름

**잘못된 판단**: "7항목으로 맞춰야 한다" → 문서 에이전트 템플릿에 7번째 항목 추가

**올바른 분석**:
- phase-details.md Step 3 = **리더의** 사전 전달 검증 체크리스트
- 템플릿 C = **문서 에이전트의** 작업 체크리스트
- 7번째 항목("CLAUDE.md의 학습된 규칙 검토")은 리더가 자기 개선 루프에서 하는 일
- 문서 에이전트는 CLAUDE.md를 수정할 권한이 없음
- v2에서도 둘 다 6항목이었고, v3에서 phase-details.md에만 7번째가 추가됨 (리더 책임으로)

**결론**: 수정 롤백. 역할이 다른 두 곳의 체크리스트를 무분별하게 맞추면 안 된다.

### 사례 2: 올바른 이슈 발견 (Issue 19)

**상황**: sot-management.md의 CLAUDE.md 템플릿에 "프로젝트 특수 규칙" 섹션이 없음

**3단계 분석**:
1. **이전 버전 확인**: init_project.py에는 처음부터 해당 섹션이 있었음
2. **목적 분석**: 같은 파일(sot-management.md) 내 3중 게이트에서 "프로젝트 특수 규칙 섹션에 추가"를 언급 → 참조 대상이 템플릿에 없으면 문제
3. **교차 참조**: 3중 게이트 규칙이 이 섹션을 직접 참조함

**결론**: 3단계 모두 "있어야 한다" → 🔴 이슈 확정, 수정 실행

### 사례 3: 올바른 기각 (Issue 18, 20, 21)

**Issue 18**: SOT 폴더 구조에 handoff 파일이 없다
- 분석: 폴더 구조 다이어그램은 **초기 상태**를 보여줌. 동적 파일은 SKILL.md에서 설명
- 판정: 이슈 아님

**Issue 20**: context-health.md에 ui-guide.md 언급이 없다
- 분석: context-health.md는 **전략 문서**. 구현 스펙이 아니라 개념을 설명
- 판정: 이슈 아님

**Issue 21**: Phase F 코드에 QC 핵심원칙 미통과 처리가 없다
- 분석: Phase F는 **기존 QC 통과한 코드**에 추가 기능을 더하는 것. 이미 통과한 핵심원칙을 다시 검증하는 것은 중복
- 판정: 이슈 아님 (선호도 차이, 정합성 문제 아님)

## 이슈 분류 기준

### 🔴 필수 수정
- 교차 참조 깨짐 (파일 A에서 참조하는 내용이 파일 B에 없음)
- 숫자/이름 불일치 (A에서 "5단계", B에서 "6단계")
- 논리적 모순 (A에서 "금지", B에서 "허용")
- 실수로 삭제된 내용 (v{N-1}에 있었는데 없어짐)

### 🟡 PASS with Notes
- 개선 여지는 있지만 동작에 영향 없음
- 설명이 불충분하지만 오해의 여지가 적음
- 표현 선호도 차이 (기능적 차이 없음)
- 향후 버전에서 고려할 사항

### 🟢 양호
- 문제 없음

### 판단 기준: 🔴 vs 🟡
```
"이것을 수정하지 않으면 스킬이 잘못 동작하거나 에이전트가 혼란스러워하는가?"
→ Yes → 🔴
→ No → 🟡
```

## 역검증 방법론

### 목적
적용된 수정 자체가 올바른지 역으로 검증. "고친 것이 진짜 고쳐야 할 것이었는가?"

### 수행 시점
전체 라운드별 리뷰 완료 후, 마지막 단계로 수행

### 검증 항목

#### 1. 수정 필요성 재확인
각 수정에 대해:
- 4대 평가 기준(Phase 2)에 부합하는가?
- 원래 없던 이유가 있지 않았는가?
- v{N-1}에서의 상태가 더 적절하지 않았는가?

#### 2. 의도적 차이 점검
- 역할이 다른 두 곳의 내용을 무분별하게 동기화하지 않았는가?
- 예: 리더 vs 워커, QC vs 문서 에이전트
- 각 역할의 권한과 책임을 기준으로 판단

#### 3. 신규 불일치 점검
- 수정 A와 수정 B가 서로 충돌하지 않는가?
- 수정이 의도치 않게 다른 참조를 깨뜨리지 않았는가?
- 추가된 내용이 기존 금지 사항과 모순되지 않는가?

### 역검증 결과 처리
| 결과 | 조치 |
|------|------|
| 수정이 적절했음 | 그대로 유지 |
| 수정이 불필요했음 | 롤백 (v{N-1}으로 되돌림) |
| 수정 방향은 맞지만 범위 과도 | 부분 롤백 |
| 수정으로 새 불일치 발생 | 추가 수정으로 해결 |

## 라운드 관리

### 라운드 순서 원칙
1. SKILL.md 먼저 (메인 오케스트레이터, 전체 구조 파악)
2. 레퍼런스 파일은 참조 빈도 높은 순서
3. 마지막에 역검증

### 라운드 간 맥락 유지
- 이전 라운드에서 발견한 이슈를 이후 라운드에서 교차 확인
- 이전 라운드에서 "정상"이라고 판단한 것도 이후 라운드에서 새 증거가 나오면 재검토

### 리뷰 완료 기준
- [ ] 모든 파일 최소 1라운드 검토 완료
- [ ] 🔴 이슈 0건 (전부 해결됨)
- [ ] 역검증 완료
- [ ] 역검증 이슈 0건 (전부 해결됨)
