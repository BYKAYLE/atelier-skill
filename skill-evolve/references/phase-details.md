# Phase별 상세 절차

---

## Phase 0: 준비

**담당**: Orchestrator (직접 수행)
**소요**: 짧음 (백업 + 브리핑 작성)

### Step 1: 대상 스킬 확인

```
1. 사용자가 지정한 스킬 경로 확인
2. SKILL.md 읽기 → 현재 버전, changelog, 구조 파악
3. references/ 목록 확인 → 레퍼런스 파일 수 및 내용 파악
4. 전체 라인 수 추정
```

### Step 2: 백업

```
1. 현재 버전 번호 확인 (예: v2.0.0)
2. 백업 경로 생성: ~/.claude/skills-archive/{skill-name}-v{N}/
3. 전체 복사 (SKILL.md + references/ + scripts/ 등)
4. 백업 완료 확인 (파일 수, 크기 비교)
```

**백업 검증 체크리스트**:
- [ ] 원본과 백업의 파일 수 일치
- [ ] SKILL.md 내용 일치
- [ ] references/ 파일 전부 복사됨

### Step 3: 목표 설정

사용자에게 확인:
- 개선 테마가 있는가? (예: "QC 강화", "에이전트 보강")
- 비교 대상이 있는가? (예: "superpowers 스킬과 비교해줘")
- 범위 제한이 있는가? (예: "SKILL.md만 건드려")

테마가 없으면 → "전반적 개선" 모드, Market Researcher가 자율 탐색

### Step 4: 리서치 브리핑 작성

Market Researcher에게 전달할 브리핑:
```
- 대상 스킬명 + 버전
- 스킬의 핵심 목적 (SKILL.md 기반 요약)
- 개선 테마/키워드
- 탐색 범위 (GitHub, npm, 커뮤니티 등)
- 제외 대상 (이미 분석한 스킬 등)
```

### Phase 0 완료 조건
- [ ] 백업 완료 및 검증
- [ ] 리서치 브리핑 작성 완료
- [ ] 사용자 테마/범위 확인 완료

## Phase 1: 리서치

**담당**: Market Researcher (서브에이전트)
**소요**: 중간 (탐색 범위에 따라)

### Step 1: 탐색

Orchestrator의 브리핑에 따라:
1. 키워드별 WebSearch 실행
2. GitHub 저장소 탐색 (stars, forks, 최근 활동)
3. 커뮤니티 언급 확인 (Reddit, Discord, 포럼)

### Step 2: 후보 정리

각 후보에 대해:
1. 기본 정보 수집 (이름, URL, Stars, 최근 업데이트)
2. README 읽기 → 핵심 기능/차별점 파악
3. 실제 코드 읽기 → 코드 품질 판단

### Step 3: 평판 팩트체크

**중요**: 이 단계가 일반 리서치와의 차이점

```
Stars 수 vs 코드 품질 매트릭스:

               Stars 높음        Stars 낮음
코드 좋음      실력파 ✅         숨은 보석 💎
코드 나쁨      마케팅 우위 ⚠️    미성숙 ❌
```

팩트체크 항목:
- README에 적힌 기능이 실제 코드에 있는가?
- 최근 6개월 커밋이 있는가?
- 이슈/PR 대응이 되고 있는가?
- 의존성이 과도하지 않은가?

### Step 4: TOP 후보 추천

보고서 작성 후 Orchestrator에게 반환:
- 전체 탐색 결과 테이블
- TOP 3~5 추천 + 추천 이유
- 제외 대상 + 제외 이유

### 사용자 승인 게이트 ✋

Orchestrator가 사용자에게 리서치 결과 전달:
- "이 후보들을 상세 분석할까요?"
- 사용자가 후보 추가/삭제 가능
- 확정 후 Phase 2 진입

### Phase 1 완료 조건
- [ ] 리서치 보고서 작성 완료
- [ ] TOP 후보 추천 완료
- [ ] 사용자 승인 완료

## Phase 2: 분석

**담당**: Comparison Analyst (서브에이전트)
**소요**: 긴 편 (심층 비교)

### Step 1: 전체 읽기

1. 대상 스킬 전체 코드 읽기 (SKILL.md + 모든 references)
2. 후보 스킬 전체 코드 읽기
3. 구조/패턴/철학 차이 파악

### Step 2: 1:1 비교

각 후보별:
1. 기능 비교 (있는 것 vs 없는 것)
2. 구조 비교 (Phase 구조, 에이전트 역할)
3. 프로세스 비교 (QC, 승인, 검증 방식)
4. 문서화 비교 (SOT, 템플릿, 보고서)

### Step 3: 4대 기준 평가

발견된 각 차이점에 대해 4대 기준 적용:

| 기준 | 통과 조건 |
|------|----------|
| ⭐ Stars 이유 | 실질적 가치가 있다 (트렌드가 아니라) |
| 🔍 우리에게 없는 이유 | 의도적 생략이 아니라 누락이다 |
| 👤 사용자 복잡도 | 증가하지 않는다 |
| 🔧 내부 흡수 | 가능하다 (또는 최소 노출) |

**4개 기준 중 3개 이상 통과 → 개선 후보**
**사용자 복잡도 증가 → 아무리 좋아도 보류** (이 기준은 거부권)

### Step 4: TOP N 도출

1. 개선 후보 우선순위 정렬
   - 필수: 4개 기준 모두 통과
   - 권장: 3개 통과 (사용자 복잡도 제외 1개 미통과)
   - 보조: 가치는 있으나 우선순위 낮음
2. TOP 5 이하로 제한 (과도한 변경 방지)
3. 각 개선사항의 대상 파일, 예상 변경량 명시

### 사용자 승인 게이트 ✋

Orchestrator가 사용자에게 분석 결과 전달:
- TOP N 개선사항 목록 + 4대 기준 평가 요약
- 사용자가 적용 대상 확정 (전체/일부/재분석)
- 확정 후 Phase 3 진입

### Phase 2 완료 조건
- [ ] 비교 분석 보고서 작성 완료
- [ ] TOP N 개선사항 도출 완료
- [ ] 사용자 승인 완료

## Phase 3: 사전 검증

**담당**: Flow Guardian (서브에이전트)
**소요**: 중간 (구조 분석)

### Step 1: 스킬 구조 맵핑

대상 스킬의 파일 간 관계 파악 (예시 — 실제 구조는 대상 스킬에 따라 다름):
```
SKILL.md ──참조──→ references/file-a.md
SKILL.md ──참조──→ references/file-b.md
file-a.md ──참조──→ file-b.md (템플릿/기준)
...
```

### Step 2: 개선사항별 파급 효과 분석

각 개선사항에 대해:
1. 직접 수정 대상 파일 식별
2. 1차 간접 영향 파일 식별 (수정 파일을 참조하는 파일)
3. 2차 간접 영향 파일 식별
4. 교차 참조 체크 (동일 개념이 여러 곳에 다른 형태로 있는지)

### Step 3: 의도 분석

각 수정 지점에서:
1. 현재 상태가 왜 이렇게 되어있는지 분석
2. v{N-1} 백업과 비교
3. changelog/decisions.md 확인
4. **의도적 설계라면 → 수정 불가, 개선사항에서 제외**

### Step 4: 판정 + 구현 계획

| 판정 | 기준 | 후속 |
|------|------|------|
| ✅ 안전 | 파급 효과 제한, 참조 영향 없음 | 구현 계획 수립 |
| ⚠️ 조건부 | 파급 있으나 관리 가능 | 추가 수정 포함하여 계획 |
| ❌ 위험 | 광범위 파급, 흐름 변경 | 제외 권고 |

안전/조건부 판정 항목에 대해 구현 계획 작성:
- 파일별 수정 순서 (의존 관계 고려)
- 각 수정의 구체적 내용
- 조건부 항목의 추가 수정 사항

### 사용자 승인 게이트 ✋

Orchestrator가 사용자에게 검증 결과 + 구현 계획 전달:
- ❌ 위험 판정 항목 보고
- 구현 계획 확인
- 사용자 확정 후 Phase 4 진입

### Phase 3 완료 조건
- [ ] 검증 보고서 작성 완료
- [ ] 구현 계획 수립 완료
- [ ] 사용자 승인 완료

## Phase 4: 구현

**담당**: Implementer (서브에이전트, 개선사항별 순차)
**소요**: 중간 (수정 횟수에 따라)

### 작업 프로토콜

개선사항 하나씩 순차 실행:

```
개선사항 1:
  1. 구현 계획 확인
  2. 대상 파일 읽기
  3. 수정 실행
  4. 구현 보고서 작성
  5. Orchestrator에게 반환

개선사항 2:
  (동일 프로세스)

...

전체 완료 → Phase 5로 전달
```

### Implementer에게 전달하는 정보

각 개선사항마다:
- 구현 계획 (Flow Guardian 승인본)
- 대상 파일 전체 내용
- 기존 스타일/포맷 예시

### 금지 사항 (Phase 4 특수)

1. **계획 외 수정 절대 금지**
   - "이것도 고치면 좋겠다" → 별도 이슈로 보고만
   - "포맷이 일관적이지 않아서" → 수정 대상 섹션 내부만

2. **삭제 최소화**
   - 기존 내용 삭제보다 추가/보강 위주
   - 삭제가 필요하면 구현 계획에 명시되어 있어야 함

3. **구조 변경 금지**
   - 파일 분리, 통합, 이동 금지
   - 파일 이름 변경 금지

### Phase 4 완료 조건
- [ ] 모든 개선사항 구현 완료
- [ ] 각 개선사항별 구현 보고서 작성
- [ ] 계획 외 발견 사항 기록 (있을 경우)

## Phase 5: 리뷰

**담당**: Reviewer (서브에이전트)
**소요**: 긴 편 (라운드 수에 따라)

### 리뷰 프로세스

```
Round 1: SKILL.md 검토
Round 2: references/ 파일 A 검토
Round 3: references/ 파일 B 검토
Round N: ... (대상 스킬의 파일 수만큼)
Round N+1: 역검증
```

### 라운드별 검토 절차

각 파일에 대해:

#### 1. 파일 목적 확인
- 이 파일이 스킬에서 하는 역할은?
- 이 파일을 읽는 에이전트/시점은?

#### 2. 변경점 확인
- v{N-1} 백업과 diff
- 추가된 내용, 수정된 내용, 삭제된 내용 식별

#### 3. 내적 일관성 확인
- 파일 내부에서 앞뒤가 맞는가?
- 번호, 이름, 개수가 일치하는가?

#### 4. 교차 참조 확인
- 이 파일이 참조하는 다른 파일과 일치하는가?
- 다른 파일이 이 파일을 참조할 때 정확한가?

#### 5. "왜 없는지 분석" 적용
- 빠진 것이 있으면 → 3단계 분석 (이전 버전/역할 목적/교차 참조)
- 3단계 모두 "있어야 한다"일 때만 이슈로 보고

### 이슈 → 재수정 루프

```
Reviewer 이슈 보고
    ↓
Flow Guardian 판정 ("이 수정이 진짜 필요한가?")
    ↓
┌──────────────────┬──────────────────────┐
│ 🚫 수정 불필요    │ ✅ 수정 필요          │
│ "의도된 설계다"   │    ↓                 │
│ → 이슈 기각      │ Implementer 재수정    │
│ (근거 기록)       │    ↓                 │
│                  │ Flow Guardian 재검증  │
│                  │ (수정 결과 확인)       │
└──────────────────┴──────────────────────┘
```

**왜 Reviewer가 아니라 Flow Guardian이 재검증하는가**:
- Flow Guardian이 "수정 필요"라고 판정한 근거를 알고 있으므로, 수정 결과가 그 근거를 충족하는지 직접 확인하는 것이 정확하다
- Reviewer에게 돌리면 또 다른 잘못된 이슈를 올릴 수 있고 같은 루프가 반복될 수 있다
- Flow Guardian은 코드의 전체 구조를 파악하고 있으므로, 수정이 다른 곳을 깨뜨리지 않는지도 함께 확인한다

### 역검증 (전체 리뷰 완료 후)

모든 라운드 완료 후 최종 안전장치:

1. **수정 필요성 재확인**: 각 적용된 수정이 진짜 필요했는가?
2. **의도적 차이 점검**: 역할이 다른 두 곳의 내용을 무분별하게 동기화하지 않았는가?
3. **신규 불일치 점검**: 수정으로 인해 새로운 교차 참조 오류가 생기지 않았는가?

역검증 이슈 발견 시 → Orchestrator에게 롤백/추가수정 판단 요청

### Phase 5 완료 조건
- [ ] 모든 파일 라운드 검토 완료
- [ ] 🔴 필수 수정 이슈 0건 (전부 해결)
- [ ] 역검증 완료
- [ ] 최종 리뷰 보고서 작성

## Phase 6: 마무리

**담당**: Orchestrator (직접 수행)
**소요**: 짧음

### Step 1: 버전 갱신

1. SKILL.md의 `version` 필드 업데이트
2. `changelog`에 이번 버전 내용 추가:
   - 버전 번호
   - 날짜
   - 적용된 개선사항 목록 (한줄씩)
   - 출처 (어떤 스킬에서 영감)

### Step 2: 기록 업데이트

MEMORY.md에 기록:
```
- v{N} (백업): ~/.claude/skills-archive/{skill-name}-v{N-1}/
  - 백업 날짜: {날짜}
- v{N+1} (활성): ~/.claude/skills/{skill-name}/
  - 변경사항: {주요 변경 요약}
```

### Step 3: 최종 보고

사용자에게 전달:
```markdown
## 스킬 진화 완료 — {스킬명} v{N} → v{N+1}

### 적용된 개선사항
1. {개선1}: {한줄 설명}
2. {개선2}: {한줄 설명}
...

### 파일별 변경 요약
| 파일 | 변경 유형 | 라인 변화 |
|------|----------|----------|

### 리뷰 결과
- 총 이슈: {N}건
- 해결: {N}건
- PASS with Notes: {N}건
- 역검증 이슈: {N}건

### 백업 위치
{경로}
```

- [ ] changelog 업데이트 완료
- [ ] MEMORY.md 업데이트 완료
- [ ] 최종 보고 완료
