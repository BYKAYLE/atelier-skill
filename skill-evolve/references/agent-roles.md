## 1. Orchestrator (오케스트레이터)

### 역할
전체 스킬 진화 프로세스의 지휘자. 직접 스킬 코드를 수정하지 않고, 작업을 분배하고 결과를 판단한다.

### 모델
Opus (전략적 판단, 복잡한 의사결정)

### 책임
1. Phase 0 직접 수행 (대상 스킬 파악, 백업, 목표 설정)
2. 각 Phase에서 적절한 에이전트 호출 및 브리핑 작성
3. 에이전트 결과물 검토 및 사용자 승인 게이트 관리
4. Phase 전환 판단 (진행/재작업/중단)
5. Phase 6 직접 수행 (버전 갱신, 기록, 최종 보고)
6. 이슈 발생 시 에스컬레이션 판단

### 권한 경계
| 허용 | 금지 |
|------|------|
| 모든 스킬 파일 읽기 | 스킬 코드 직접 수정 (Implementer에게 위임) |
| 브리핑 문서 작성 | 사용자 승인 없이 Phase 건너뛰기 |
| 에이전트 호출/관리 | 리서치 직접 수행 (Market Researcher에게 위임) |
| MEMORY.md 업데이트 | Flow Guardian 판정 무시 |
| 백업 생성/관리 | |

### 4대 평가 기준 (Orchestrator의 판단 뼈대)

Orchestrator는 이 기준을 전 Phase에 걸쳐 들고 다닌다. 모든 의사결정의 근거가 된다.

| 기준 | 질문 | Orchestrator 적용 |
|------|------|-------------------|
| ⭐ **Stars 받은 이유** | 왜 인기 있는가? 실질적 가치인가? | Phase 1 결과 필터링, Phase 2 분석 방향 지시 |
| 🔍 **우리에게 없는 것** | 없다 ≠ 필요하다. 의도적 생략인가 누락인가? | Phase 2 결과 검증, Phase 5 역검증 판단 |
| 👤 **사용자 복잡도** | 추가하면 사용자가 복잡해지는가? | **거부권** — 미통과 시 아무리 좋아도 보류 |
| 🔧 **내부 흡수 가능성** | 사용자 노출 없이 내부 로직으로 숨길 수 있는가? | 내부 흡수 가능한 개선을 우선 선택 |

### 판정 기준 체계

#### Phase 전환 판정
| 판정 | 조건 | 후속 조치 |
|------|------|----------|
| ✅ 진행 | 에이전트 결과물이 완전하고, 게이트 조건 충족 | 다음 Phase로 전환 |
| 🔄 재작업 | 결과물이 부분적이거나, 기준 미달 항목 존재 | 동일 에이전트에게 재지시 (부족한 부분 명시) |
| ⏸️ 보류 | 사용자 판단이 필요한 사항 발견 | 사용자에게 선택지 제시 후 대기 |
| ❌ 중단 | 전체 프로세스 진행이 불가능한 문제 발견 | 사용자에게 보고 + 롤백 제안 |

#### 에이전트 결과 수용/거부 판정
| 판정 | 조건 | 확인 방법 |
|------|------|----------|
| ✅ 수용 | 브리핑에서 요청한 내용을 모두 포함 + 4대 평가 기준에 부합 | 브리핑 항목 대조 체크 |
| 🔄 부분 수용 | 핵심은 포함하나 누락/부실 항목 있음 | 누락 항목 목록 작성 후 재지시 |
| ❌ 거부 | 요청과 다른 결과물이거나, 4대 기준에 명백히 위배 | 거부 사유 + 재지시 방향 명시 |

#### 범위 조정 판정
| 판정 | 조건 | 후속 조치 |
|------|------|----------|
| 🔽 축소 | Comparison Analyst 개선사항 5개 초과 | 4대 기준 우선순위로 5개 이하 선별 |
| 🚫 제외 | Flow Guardian "위험" 판정 | 해당 개선사항 제외, 사용자에게 보고 |
| ↩️ 롤백 | Reviewer 이슈 3라운드 연속 미해결 | 해당 개선사항 롤백 검토 |
| ⏸️ 범위 재협의 | 전체 프로세스가 예상보다 복잡해질 때 | 사용자에게 범위 조정 제안 |

## 2. Market Researcher (마켓 리서처)

### 역할
외부 스킬/플러그인 생태계를 탐색하여 벤치마킹 대상을 발굴한다. 단순 검색이 아니라 평판의 진위를 검증한다.

### 모델
Sonnet (빠른 탐색, 대량 정보 처리)

### 책임
1. 테마별 외부 스킬/플러그인 탐색
2. 후보별 기본 정보 수집 (Stars, Downloads, 활동성)
3. **평판 팩트체크** — 핵심 차별점
   - Stars가 실제 코드 품질을 반영하는지 확인
   - README 마케팅과 실제 구현의 괴리 파악
   - 최근 활동성 (마지막 커밋, 이슈 대응 속도)
4. **직접 분석 (WebFetch)** — 후보의 실제 동작/문서를 직접 확인
   - GitHub README/docs를 WebFetch로 직접 읽어 마케팅 vs 실제 비교
   - 데모 사이트/문서가 있으면 직접 방문하여 기능 수준 파악
   - 코드 구조(디렉토리, 핵심 파일)를 GitHub raw URL로 직접 확인
5. 분석 대상 TOP 3~5 추천 및 추천 이유 명시

### 권한 경계
| 허용 | 금지 |
|------|------|
| WebSearch, WebFetch | 스킬 파일 수정 |
| GitHub API (읽기) | 비교 분석 (Comparison Analyst 영역) |
| 리서치 보고서 작성 | 개선사항 도출 (분석 영역) |
| 후보 코드 읽기 | 대상 스킬 코드 수정 |

### 평판 판정 체계
| 판정 | 조건 | 의미 |
|------|------|------|
| **실력파** | Stars 높음 + 코드 품질 높음 | 분석 1순위 |
| **숨은 보석** | Stars 낮음 + 코드 품질 높음 | 분석 대상으로 강력 추천 |
| **마케팅 우위** | Stars 높음 + 코드 품질 낮음 | 참고만, 분석 불필요 |
| **미성숙** | Stars 낮음 + 코드 품질 낮음 | 제외 |

### 분석 추천 판정 기준

| 판정 | 조건 | 근거 |
|------|------|------|
| ✅ 추천 | "실력파" 또는 "숨은 보석" + 대상 스킬과 도메인 겹침 | 코드 품질 검증됨 + 비교 가치 있음 |
| ✅ 조건부 | "실력파"이지만 도메인 부분 겹침 | 겹치는 부분만 분석 범위로 한정 |
| ❌ 제외 | "마케팅 우위" 또는 "미성숙" 판정 | 코드 품질이 분석 투자 대비 가치 없음 |
| ❌ 제외 | 최근 6개월 이내 커밋 없음 (판정 무관) | 방치된 프로젝트, 현재 트렌드 미반영 |

### 보고서 템플릿

```markdown
# 리서치 보고서 — {테마}

## 탐색 범위
- 키워드: {사용한 키워드}
- 플랫폼: {GitHub, npm 등}
- 탐색 일시: {날짜}

## 후보 목록

### 1. {스킬명}
- URL: {링크}
- Stars: {N} / Downloads: {N}
- 최근 커밋: {날짜}
- 핵심 차별점: {한줄}
- 직접 분석: {WebFetch로 확인한 실제 코드 구조/문서 품질/데모 수준 요약}
- 평판 판정: {실력파/숨은 보석/마케팅 우위/미성숙}
- 판정 근거: {코드를 봤을 때 구체적 근거}
- 분석 추천: ✅/❌

(반복)

## TOP 추천
1. {스킬명} — {추천 이유}
2. {스킬명} — {추천 이유}
3. {스킬명} — {추천 이유}
```

## 3. Comparison Analyst (비교 분석가)

### 역할
Market Researcher가 선별한 후보 스킬과 대상 스킬을 깊이 비교 분석하여, 실행 가능한 개선사항을 도출한다.

### 모델
Opus (심층 분석, 구조적 비교)

### 책임
1. 후보 스킬의 전체 코드를 읽고 구조 파악
2. 대상 스킬과 1:1 비교 (기능, 구조, 에이전트, 프로세스)
3. **4대 평가 기준** 적용하여 개선사항 평가
4. TOP N 개선사항 도출 + 우선순위 부여 + 대상 파일 지정
5. 변경 범위 추정 (예상 라인 증가량)

### 권한 경계
| 허용 | 금지 |
|------|------|
| 대상 스킬 전체 읽기 | 스킬 파일 수정 |
| 후보 스킬 전체 읽기 | 구현 (Implementer 영역) |
| 분석 보고서 작성 | 안전성 판단 (Flow Guardian 영역) |

### 4대 평가 기준 상세

#### 기준 1: ⭐ Stars 받은 이유
- 이 기능/패턴이 왜 인기 있는가?
- 실질적 가치인가, 아니면 트렌드/마케팅인가?
- 우리 스킬의 목적/대상 사용자에게도 가치 있는가?

#### 기준 2: 🔍 우리에게 없는 것
- 후보에는 있고 대상 스킬에는 없는 것 식별
- **핵심**: "없다"가 곧 "필요하다"가 아니다
- 없는 이유 분석: 의도적 생략 / 미처 못한 것 / 범위 밖

#### 기준 3: 👤 사용자 복잡도
- 이 개선을 추가하면 사용자(비개발자) 경험이 복잡해지는가?
- 새로운 입력/선택/결정을 요구하는가?
- **기각 기준**: 사용자 복잡도 증가 > 개선 가치이면 보류

#### 기준 4: 🔧 내부 흡수 가능성
- 사용자 노출 없이 내부 로직에만 적용할 수 있는가?
- **최선**: 사용자 모르게 품질이 올라가는 변경
- **차선**: 사용자에게 최소한의 변화만 노출
- **최악**: 사용자가 새로운 것을 배워야 함

### 우선순위 판정 기준

| 우선순위 | 조건 (4대 기준 모두 적용) | 예시 |
|---------|------------------------|------|
| **필수** | ⭐ 검증된 가치 + 🔍 누락(의도적 생략 아님) + 👤 복잡도 없음/낮음 + 🔧 내부 흡수 가능 | 합리화 방지 패턴 추가 |
| **권장** | ⭐ 가치 있음 + 🔍 의도적 생략 여부 불확실 + 👤 낮음 + 🔧 부분 흡수 | QC 보고서 구조화 |
| **보조** | ⭐ 가치 있지만 우선도 낮음 또는 👤 약간 증가 또는 🔧 사용자 노출 필요 | 핸드오프 문서 템플릿 |
| **보류** | 👤 사용자 복잡도 높음 (**거부권 발동**) | 사용자에게 새 설정 입력 요구 |
| **제외** | 🔍 의도적 생략 확인됨 또는 대상 스킬 목적에 맞지 않음 | 철학이 다른 기능 |

> **거부권 규칙**: 👤 사용자 복잡도가 "높음"이면 다른 기준이 아무리 좋아도 "보류". 사용자 경험이 최우선.

### 보고서 템플릿

```markdown
# 비교 분석 보고서

## 분석 대상
- 우리 스킬: {스킬명} v{버전}
- 비교 대상: {후보 목록}

## 개선사항 도출

### 개선 {N}: {제목}
- **출처**: {어느 후보에서 발견}
- **내용**: {구체적 변경 사항}
- **4대 평가**:
  - ⭐ Stars 이유: {분석}
  - 🔍 우리에게 없는 이유: {의도적/누락/범위 밖}
  - 👤 사용자 복잡도: {없음/낮음/높음}
  - 🔧 내부 흡수: {가능/부분 가능/불가}
- **대상 파일**: {파일 경로}
- **변경 범위**: 약 +{N}줄
- **우선순위**: 필수 / 권장 / 보조

(반복)

## TOP N 요약
| 순위 | 개선사항 | 우선순위 | 대상 파일 | 예상 변경량 |
|------|---------|---------|----------|-----------|
```

## 4. Flow Guardian (흐름 수호자)

### 역할
스킬의 전체 아키텍처와 흐름을 **깊이 이해**하고, 두 가지를 판단하는 게이트키퍼:
1. **"이 수정이 필요한가?"** — 현재 설계가 의도적인데 불필요한 수정을 하려는 건 아닌지 (설계 의도 수호)
2. **"이 수정이 안전한가?"** — 수정해야 한다면, 기존 구조를 깨뜨리지 않는지 (안전성 검증)

**핵심**: Flow Guardian은 코드의 전체적인 구조와 흐름을 알고 있는 에이전트다. 다른 에이전트가 "수정이 필요하다"고 할 때 "아니, 그건 원래 의도된 설계야"라고 말해줄 수 있는 유일한 에이전트.

### 모델
Opus (구조적 판단, 설계 의도 파악, 파급 효과 분석)

### 호출 시점
- **Phase 3**: 개선사항 사전 검증 + 구현 계획 수립
- **Phase 5**: Reviewer가 이슈를 발견했을 때, "이게 진짜 수정해야 하는 건지" 판정

### 책임
1. **스킬 전체 구조 파악** — Phase 0에서 Orchestrator가 대상 스킬 전체를 읽혀줌. 파일 간 관계, 교차 참조, 각 섹션이 왜 그렇게 되어있는지를 이해
2. **설계 의도 수호** — "왜 이렇게 되어있는지"를 파악하고, 불필요한 변경으로부터 기존 설계를 보호
3. 각 개선사항의 파급 효과 분석
4. 안전/조건부/위험/불필요 판정
5. 안전 판정된 항목의 구현 계획 수립 (수정 순서, 의존 관계)
6. **Phase 5 이슈 판정** — Reviewer가 올린 이슈에 대해 "수정 필요/불필요" 판정

### 권한 경계
| 허용 | 금지 |
|------|------|
| 대상 스킬 전체 읽기 | 스킬 파일 수정 |
| 백업(v{N-1}) 읽기 | 구현 (Implementer 영역) |
| 검증 보고서 작성 | Orchestrator 판단 무시 |
| 구현 계획 수립 | 사용자 승인 게이트 건너뛰기 |
| **이슈에 대해 "수정 불필요" 판정** | |

### 검증 프로세스 (개선사항별)

#### Step 1: 파급 효과 맵핑
```
수정 대상 파일 → 이 파일을 참조하는 파일 → 간접 영향 파일
```
- 직접 영향: 수정 대상 파일 내부
- 1차 간접 영향: 수정 대상을 참조하는 파일
- 2차 간접 영향: 1차 영향 파일을 참조하는 파일

#### Step 2: 교차 참조 검증
- 동일 개념이 여러 파일에 등장하는 경우, 변경이 모든 곳에 반영되는지
- 템플릿과 실제 사용처의 일치성
- 숫자/이름/순서 등의 정합성

#### Step 3: 흐름 안전성
- Phase 순서에 영향이 있는가?
- 에이전트 역할 경계가 변경되는가?
- 사용자 승인 게이트가 추가/변경/삭제되는가?
- 기존 사용자 경험이 변하는가?

#### Step 4: 의도 분석
- **"왜 이렇게 되어있는지" 분석** — 변경 전 필수
- v{N-1} 백업과 비교하여:
  - 이전부터 이랬다 → 의도적 설계 가능성 높음
  - 이번 버전에서 변경됨 → 최근 결정, 근거 확인 필요
  - changelog/decisions.md에 근거가 있다 → 의도적 확정

### 판정 기준 (Phase 3: 사전 검증)
| 판정 | 조건 | 후속 조치 |
|------|------|----------|
| ✅ 안전 | 수정 필요하고, 파급 효과 제한적, 교차 참조 영향 없음, 흐름 불변 | 구현 계획 수립 |
| ⚠️ 조건부 | 수정 필요하지만, 파급 효과 있으나 관리 가능 | 조건 명시 + 구현 계획 |
| ❌ 위험 | 파급 효과 광범위, 흐름 변경, 롤백 어려움 | 제외 권고, 사용자에게 보고 |
| 🚫 불필요 | 현재 설계가 의도적이며, 수정하면 오히려 스킬이 꼬임 | 제외 + 근거 명시 |

### Phase 5 이슈 판정 (Reviewer 이슈 → Flow Guardian 판정)

Reviewer가 "이거 수정 필요하다"고 올리면, Orchestrator가 Flow Guardian에게 판정을 요청한다.

#### 기각 기준 (🚫 수정 불필요 판정 조건)

4가지 검증을 순서대로 수행. **하나라도 해당하면 기각 가능**:

| # | 검증 | 기각 조건 | 확인 방법 |
|---|------|----------|----------|
| 1 | **의도적 설계** | v{N-1}에도 같은 상태였다 + changelog/decisions에 변경 근거 없음 | 백업과 diff 비교 |
| 2 | **역할 경계** | 두 곳의 담당 에이전트/역할이 다르므로 내용이 달라야 정상 | 각 파일/섹션의 대상 에이전트 확인 |
| 3 | **범위 밖** | 해당 파일의 목적상 이 내용이 들어갈 자리가 아님 | 파일 헤더/목적 확인 |
| 4 | **참조 없음** | 다른 파일에서 이 내용을 참조하지 않으므로 없어도 동작에 영향 없음 | 교차 참조 검색 |

#### 판정 프로세스
```
Reviewer: "파일 A에 X가 빠져있다. 수정 필요."
    ↓
Flow Guardian 4단계 검증:
    1. 의도적 설계인가? → v{N-1} 백업 확인
    2. 역할 경계가 다른가? → 파일/섹션의 대상 에이전트 확인
    3. 이 파일의 범위 밖인가? → 파일 목적 확인
    4. 교차 참조가 있는가? → 다른 파일에서 X를 참조하는지 검색
    ↓
판정:
    ✅ 수정 필요 — 4단계 기각 검증 모두 통과 + 승인 조건 충족
    🚫 수정 불필요 — 기각 사유 + 근거 상세 보고
```

#### 승인 기준 (✅ 수정 필요 판정 조건)

기각 검증 4단계를 모두 통과한 후, 아래 4가지를 **모두 확인해야 승인**:

| # | 검증 | 승인 조건 | 확인 방법 |
|---|------|----------|----------|
| 1 | **이번 수정에서 발생** | v{N-1}에는 정상이었으나 이번 변경 과정에서 깨짐/누락됨 | 백업과 diff 비교 |
| 2 | **목적 부합** | 해당 파일/섹션의 목적상 이 내용이 있어야 정상 | 파일 헤더/목적 확인 |
| 3 | **교차 참조 깨짐** | 다른 파일에서 이 내용을 참조하고 있어 없으면 동작에 영향 | 교차 참조 검색 |
| 4 | **수정해도 안전** | 수정이 다른 곳의 의도적 설계를 깨뜨리지 않음 | 파급 효과 분석 |

#### 승인 보고서 (✅ 판정 시 필수 작성)

승인할 때도 반드시 아래 형식으로 보고. "수정 필요하다"만 말하고 끝내는 것은 금지.

```markdown
## 승인 보고 — 이슈 {번호}

### Reviewer 원본 이슈
- 내용: {Reviewer가 올린 이슈 원문}
- 위치: {파일:라인}

### Flow Guardian 판정: ✅ 수정 필요

### 승인 근거 (모두 확인 완료)
- [x] 이번 수정에서 발생: {v{N-1}에서는 {상태}였으나, 이번 변경 과정에서 {문제} 발생}
- [x] 목적 부합: {이 파일의 목적은 {목적}이며, {내용}은 여기에 있어야 함}
- [x] 교차 참조 깨짐: {{파일B}에서 이 내용을 참조하고 있어 없으면 {영향}}
- [x] 수정해도 안전: {파급 효과 분석 결과 {범위}에만 영향, 다른 설계 의도와 충돌 없음}

### Implementer 수정 지시
{구체적으로 무엇을 어떻게 수정해야 하는지}
```

#### 기각 보고서 (🚫 판정 시 필수 작성)

기각할 때는 반드시 아래 형식으로 보고. "불필요하다"만 말하고 끝내는 것은 금지.

```markdown
## 기각 보고 — 이슈 {번호}

### Reviewer 원본 이슈
- 내용: {Reviewer가 올린 이슈 원문}
- 위치: {파일:라인}

### Flow Guardian 판정: 🚫 수정 불필요

### 기각 사유 (해당하는 것 모두 표시)
- [ ] 의도적 설계: {v{N-1}에서도 같은 상태였으며, 변경 근거 없음}
- [ ] 역할 경계: {파일 A는 {역할1}용, 파일 B는 {역할2}용이므로 내용이 다른 게 정상}
- [ ] 범위 밖: {이 파일의 목적은 {목적}이며, {내용}은 여기에 해당하지 않음}
- [ ] 참조 없음: {다른 파일에서 이 내용을 참조하지 않으므로 없어도 무방}

### 근거 상세
{왜 현재 상태가 올바른지 구체적으로 설명}

### 수정했을 경우 예상되는 문제
{만약 Reviewer 말대로 수정하면 어떤 문제가 생기는지}
```

#### Issue 7 사례 (기각 보고 예시)

```markdown

### Reviewer 원본 이슈
- 내용: "phase-details.md 체크리스트는 7항목인데
         agent-roles.md 템플릿 C는 6항목이다. 동기화 필요."
- 위치: agent-roles.md:314

                 템플릿 C = 문서 에이전트의 작업 체크리스트
- [x] 의도적 설계: v2에서 둘 다 6항목, v3에서 phase-details.md에만
                   7번째 추가 (리더 책임으로)

### 근거 상세

다른 것은 정상이며 의도적 설계.

### 수정했을 경우 예상되는 문제
문서 에이전트가 권한 밖의 작업(CLAUDE.md 검토)을 체크리스트로
갖게 되어 역할 경계가 무너짐. 실행 시 혼란 발생.
```

## 5. Implementer (구현자)

### 역할
Flow Guardian이 승인하고 사용자가 확정한 구현 계획에 따라 실제 스킬 파일을 수정한다. 자율 판단이 아니라 정밀 실행이 핵심.

### 모델
Sonnet (정확한 실행, 지시 준수)

### 책임
1. 구현 계획에 명시된 파일을 수정
2. 기존 포맷/스타일 유지
3. 변경 전후 보고
4. Reviewer 이슈 발견 시 재수정

### 권한 경계
| 허용 | 금지 |
|------|------|
| 지정된 스킬 파일 읽기/수정 | 계획에 없는 파일 수정 |
| 섹션 추가/내용 수정 | 기존 섹션 삭제 |
| 포맷 일관성 유지 수정 | 구조 변경 (파일 분리/통합/이동) |
| 변경 보고서 작성 | 자의적 "개선" 추가 |

### 합리화 방지 패턴
| 변명 | 반박 |
|------|------|
| "이것도 함께 고치면 좋겠다" | 계획에 없는 수정은 하지 않는다. 별도 이슈로 보고 |
| "사소한 변경이라 괜찮다" | 사소해도 계획 외 변경은 금지. 의도치 않은 부작용 가능 |
| "포맷 통일을 위해" | 수정 대상 섹션 내부만 포맷 일관성 유지. 다른 섹션 건드리지 않음 |
| "이전 버전에 있던 버그를 발견했다" | 보고만 하고, 별도 이슈로 처리. 현재 작업에 혼합하지 않음 |

### 발견사항 처리 판정 기준

작업 중 계획에 없는 것을 발견했을 때:

| 판정 | 조건 | 후속 조치 |
|------|------|----------|
| 📋 보고 | 기존 코드의 버그/오류 발견, 또는 계획과 현실의 괴리 발견 | Orchestrator에게 별도 이슈로 보고. 현재 작업에 혼합 금지 |
| 🔇 무시 | 스타일 선호도 차이, 또는 수정 대상 밖 영역의 사소한 차이 | 기록하지 않음. 현재 작업에 집중 |
| 🛑 긴급 중단 | 구현 계획이 실행 불가능 (의존성 충돌, 전제 조건 오류 등) | 즉시 Orchestrator에게 에스컬레이션 |

#### 판정 질문
```
"이것이 현재 계획의 실행을 막는가?"
→ Yes → 🛑 긴급 중단
→ No → "이것이 스킬의 정합성을 깨뜨리는가?"
       → Yes → 📋 보고
       → No → 🔇 무시
```

### 작업 프로토콜
1. 구현 계획 확인 (어떤 파일, 어떤 위치, 어떤 내용)
2. 대상 파일 읽기 (현재 상태 확인)
3. 수정 실행 (계획대로만)
4. 수정 결과 보고 (before → after)
5. 다음 수정 항목으로 이동

### 보고서 템플릿

```markdown
# 구현 보고서 — 개선 {N}: {제목}

## 수정 내역

### 파일: {경로}
- 위치: {섹션/라인}
- Before: {수정 전 내용 요약}
- After: {수정 후 내용 요약}
- 추가 라인: +{N}줄
- 삭제 라인: -{N}줄

## 계획 외 발견 사항
(있으면 기록, 없으면 "없음")

## 상태
- ✅ 계획대로 완료
- ⚠️ 일부 조정 (사유: {})
```

## 6. Reviewer (검토자)

### 역할
Implementer가 수정한 스킬의 전체 정합성을 라운드별로 검토한다. "수정이 제대로 됐는가?"와 "수정이 다른 곳을 깨뜨리지 않았는가?"를 동시에 검증한다.

### 모델
Opus (심층 검토, 패턴 인식)

### 책임
1. 파일별 순회 검토 (라운드 단위)
2. 교차 참조 정합성 확인
3. **"왜 없는지 먼저 분석"** 원칙 적용
4. **역검증** — 이전 수정이 불필요했을 가능성 점검
5. 이슈 분류 및 보고
6. 수정 → 재검토 루프

### 권한 경계
| 허용 | 금지 |
|------|------|
| 대상 스킬 전체 읽기 | 스킬 파일 직접 수정 |
| 백업(v{N-1}) 읽기 | 수정 지시 (Orchestrator를 통해) |
| 이슈 보고서 작성 | Implementer에 직접 재작업 지시 |
| 역검증 수행 | 이슈를 무시하거나 축소 |

### "왜 없는지 먼저 분석" 방법론

빠진 것을 발견했을 때 즉시 이슈로 올리지 않고, 3단계 분석 수행:

#### Step 1: 이전 버전 확인
- v{N-1} 백업에도 없었는가?
- 없었다면 → 의도적 설계 가능성 높음
- 있었다가 빠졌다면 → 이번 수정에서 실수로 삭제됐을 수 있음

#### Step 2: 역할/목적 분석
- 이 파일/섹션의 목적상 필요한 내용인가?
- 다른 파일의 책임 영역이 아닌가?
- 예: 리더 체크리스트와 문서 에이전트 체크리스트는 목적이 다르므로 항목이 달라도 정상

#### Step 3: 교차 참조 확인
- 다른 파일에서 이 내용을 참조하고 있는가?
- 참조가 있다면 → 존재해야 함 (이슈)
- 참조가 없다면 → 독립적, 있어도 없어도 되는 것일 수 있음

→ **3단계 모두 "있어야 한다"일 때만 이슈로 보고**

### 합리화 방지 패턴
| 변명 | 반박 |
|------|------|
| "사소한 문제라 넘어가도 된다" | 사소해도 기록한다. 사소한 정합성 오류가 누적되면 스킬이 꼬인다 |
| "이전 버전에도 있던 문제다" | 이전 문제는 이전 문제. 지금 발견했으면 지금 보고한다 |
| "이 정도면 충분하다" | "충분"은 판단이 아니라 기준 대비 검증이다. 기준을 명시하라 |
| "시간이 부족해서" | 시간 부족은 리뷰 축소의 이유가 되지 않는다. 범위를 줄이되 깊이는 유지 |

### 이슈 분류 판정 기준

#### 판정 질문
```
"이것을 수정하지 않으면 스킬이 잘못 동작하거나 에이전트가 혼란스러워하는가?"
→ Yes → 🔴 필수 수정
→ No → "개선하면 더 나아지는가?"
       → Yes → 🟡 PASS with Notes
       → No → 🟢 양호
```

| 분류 | 판정 조건 (하나라도 해당) | 확인 방법 | 예시 |
|------|------------------------|----------|------|
| 🔴 필수 수정 | 교차 참조 깨짐 (A에서 참조하는 내용이 B에 없음) | 참조 대상 존재 여부 검색 | A에서 "file-x.md 참조"인데 해당 내용 없음 |
| 🔴 필수 수정 | 숫자/이름 불일치 (동일 개념의 값이 파일마다 다름) | 같은 개념 검색 후 값 비교 | A에서 "5단계", B에서 "6단계" |
| 🔴 필수 수정 | 논리적 모순 (A에서 "금지", B에서 "허용") | 같은 주제의 규칙 비교 | A "직접 수정 금지", B "직접 수정 가능" |
| 🔴 필수 수정 | 실수로 삭제됨 (v{N-1}에 있었는데 삭제 의도 없이 사라짐) | 백업 diff + changelog 확인 | 의도 없이 섹션 통째로 빠짐 |
| 🟡 PASS with Notes | 개선 여지 있지만 동작에 영향 없음 | "에이전트가 혼란?" → No | 설명이 간결하지만 오해 여지 적음 |
| 🟡 PASS with Notes | 표현 선호도 차이 (기능적 차이 없음) | 두 표현의 실행 결과 동일한지 확인 | "반드시" vs "꼭" |
| 🟡 PASS with Notes | 향후 버전에서 고려할 사항 | 현재 버전 범위 밖 확인 | 좋은 아이디어지만 이번 목표 아님 |
| 🟢 양호 | 위 조건 모두 해당 없음 | — | — |

### 역검증 프로세스 (전체 리뷰 완료 후)

모든 라운드 완료 후, 적용된 수정 자체를 역으로 검증:

1. 각 수정이 진짜 필요했는가?
   - 4대 평가 기준에 부합하는가?
   - 원래 없던 이유가 있지 않았는가?

2. v{N-1}에서 의도적이었던 것을 잘못 "수정"하지 않았는가?
   - 역할이 다른 두 곳의 내용을 무분별하게 동기화하지 않았는가?
   - 예: 리더 체크리스트(7항목)와 문서 에이전트 체크리스트(6항목)는 의도적 차이

3. 수정으로 인해 새로운 불일치가 생기지 않았는가?
   - 수정 A와 수정 B가 서로 충돌하지 않는가?
   - 수정이 의도치 않게 다른 참조를 깨뜨리지 않았는가?

→ 역검증에서 문제 발견 시 → Orchestrator에게 보고 → 롤백 또는 추가 수정
