# Skill Evolve System

기존 스킬을 체계적으로 분석하고, 외부 벤치마킹을 거쳐, 안전하게 버전업하는 오케스트레이터.

핵심 철학: "감으로 개선"이 아니라 "근거 기반 진화". 외부 비교 → 내부 검증 → 안전한 적용 → 정합성 확인.

---

## 핵심 원칙 (우선순위 순)

1. **백업 우선** — 변경 전 반드시 현재 버전을 백업. 롤백 가능해야 한다.
2. **근거 기반** — 모든 개선사항에는 "왜 추가하는가"의 근거가 있어야 한다. 감이 아닌 비교 분석.
3. **안전한 변경** — 기존 흐름을 깨뜨리지 않는 변경만 허용. Flow Guardian이 사전 검증.
4. **정합성 검증** — 수정 후 전체 스킬의 내적 일관성을 라운드별로 검토. 교차 참조 무결성 확인.
5. **왜 없는지 먼저 분석** — 빠진 것을 발견했을 때, "추가해야 한다"가 아니라 "왜 빠져있는지" 먼저 분석.
6. **사용자 승인 게이트** — 리서치 결과, 개선 목록, 구현 계획은 사용자 승인 후 진행.

---

## 4대 평가 기준 (Orchestrator 판단 뼈대)

이 기준은 Orchestrator가 전 Phase에 걸쳐 들고 다니는 판단 프레임워크다. 리서치 결과를 평가할 때, 개선사항을 선별할 때, 구현 계획을 승인할 때, 리뷰 이슈를 판단할 때 — 모든 의사결정의 기준이 된다.

| 기준 | 질문 | 통과 조건 |
|------|------|----------|
| ⭐ **Stars 받은 이유** | 이 기능/패턴이 왜 인기 있는가? | 실질적 가치가 있다 (트렌드/마케팅이 아니라) |
| 🔍 **우리에게 없는 것** | 대상 스킬에 없는 것 중 진짜 가치 있는 것은? | 의도적 생략이 아니라 진짜 누락이다 |
| 👤 **사용자 복잡도** | 추가하면 사용자 경험이 복잡해지는가? | 복잡해지지 않는다 **(거부권 — 이 기준 미통과 시 아무리 좋아도 보류)** |
| 🔧 **내부 흡수 가능성** | 사용자 노출 없이 내부 로직으로 숨길 수 있는가? | 가능하다 (사용자 모르게 품질이 올라가는 것이 최선) |

### 적용 시점
- **Phase 1** (리서치): Market Researcher가 후보를 올리면, Orchestrator가 4대 기준으로 1차 필터링
- **Phase 2** (분석): Comparison Analyst가 이 기준을 상세 적용하여 개선사항 도출
- **Phase 3** (검증): Flow Guardian 판정에 4대 기준 부합 여부를 추가 확인
- **Phase 5** (리뷰): Reviewer 이슈 판단 시 "이 수정이 4대 기준에 부합했는가?" 역검증

## 에이전트 구조

| 에이전트 | 모델 | 역할 요약 | 호출 Phase |
|----------|------|----------|-----------|
| **Orchestrator** (리더) | Opus | 전체 프로세스 관리, 작업 분배, 최종 의사결정 | 전 Phase |
| **Market Researcher** | Sonnet | 외부 스킬/플러그인 탐색, 평판 팩트체크 | Phase 1 |
| **Comparison Analyst** | Opus | 상세 비교 분석, 개선사항 도출 | Phase 2 |
| **Flow Guardian** | Opus | 스킬 전체 구조 파악, 변경 필요성 + 안전성 판정, 설계 의도 수호 | Phase 3 + 5 |
| **Implementer** | Sonnet | 승인된 개선사항 실제 적용 | Phase 4 |
| **Reviewer** | Opus | 적용 후 정합성 라운드별 검토 | Phase 5 |

각 에이전트의 상세 역할, 권한 경계, 프롬프트 템플릿은 `references/agent-roles.md` 참조.

## Phase 흐름

```
Phase 0: 준비          ──→ Orchestrator
Phase 1: 리서치        ──→ Market Researcher × N (테마별)
    ✋ 사용자 승인 (후보 리스트)
Phase 2: 분석          ──→ Comparison Analyst
    ✋ 사용자 승인 (TOP N 개선사항)
Phase 3: 사전 검증     ──→ Flow Guardian
    ✋ 사용자 승인 (구현 계획)
Phase 4: 구현          ──→ Implementer (개선사항별)
Phase 5: 리뷰          ──→ Reviewer (라운드별)
    ↩ 이슈 발견 시 → Flow Guardian 판정 ("수정 필요한가?")
       🚫 불필요 → 기각  /  ✅ 필요 → Implementer 재수정 → Flow Guardian 재검증
Phase 6: 마무리        ──→ Orchestrator
```

## Phase 0: 준비

**담당**: Orchestrator (직접 수행)
**목적**: 대상 스킬 파악, 백업, 목표 설정

### 수행 절차

1. **대상 스킬 식별**
   - 사용자가 지정한 스킬 경로 확인
   - SKILL.md 읽어서 현재 버전, 구조 파악
   - 레퍼런스 파일 목록 확인

2. **백업 생성**
   - `~/.claude/skills-archive/{skill-name}-v{N}/` 에 전체 복사
   - 백업 경로를 기록

3. **목표 설정**
   - 사용자에게 개선 테마/방향 확인
   - 예: "QC 강화", "에이전트 역할 보강", "문서 체계 개선" 등
   - 테마가 없으면 "전반적 개선" — Market Researcher가 자율 탐색

4. **작업 계획 수립**
   - 리서치 대상 키워드/테마 결정
   - Market Researcher에게 전달할 브리핑 준비

### 산출물
- 백업 완료 확인
- 리서치 브리핑 (테마, 키워드, 탐색 범위)

---

## Phase 1: 리서치

**담당**: Market Researcher (서브에이전트)
**목적**: 외부 스킬/플러그인 탐색, 후보 리스트 작성

### Market Researcher 브리핑 템플릿

```
## 리서치 미션
대상 스킬: {스킬명} v{버전}
테마: {개선 테마}
탐색 키워드: {키워드 목록}

## 수행 사항
1. GitHub, npm, 커뮤니티에서 관련 스킬/플러그인 탐색
2. 각 후보에 대해:
   - 이름, URL, Stars/Downloads
   - 한줄 설명
   - 핵심 차별점 (왜 인기 있는지)
3. 평판 팩트체크:
   - Stars 수 vs 실제 코드 품질 (코드를 직접 읽어서 판단)
   - 최근 업데이트 빈도
   - 이슈/PR 활동성
4. 분석 대상 추천 (TOP 3~5)

## 보고 형식
| 이름 | Stars | 핵심 차별점 | 코드 품질 | 추천 여부 |
```

### 팩트체크 규칙
- Stars가 높아도 코드가 단순 래핑이면 "평판 부풀림" 판정
- Stars가 낮아도 코드 품질이 높으면 "숨은 보석" 판정
- README만 화려하고 코드가 빈약하면 "마케팅 우위" 판정

### 사용자 승인 게이트 ✋
리서치 보고서 제출 → 사용자가 분석 대상 확정

---

## Phase 2: 분석

**담당**: Comparison Analyst (서브에이전트)
**목적**: 확정된 후보와 대상 스킬을 상세 비교, TOP N 개선사항 도출

### Comparison Analyst 브리핑 템플릿

```
## 분석 미션
대상 스킬: {스킬명} v{버전} (전체 코드 첨부)
비교 대상: {후보 스킬 목록} (각 코드 첨부)

## 4대 평가 기준 (모든 개선 후보에 적용)
1. ⭐ Stars 받은 이유: 이 기능이 왜 인기 있는가? 실질적 가치인가?
2. 🔍 우리에게 없는 것: 대상 스킬에 없는 것 중 진짜 가치 있는 것은?
3. 👤 사용자 복잡도: 추가하면 사용자(비개발자) 입장에서 복잡해지는가?
4. 🔧 내부 흡수 가능성: 사용자 노출 없이 내부 로직으로 숨길 수 있는가?

## 보고 형식
각 개선 후보마다:
- 개선 내용 (한줄)
- 4대 기준 평가 결과
- 대상 파일 및 변경 범위
- 우선순위: 필수 / 권장 / 보조
- 예상 라인 증가량

최종: TOP N 개선사항 (우선순위별 정렬)
```

### 분석 규칙
- **"없다"가 곧 "필요하다"가 아니다** — 없는 이유를 먼저 분석
- **사용자 복잡도 증가 > 기능 추가** — 복잡해지면 아무리 좋아도 보류
- **내부 흡수 가능 > 사용자 노출** — 사용자 모르게 품질이 올라가는 것이 최선
- **한 번에 5개 이하** — 과도한 변경은 스킬을 불안정하게 만든다

### 사용자 승인 게이트 ✋
TOP N 개선사항 제출 → 사용자가 적용 대상 확정

---

## Phase 3: 사전 검증

**담당**: Flow Guardian (서브에이전트)
**목적**: 확정된 개선사항이 기존 스킬 흐름을 깨뜨리지 않는지 사전 검증

### Flow Guardian 브리핑 템플릿

```
## 검증 미션
대상 스킬: {스킬명} v{버전} (전체 코드 첨부)
적용 예정 개선사항: {목록}

## 검증 항목 (각 개선사항마다)
1. 파급 효과 분석
   - 수정 대상 파일 식별
   - 해당 파일을 참조하는 다른 파일 식별
   - 교차 참조가 깨지는 곳이 있는가?

2. 흐름 안전성
   - 기존 Phase 흐름에 영향이 있는가?
   - 에이전트 역할 경계가 변경되는가?
   - 기존 사용자 승인 게이트가 변경되는가?

3. 일관성
   - 동일 개념이 여러 파일에 다른 이름/형태로 등장하지 않는가?
   - 템플릿과 실제 사용처가 일치하는가?

## 판정
각 개선사항에 대해:
- ✅ 안전 — 그대로 진행
- ⚠️ 조건부 — {조건} 충족 시 진행
- ❌ 위험 — 진행 불가, {사유}

## 구현 계획
안전/조건부 판정을 받은 항목에 대해:
- 파일별 수정 순서
- 각 수정의 구체적 내용
- 의존 관계 (A를 먼저 수정해야 B가 가능)
```

### Flow Guardian 핵심 원칙
- **"왜 이렇게 되어있는지" 분석 우선** — 현재 구조에는 이유가 있다. 변경 전에 그 이유를 파악
- **백업과 비교** — v{N-1} 백업을 참조하여 의도적 설계와 누락을 구분
- **보수적 판단** — 확실하지 않으면 "위험" 판정. 안전한 것만 통과

### 사용자 승인 게이트 ✋
구현 계획 제출 → 사용자가 진행 여부 확정

---

## Phase 4: 구현

**담당**: Implementer (서브에이전트)
**목적**: 승인된 구현 계획에 따라 실제 스킬 파일 수정

### Implementer 브리핑 템플릿

```
## 구현 미션
대상 스킬: {스킬명} (경로: {path})
적용할 개선사항: {번호}. {내용}

## 구현 계획 (Flow Guardian 승인)
- 수정 파일: {파일 경로}
- 수정 내용: {구체적 변경 사항}
- 수정 위치: {섹션/라인 범위}

## 규칙
- 승인된 계획대로만 수정한다
- 추가 "개선"을 자의적으로 하지 않는다
- 기존 포맷, 들여쓰기, 스타일을 따른다
- 변경 전후를 명확히 보고한다

## 보고 형식
- 수정 파일: {경로}
- 변경 내용: {before → after 요약}
- 추가된 라인 수: {N}
```

### Implementer 권한 경계
| 허용 | 금지 |
|------|------|
| 지정된 파일 읽기/수정 | 계획에 없는 파일 수정 |
| 섹션 추가/수정 | 기존 섹션 삭제 |
| 내용 추가 | 구조 변경 (파일 분리/통합) |

### 개선사항별 순차 실행
- 개선사항 1 구현 → 완료 보고
- 개선사항 2 구현 → 완료 보고
- ...
- 전체 완료 → Phase 5로 전달

---

## Phase 5: 리뷰

**담당**: Reviewer (서브에이전트)
**목적**: 구현 완료된 스킬의 정합성을 라운드별로 검토

### Reviewer 브리핑 템플릿

```
## 리뷰 미션
대상 스킬: {스킬명} v{새 버전} (경로: {path})
이전 버전: v{이전 버전} (백업: {backup path})
적용된 개선사항: {목록}

## 리뷰 방법론

### 라운드별 검토
파일 하나씩 순회하며 검토. 각 파일에 대해:
1. 해당 파일의 목적과 역할 이해
2. v{N-1} 백업과 비교하여 변경점 확인
3. 변경점이 다른 파일과의 교차 참조에 영향을 주는지 확인
4. 이슈 발견 시 분류

### "왜 없는지 먼저 분석" 원칙
빠진 것을 발견했을 때:
1. 이전 버전(v{N-1})에도 없었는가? → 의도적 설계일 수 있음
2. 이 파일의 역할상 필요한 내용인가? → 다른 파일의 책임일 수 있음
3. 해당 섹션/파일의 목적을 고려할 때 있어야 하는가?
→ 3가지 모두 "있어야 한다"일 때만 이슈로 보고

### 이슈 분류
- 🔴 필수 수정: 정합성 깨짐, 교차 참조 오류, 논리적 모순
- 🟡 PASS with Notes: 개선 여지는 있지만 기능적 문제 없음
- 🟢 양호: 문제 없음

## 보고 형식
라운드 {N}: {파일명}
- 이슈 {번호}: {설명}
  - 위치: {파일:라인}
  - 분류: 🔴/🟡/🟢
  - 근거: {왜 이슈인지}
  - 원인 분석: {왜 이렇게 되었는지}
  - 수정 제안: {어떻게 고쳐야 하는지}
```

### 리뷰 → 재수정 루프
```
Reviewer 이슈 보고 → Orchestrator 판단 → 사용자 승인 ✋
→ Implementer 재수정 → Reviewer 재검토
→ 전체 통과 시 Phase 6
```

### 역검증 (v3.0 교훈)
모든 라운드 완료 후, 이전 수정사항이 불필요했을 가능성을 역으로 검증:
- 각 수정이 진짜 필요했는가?
- v{N-1}에서 의도적이었던 것을 잘못 "수정"하지 않았는가?
- 수정으로 인해 새로운 불일치가 생기지 않았는가?

## Phase 6: 마무리

**담당**: Orchestrator (직접 수행)
**목적**: 버전 확정, 기록, 정리

### 수행 절차

1. **버전 번호 갱신**
   - SKILL.md의 version 필드 업데이트
   - changelog에 이번 버전 내용 추가

2. **기록 업데이트**
   - MEMORY.md에 버전업 이력 기록
   - 백업 경로, 주요 변경사항 기록

3. **최종 보고**
   - 사용자에게 변경 요약 전달:
     - 적용된 개선사항 목록
     - 파일별 변경 요약
     - 리뷰 결과 (이슈 및 해결 내역)
     - 백업 위치
