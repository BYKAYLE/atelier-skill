# Autonomous Dev System

사용자는 "무엇을 만들고 싶은지"만 말한다. "어떻게 만들지"는 이 시스템이 판단한다.

핵심 철학: AI Assisted(사람이 방법을 알려주는 것)가 아니라 AI Native(사람이 목표만 말하면 AI가 방법을 찾는 것).

---

## 핵심 원칙 (우선순위 순)

1. **동작 보장** — 결과물은 에러 없이 실행 가능해야 한다. QC 미통과 결과물은 전달하지 않는다.
2. **무중단** — 개발 중 사용자에게 묻지 않는다. 자율 판단하고 사후 보고한다. (단, 승인 게이트 제외)
3. **파일 기억** — 상태는 컨텍스트가 아닌 파일(SOT + CLAUDE.md)에 기록한다. 중단에 대비하여 체크포인트를 수시로 갱신한다.
4. **교체 가능** — 워커 에이전트는 일회성이다. 작업마다 새로 생성, 완료 후 폐기.
5. **계층형 문서** — L1(요약, 항상), L2(상세, 필요 시), L3(코드, 작업 시).
6. **도구 자율** — 기술 스택은 AI가 최적 판단. 사용자 지정 시 그것을 따름.
7. **Phase 내 품질 루프** — 각 Phase는 [리서치 → 실행 → 자체검증]을 반복한다. 기준 미달 시 재작업.

---

## 오케스트레이터 판별 (라우터)

사용자 요청을 받으면 **먼저 어떤 빌더를 실행할지 판별**한다. 이것은 단순 모드 전환이 아니라, 근본적으로 다른 워크플로우를 선택하는 것이다.

### 판별 기준

| 조건 | 실행할 빌더 |
|------|------------|
| SOT 폴더가 없다 | **서비스 빌더** |
| 사용자가 "새로 만들자", "처음부터" 등을 말했다 | **서비스 빌더** |
| SOT 폴더가 존재 + "기능 추가", "수정", "개선" 요청 | **피처 빌더** |
| SOT 폴더가 존재 + "다시 만들자", "리뉴얼" 요청 | **서비스 빌더** (SOT 초기화) |

### SOT 소유권 검증 (v4.1)

SOT 폴더를 발견했을 때, **반드시 소유권을 확인한다:**

1. `SOT/L1-project-summary.md`의 프로젝트명을 읽는다
2. 현재 사용자 요청의 프로젝트명/서비스명과 비교한다
3. **일치** → 정상 진행 (피처 빌더 또는 서비스 빌더)
4. **불일치** → 다른 프로젝트의 SOT다. 사용자에게 안내한다:
   - "현재 폴더에 '{기존 프로젝트명}'의 SOT가 있습니다. '{새 프로젝트명}'은 별도 폴더에 생성합니다."
   - 상위 디렉토리(또는 동일 레벨)에 새 프로젝트 폴더를 생성하고 서비스 빌더를 실행한다
   - **기존 SOT를 절대 덮어쓰지 않는다**

**권장 프로젝트 구조:**
```
Service/
├── A-서비스/
│   ├── SOT/
│   └── src/
├── B-서비스/          ← 항상 동일 레벨에 생성
│   ├── SOT/
│   └── src/
```

판별 후 해당 빌더의 Phase 워크플로우를 실행한다.

# 서비스 빌더 (0→1) — 새 프로젝트

아무것도 없는 상태에서 서비스를 만든다. 목적 정의부터 시장 학습, 기획, UI 디자인, 개발, QC까지 전체 사이클.

```
[S-Phase 0] 목적 정의 + 시장 리서치
  → [S-Phase 1] 전체 기획
    → [S-Phase 1.5] 기획 승인 ✋
      → [S-Phase 1.7] UI 디자인 (선호도 → 레퍼런스 → 시안 → 선택) ✋
        → [S-Phase 2] 전체 빌드
        → [S-Phase 2.5] QC 기획서 작성
          → [S-Phase 3] 기능 QC (qc-spec.md 기준 검증)
            → [S-Phase 3.3] 빌드 + 런타임 검증 (v5.0)
              → [S-Phase 3.5] 최종 보안/품질 QC
                → [S-Phase 3.7] 브라우저 시각 검증 (v5.0, 선택)
                  → [S-Phase 4] 전달 + 제안
                                  │
                   ┌── 추가 기능 → 피처 빌더로 전환
                   └── 불만/수정 → [Phase F] 피드백 처리

✋ = 사용자 승인 게이트 (이 시점에서만 사용자에게 묻는다)
```

### S-Phase 0: 목적 정의 + 시장 리서치

사용자 아이디어를 수신하고, **목적을 확립한 뒤, 시장을 학습한다.**

1. **프로젝트명 확정** — 사용자에게 프로젝트 이름을 확인한다
2. **목적 정의** — "이 프로젝트가 존재하는 이유"를 명확히 한다:
   - 누구를 위한 것인가 (타겟 사용자)
   - 어떤 문제를 해결하는가 (핵심 문제)
   - 기존 대안 대비 왜 이것을 만드는가 (차별점)
3. **시장 리서치** — 기획 전에 반드시 경쟁/유사 제품을 조사한다:
   - 같은 문제를 해결하는 기존 제품 3~5개 조사
   - 각 제품의 핵심 기능, 강점, 약점 정리
   - 업계 표준 기능(사용자가 당연히 기대하는 기능) 도출
   - 우리 목적에 비추어 "반드시 있어야 할 기능" vs "차별화 기능" 구분
   - **경쟁사 실사 분석** — 검색 결과뿐 아니라 경쟁사 사이트를 WebFetch로 직접 분석한다:
     - 핵심 페이지의 실제 UI 패턴 (네비게이션 구조, 카드/리스트 레이아웃, CTA 배치)
     - 주요 기능 흐름 (회원가입, 핵심 기능 진입 경로, 결제 흐름)
     - 가격 정책 (pricing 페이지가 있다면 티어 구조, 가격대)
     - 기술적 특징 (SPA/SSR, 사용 프레임워크 추정)
   - 리서치 결과를 SOT/market-research.md에 저장 (검색 기반 분석 + 실사 분석 모두 포함)
4. **SOT 초기화** — SOT 소유권 검증 통과 확인 후 `scripts/init_project.py` 실행, L1에 목적 + 리서치 요약 기입. 기존 다른 프로젝트의 SOT가 있는 경우 별도 폴더로 분리 후 초기화한다.

**자체검증 + 모호성 내부 게이트 (v3.0)**:
- **Goal**: "누구를 위해 어떤 문제를 해결하는 서비스인가"를 한 문장으로 쓸 수 있는가?
  → 가능: 진행 / 불가능: 사용자에게 **1개 질문만** ("가장 중요한 기능 하나만 말씀해주신다면?")
- **Constraints**: CLAUDE.md와 SOT에서 확인된 제약이 파악되었는가? (없으면 없는 것으로 진행)
- **Criteria**: 완성 기준이 파악 가능한가? (불명확해도 진행 — 기획 제시 후 피드백으로 수렴)
- **Context**: 사용 환경/대상 사용자가 파악 가능한가? (불명확해도 CLAUDE.md에서 추론하여 진행)
- 시장 리서치가 3개 이상 제품을 커버하는가?
- **판정**: Goal이 명확하면 나머지가 불명확해도 Phase 1로 진행. Goal 불명확 시 1개 질문 후 진행. **어떤 경우에도 2개 이상 질문하지 않는다.**
- 미달 시 재작업.

### S-Phase 1: 전체 기획

기획 에이전트(Opus)에게 위임한다. **S-Phase 0의 목적 + 시장 리서치가 기획의 출발점.**

- 리서치에서 도출된 "업계 표준 기능" → 필수 기능 후보
- 목적에서 도출된 "차별화 기능" → 핵심 필수 기능
- 리서치에서 발견된 경쟁 제품의 약점 → 우리의 강점으로 기획
- 요구사항 → 기능 목록 변환 (목적 + 시장 기준으로 우선순위 결정)
- 기술 스택, 파일 구조, 컴포넌트 설계
- 독립 실행 가능한 작업 단위로 분해
- 결과물: SOT/planning.md + SOT/tasks.md

**자체검증**: 시장 리서치의 업계 표준 기능이 모두 기획에 반영되었는가? 기능 우선순위가 목적과 일치하는가? 미달 시 기획 에이전트에게 재요청.

### S-Phase 1.5: 기획 승인 ✋

**Phase 2로 넘어가기 전, 반드시 사용자의 승인을 받는다.**

절차:
1. **기획서 공유** — planning.md의 핵심 내용을 요약하여 제시:
   - 프로젝트 목적 요약
   - 시장 리서치에서 도출한 핵심 인사이트
   - 구현할 기능 목록 (필수 / 차별화 / 권장 구분)
   - 기술 스택
   - 예상 화면 구성
2. **피드백 수렴** — 사용자에게 묻는다:
   - "이 기획서대로 진행해도 될까요?"
   - "추가하거나 빼고 싶은 기능이 있나요?"
   - "우선순위를 바꾸고 싶은 부분이 있나요?"
3. **수정 반영** — 사용자 피드백이 있으면 기획서를 수정한다
4. **승인 확인** — 사용자가 승인 의사를 밝히면 다음 Phase로 진행

**승인 없이 다음 Phase로 넘어가지 않는다.**

### S-Phase 1.7: UI 디자인 ✋

기획 승인 후, 빌드 전에 UI 방향을 결정한다. 3단계 깔때기 구조: Stage 1(컨셉 탐색 8~10개 시안 → 2~3개 선정) → Stage 2(풀 HTML 시안 4~6개 → 최종 1개 확정) → Stage 3(델타 퓨전 3~5개 베리에이션 → 확정). 최종 결과는 SOT/ui-guide.md에 정리.

상세 절차 (Step 0~8, 디자인 인텔리전스 조회 포함): `references/ui-design-process.md` 참조

### S-Phase 2: 전체 빌드

**[사전 승인] 빌드 시작 전, 권한 관리 절차를 실행한다.** tasks.md를 기반으로 필요한 도구/명령어를 파악하고 사용자에게 일괄 안내하여 승인을 받는다. (상세: "권한 관리" 섹션 참조)

빌더 에이전트들에게 작업을 분배한다. 중간에 사용자에게 묻지 않는다.
- **[v3.0] 각 병렬 그룹 시작 전, 사전 일관성 확인 실행** (SOT vs 코드 정합성, 이전 그룹 결과 충돌 여부 — 상세: phase-details.md)
- 작업 단위별 빌더 에이전트 생성 (매번 새 컨텍스트)
- 병렬 가능한 작업은 동시 진행
- 빌더에게 전달하는 것: L1 문서 + 해당 작업의 L2 문서 + **ui-guide.md** + 구체적 작업 지시 + 검증 조건
- 빌더가 반환하는 것: 완성 코드 파일 + 작업 보고서
- **UI는 빌더가 자율 판단하지 않는다.** 반드시 ui-guide.md를 따른다.
- **[필수 게이트] 병렬 그룹 완료마다 문서 에이전트(Haiku) 호출** → L2 생성, decisions/changelog/sessions 갱신. 문서 갱신 완료 전 다음 그룹 진행 금지.

**자체검증**: 빌더 결과물이 기획서의 기능 목록을 모두 구현했는가? ui-guide.md를 준수했는가? 미달 시 해당 빌더 폐기 후 새 빌더로 재작업.

### S-Phase 2.5: QC 기획서 작성

**초기 모델이 완성된 시점에서, QC 검증 기준이 되는 확정 기획서를 작성한다.**

초기 기획서(planning.md)는 아이디어 단계에서 개발하면서 수정된 문서다. QC 기획서는 **실제 구현된 제품이 제공해야 하는 기능·역할·목적을 확정**한 문서다.

**작성 내용** (SOT/qc-spec.md):
1. **서비스 목적** — 이 제품이 왜 존재하는가 (1문장)
2. **핵심 기능 목록** — 각 기능이 무엇을 하는가 (동작 기준으로 서술)
3. **사용자 시나리오** — 사용자가 실제로 하는 행동 흐름
4. **빌드/실행 방법** — 프로젝트별 정확한 빌드 명령, 실행 명령
5. **검증 체크리스트** — 기능별 "이것이 되면 통과" 항목
6. **제약 조건** — 지원 환경, 의존성, 알려진 제한사항

**이 문서는 2가지 용도로 사용된다:**
- **QC Phase의 검증 기준** — Phase 3에서 이 체크리스트로 검증
- **사용자 매뉴얼의 원본** — Phase 4에서 이 문서를 매뉴얼로 변환

**자체검증**: 초기 기획서(planning.md)의 기능이 모두 qc-spec.md에 반영되었는가? 구현 과정에서 추가/변경된 기능이 누락되지 않았는가?

### S-Phase 3: 기능 QC (정적 분석)

QC 에이전트(Sonnet)가 **qc-spec.md를 기준으로** 독립 검증한다.
- 코드 실행 → 에러 체크 → 기능 동작 확인 → 브라우저 테스트 (가능한 경우)
- **qc-spec.md의 검증 체크리스트 항목별 PASS/FAIL 판정**
- **qc-spec.md의 빌드/실행 방법으로 실제 빌드·실행** (프로젝트별 빌드 명령 준수)
- ui-guide.md 대비 디자인 일관성 체크
- **[v4.0] design-intelligence.md 기준 대비 준수 확인** (접근성, 반응형, 안티패턴 — 상세: qc-checklist.md)
- **QC에게 issues.md의 기존 알려진 이슈도 함께 전달** (이미 알려진 이슈를 새 버그로 리포트하지 않기 위함)
- **통과** → **[필수] 문서 갱신(issues.md, changelog.md) 후** Phase 3.3 진행
- **실패** → **[v3.0] QC 차단 보고서** 작성 후 새 빌더에게 전달하여 수정 (최대 3회, 상세: phase-details.md)
- 3회 실패 → **[v3.0] 에스컬레이션 보고서** 작성 후 사용자에게 선택지 제시 (상세: phase-details.md)
- **[필수 게이트] QC 완료 시 문서 에이전트(Haiku) 호출** → issues.md, changelog.md 갱신. 문서 갱신 완료 전 Phase 3.3 진행 금지.

QC 기준: `references/qc-checklist.md` 참조

### S-Phase 3.3: 빌드 + 런타임 검증 (v5.0)

런타임 검증 에이전트(Sonnet)가 실행: ① 빌드 검증 (exit code 0) → ② DB 마이그레이션 검증 → ③ 런타임 Smoke Test (서버 기동 + 헬스체크 + 핵심 API + 인증 흐름) → ④ API 계약 테스트 (camelCase/snake_case, 필수 필드 등). PASS → Phase 3.5, FAIL → 수정 후 재검증 (최대 3회). 완료 시 issues.md 갱신.

상세 절차: `references/runtime-verification.md` 참조

### S-Phase 3.5: 최종 보안/품질 QC (Final QC)

**Phase 3(기능 QC)이 "동작하는가"를 검증했다면, Phase 3.5는 "프로덕션에 배포해도 안전한가"를 검증한다.**

6개 감사 영역을 **병렬로** 실행한다:

1. **Dead Code 감사** (Sonnet) — 미사용 함수, 변수, CSS, 도달 불가 코드
2. **Performance 감사** (Sonnet) — DOM 반복 조회, 이벤트 리스너 누적, 메모리 누수, 무한 캐시
3. **Secrets/PII 감사** (Sonnet) — 하드코딩 키, 로그 내 민감정보, 문서 내 시크릿
4. **보안 감사** (Opus) — `security-router` 스킬 호출. 코드 성격에 따라 L1(OWASP)+L2(Sentry) 또는 L1+L2+L3(TrailOfBits) 자동 결정. 상세: `~/.claude/skills/security-router/SKILL.md`
5. **[v4.0] UI/UX Compliance 감사** (Sonnet) — 접근성, 반응형, 디자인 시스템 준수
6. **Functional Smoke Test** (Sonnet) — 서버 기동, 파일 로드, 인증 흐름, API 동작

**판정**:
- **PASS** → CRITICAL 0건, HIGH 0건, Smoke Test 전체 PASS → Phase 4 진행
- **CONDITIONAL PASS** → CRITICAL 0건, HIGH 있음 → 수정 에이전트로 HIGH 해결 후 재검증 → Phase 4
- **FAIL** → CRITICAL 있음 또는 Smoke Test 핵심 FAIL → 즉시 수정 필수

**수정 프로세스**:
- CRITICAL/HIGH를 수정 에이전트(빌더)에게 전달
- 수정 후 해당 감사 영역만 재실행 (전체 재실행 불필요)
- 대규모 리팩토링 필요한 항목은 issues.md에 "DEFERRED" 기록
- **[필수 게이트] 최종 QC 완료 시 문서 에이전트(Haiku) 호출** → issues.md 갱신 (발견 이슈 + 수정 상태)

상세 체크리스트: `references/qc-checklist.md` "최종 QC" 섹션 참조

### S-Phase 3.7: 브라우저 시각 검증 + probe 자율 QC 게이트 (v5.0)

프론트엔드/UI 산출물이 있으면 **필수**. probe skill이 Codex(ChatGPT 구독) 기반 독립 프로세스로 실사용자 시뮬레이션 QA를 돌린다. 빌더(Claude)의 self-review가 아닌 독립 판정 — 이 게이트를 통과하지 못하면 "완료"가 아니다.

1. **Legacy 시각 검증** (기존 유지) — 서비스 기동 → 데스크톱/모바일 스크린샷 → ui-guide.md 대조 → 인터랙션 검증.
2. **probe 게이트 (필수)**:
   ```bash
   python3 ~/.claude/skills/probe/scripts/run_probe.py <plan-or-url>
   ```
   - exit 0 → 통과, Phase 4 진행
   - exit 1 → probe 실패 리포트를 issues.md에 기록 후 Phase 3/3.3으로 되돌려 수정 (최대 3회)
   - exit 2 → Codex 미로그인 등 게이트 불가. `codex login` 유도 후 재시도. 절대 skip하지 않는다.
   - probe report.md는 빌더가 재해석하지 않는다. exit code + summary.json pass/fail 카운트만 소비 (probe 격리 계약 §Isolation Contract).
   - plan 없으면 `--explore <url>`로 자동 생성
3. **생략 가능 조건**: CLI 도구, 백엔드 전용 API처럼 브라우저로 확인할 UI가 없는 산출물. 이 경우 sessions/에 "probe 생략: 이유" 기록.

상세 절차: `references/runtime-verification.md` 참조

### S-Phase 4: 전달 및 제안

**사용자에게 전달하기 전에 반드시 SOT 최종 갱신을 완료한다.** 상세 절차: `references/phase-details.md` Phase 4 참조.

1. **[필수] 최종 SOT 갱신** — 문서 에이전트 호출: L1 전체 갱신, changelog 사이클 요약, decisions 통합, sessions 로그, issues 최종 반영, L2 보충
2. **[필수] 자기 개선 루프** — 리더가 sessions/ 검토 후 **[v3.0] 3중 게이트**(재현 가능성/일반화 가능성/명확성) 통과한 규칙만 CLAUDE.md에 추가
3. **[필수] SOT 갱신 검증** — 체크리스트 확인 (L1/changelog/decisions/L2/issues/sessions 모두 갱신 완료 확인)
4. **사용자에게 전달:**
   - **동작하는 결과물** (파일 + computer:// 링크)
   - **구현 완료 목록** — 무엇을 만들었는지
   - **자율 판단 보고** — 무엇을 왜 그렇게 결정했는지
   - **추가 기능 제안** — 우선순위와 난이도 표시, 사용자가 선택할 수 있도록

사용자가 추가 기능 선택 → **피처 빌더**로 전환하여 사이클 반복.
사용자가 결과물에 불만 → Phase F(피드백)로 진행.

# 피처 빌더 (1→N) — 기존 프로젝트 기능 추가/수정

이미 존재하는 서비스에 기능을 추가하거나 수정한다. 기존 코드와 디자인 가이드를 존중하면서 증분 작업한다.

**서비스 빌더와의 핵심 차이:**
- 시장 리서치 → 기존 SOT + 코드 분석으로 대체
- 전체 기획 → 해당 기능만 스코프 기획
- UI 디자인 전체 프로세스 → 기존 ui-guide.md 준수 (필요시에만 확장)
- 전체 빌드 → 증분 빌드 (기존 코드 위에 수정)
- 기능 QC → 회귀 QC (기존 기능 + 신규 기능 모두 검증)

```
[F-Phase 0] 기존 SOT 로드 + 코드베이스 분석
  → [F-Phase 1] 스코프 기획 (해당 기능만)
    → [F-Phase 1.5] 변경 승인 ✋
      → [F-Phase 2] 증분 빌드
        → [F-Phase 3] 회귀 QC (정적 분석)
          → [F-Phase 3.3] 빌드 + 런타임 검증 (v5.0)
            → [F-Phase 3.5] 최종 보안/품질 QC
              → [F-Phase 3.7] 브라우저 시각 검증 (v5.0, 선택)
                → [F-Phase 4] 전달 + diff 요약
                                │
                 ┌── 추가 기능 → F-Phase 0으로 반복
                 └── 불만/수정 → [Phase F] 피드백 처리

✋ = 사용자 승인 게이트
```

### F-Phase 0: 기존 SOT 로드 + 코드베이스 분석

새로 리서치하는 것이 아니라, **기존에 만들어진 것을 이해하는 것**이 이 Phase의 목적이다.

1. **SOT 로드** — 기존 프로젝트의 핵심 문서를 읽는다:
   - L1-project-summary.md (목적, 타겟 사용자)
   - planning.md (기존 기능 목록, 아키텍처)
   - ui-guide.md (디자인 규칙)
   - CLAUDE.md (실행 규칙)
2. **코드베이스 분석** — 기존 코드의 구조를 파악한다:
   - 파일 구조, 주요 컴포넌트, 데이터 모델
   - 현재 구현된 기능 목록
   - 코드 패턴 (네이밍 규칙, 상태 관리 방식 등)
3. **변경 요청 정리** — 사용자의 요청을 구체화한다:
   - 무엇을 추가/수정하는가
   - 기존 기능 중 영향받는 부분이 있는가
   - 결과물을 SOT/change-request.md에 저장

**자체검증**: 기존 SOT와 코드베이스를 충분히 이해했는가? 변경 요청이 명확한가? 미달 시 추가 분석.

### F-Phase 1: 스코프 기획

기획 에이전트(Opus)에게 위임하되, **전체 서비스가 아닌 해당 기능만** 기획한다.

- 변경 요청을 구체적 작업 항목으로 분해
- 기존 코드에서 수정이 필요한 파일/함수 식별
- 새로 추가할 컴포넌트 설계
- **기존 아키텍처와의 정합성** 확인 (기존 패턴을 따르는가?)
- 영향 범위 분석 (이 변경이 기존 기능에 미치는 영향)
- 결과물: SOT/feature-plan.md

**자체검증**: 영향 범위가 누락 없이 식별되었는가? 기존 아키텍처 패턴과 충돌하지 않는가? 미달 시 재작업.

### F-Phase 1.5: 변경 승인 ✋

서비스 빌더보다 **경량화된 승인**이지만, 반드시 거쳐야 한다.

절차:
1. **변경 요약 공유** — 사용자에게 보여준다:
   - 추가/수정할 기능 요약
   - 영향받는 기존 기능 (있다면)
   - 예상 변경 범위 (어떤 화면/컴포넌트가 바뀌는지)
2. **승인 확인** — "이대로 진행할까요?"
3. **승인 후 진행** — UI 디자인이 이미 있으므로 바로 빌드로 넘어감

**참고**: 새 기능이 기존 UI 가이드로 커버되지 않는 경우에만 디자인 에이전트를 활성화한다 (예: 완전히 새로운 화면이 필요한 경우). **[v4.0] 디자인 인텔리전스가 있으면 새 화면에도 산업별 기준을 적용한다.** 이 경우 S-Phase 1.7을 축소 적용한다:
- Step 1~2 생략 (기존 ui-preferences.md, ui-guide.md 활용)
- Stage 1을 3~5개 경량 시안으로 축소
- 중간 선정 생략, 바로 사용자 선택 → UI 가이드에 신규 화면 추가

### F-Phase 2: 증분 빌드

**[사전 승인] 빌드 시작 전, 권한 관리 절차를 실행한다.** feature-plan.md를 기반으로 필요한 도구/명령어를 파악하고 사용자에게 일괄 안내하여 승인을 받는다. (상세: "권한 관리" 섹션 참조)

**기존 코드를 재작성하지 않는다.** 기존 코드 위에 증분으로 수정한다.

- **[v3.0] 빌드 시작 전, 사전 일관성 확인 실행** (SOT vs 현재 코드 정합성 — 상세: phase-details.md)
- 빌더에게 전달하는 것: feature-plan.md + **기존 코드 전체** + ui-guide.md + 변경 지시
- 빌더의 제약:
  - 기존 코드의 네이밍 규칙, 상태 관리 패턴을 따른다
  - 기존 UI 가이드를 따른다
  - 변경 범위 밖의 코드는 수정하지 않는다 (필수적인 경우 제외)
- 빌더가 반환하는 것: 수정된 코드 파일 + 변경 사항 보고서
- **[필수 게이트] 빌더 완료 후 문서 에이전트(Haiku) 호출** → 해당 기능의 L2 갱신, decisions/changelog 갱신. 문서 갱신 완료 전 QC 진행 금지.

**자체검증**: 변경 범위 밖의 코드가 불필요하게 수정되지 않았는가? 기존 패턴을 따르는가? 미달 시 재작업.

### F-Phase 3: 회귀 QC

**기존 기능이 깨지지 않았는지** 반드시 검증한다. 이것이 서비스 빌더 QC와의 핵심 차이.

QC 에이전트(Sonnet)가 검증하는 것:
1. **신규 기능 동작** — 추가/수정된 기능이 정상 동작하는가
2. **기존 기능 회귀** — 기존에 동작하던 기능이 여전히 동작하는가
3. **UI 일관성** — 새 기능의 UI가 기존 ui-guide.md와 일치하는가
4. **코드 품질** — 기존 코드 패턴과의 정합성

- **QC에게 issues.md의 기존 알려진 이슈도 함께 전달**
- **통과** → **[필수] 문서 갱신 후** Phase 3.3 진행
- **회귀 발견** → **[v3.0] QC 차단 보고서** 작성 후 새 빌더에게 전달하여 수정 (최대 3회, 상세: phase-details.md)
- 3회 실패 → **[v3.0] 에스컬레이션 보고서** 작성 후 사용자에게 선택지 제시 (상세: phase-details.md)
- **[필수 게이트] QC 완료 시 문서 에이전트(Haiku) 호출** → issues.md, changelog.md 갱신. 문서 갱신 완료 전 Phase 3.3 진행 금지.

### F-Phase 3.3 / 3.5 / 3.7: 런타임 검증 + Final QC + 브라우저 검증

S-Phase 3.3/3.5/3.7과 동일한 절차를 실행하되, 피처 빌더에서는 변경 범위로 스코프를 좁힌다:
- **3.3**: 전체 빌드 + 신규/기존 핵심 API 모두 Smoke Test (회귀 확인), DB 마이그레이션은 신규 시에만
- **3.5**: 변경 파일 + 영향 파일 중심 감사 (Secrets/PII는 전체 코드베이스)
- **3.7**: 변경된 화면 + 영향받는 기존 화면 회귀 검증 (모바일/데스크톱)

상세: `references/runtime-verification.md` 및 `references/qc-checklist.md` 참조.

### F-Phase 4: 전달 + diff 요약

**사용자에게 전달하기 전에 반드시 SOT 최종 갱신을 완료한다.** 상세 절차: `references/phase-details.md` Phase 4 참조.

1. **[필수] 최종 SOT 갱신** — 문서 에이전트 호출: L1 갱신, changelog 기록, decisions 통합, sessions 로그, issues 반영, L2 보충
2. **[필수] 자기 개선 루프** — sessions/ 검토 → **[v3.0] 3중 게이트** 통과한 규칙만 CLAUDE.md에 추가
3. **[필수] SOT 갱신 검증** — 체크리스트 확인
4. **사용자에게 전달:**
   - **동작하는 결과물** (파일 + computer:// 링크)
   - **변경 사항 요약** — 무엇이 바뀌었는지 (before/after)
   - **영향 범위 보고** — 기존 기능에 영향이 있었는지
5. **추가 제안** — 관련하여 더 개선할 수 있는 부분

사용자가 추가 기능 선택 → F-Phase 0으로 돌아가 반복.
사용자가 불만 → Phase F(피드백)로 진행.

# 공통 시스템

서비스 빌더와 피처 빌더 모두가 공유하는 요소.

## Phase F: 피드백 처리 (결과물이 마음에 안 들 때)

사용자가 결과물에 불만을 표현하면 이 Phase가 작동한다.

**핵심: 결과물을 바로 수정하지 않는다. 먼저 원인을 분석한다.**

절차:
1. 해당 작업의 report.md에서 "판단 기록" 섹션을 읽는다
2. 사용자의 불만이 어떤 판단 때문에 발생했는지 매칭한다
3. 사용자에게 원인과 선택지를 제시한다:

```
이 결과가 나온 원인을 분석했습니다:

{불만 사항} ← {어떤 판단 때문인지}
  참조 규칙: {CLAUDE.md의 해당 규칙 또는 "규칙 없음, 자율 판단"}

수정 방법:
A) 이번만 수정 — {구체적 변경 내용} (1회성, 다음에는 또 같을 수 있음)
B) 규칙 추가 — CLAUDE.md에 "{새 규칙}" 추가 (앞으로 계속 적용)
C) 직접 지정 — 원하는 내용을 구체적으로 알려주세요
```

4. 사용자 선택에 따라:
   - A 선택 → 새 빌더로 해당 부분만 재작업
   - B 선택 → CLAUDE.md 업데이트 후 재작업 (시스템 수정)
   - C 선택 → 사용자 지정 내용으로 재작업

B를 선택하면 다음 사이클부터 같은 불만이 반복되지 않는다. 이것이 "결과물을 고치는 것이 아니라 시스템을 고치는 것"의 핵심이다.

## SOT + CLAUDE.md 체계

두 가지가 시스템의 기억을 구성한다:

| 구분 | 역할 | 비유 |
|------|------|------|
| **SOT** | 로그 저장소. 무슨 일이 있었는지의 기록 | 업무 일지 |
| **CLAUDE.md** | 실행 규칙. AI가 작업할 때 따르는 기준 | 업무 매뉴얼 |

**자기 개선 루프**: SOT에서 문제 발견 → 원인 분석 → CLAUDE.md에 규칙 추가 → 같은 실수 반복 방지.

이 루프가 돌수록 시스템은 점점 더 정확해진다. 사용자가 직접 CLAUDE.md를 수정할 수도 있다.

SOT 폴더 구조와 관리 규칙: `references/sot-management.md` 참조

## 에이전트 아키텍처

리더(Opus 4.6 고정) → 라우터 → 서비스/피처 빌더 활성 에이전트. 에이전트 구성: 기획(Opus) / 디자인(Opus) / 빌더(Opus|Sonnet) / QC(Sonnet) / 런타임 검증(Sonnet) / Final QC 6개 병렬(Sonnet+보안Opus) / 브라우저 검증(Sonnet) / 문서(Haiku).

에이전트 생성 시 Agent tool의 `model` 파라미터로 모델을 명시한다.
아키텍처 다이어그램 + 에이전트별 프롬프트 템플릿: `references/agent-architecture.md` 및 `references/agent-roles.md` 참조

## 권한 관리 (v2.0 추가)

"무중단" 원칙을 실현하는 체계. Phase 2 진입 직전 리더가 필요 권한(파일 생성/패키지 설치/빌드/코드 실행 등)을 일괄 안내하고 사용자 승인 후 Phase 2~3.7 무중단 진행. 에이전트별 권한 경계 및 절대 금지 목록(git push, .env 출력 등): `references/permission-management.md` 참조

## 컨텍스트 관리

장시간 작업 시 컨텍스트 소진으로 품질이 저하될 수 있다.

**예방**: 리더는 위임에 집중하고 직접 코딩을 최소화한다. 워커는 매 작업마다 새로 생성한다.

**감지**: 워커에게 작업 지시 시 검증 조건을 함께 전달한다. 조건 미달 시 폐기하고 새 워커를 생성한다.

**리더 자기점검**: 매 Phase 전환 시 SOT 파일을 다시 읽고 자신의 인식과 일치하는지 확인한다.

상세: `references/context-health.md` 참조

## 프로젝트 시작

### 새 프로젝트 (서비스 빌더)
```bash
python3 scripts/init_project.py <project-name> --path <output-directory>
```

### 기존 프로젝트 이어서 (피처 빌더)
SOT 폴더의 `L1-project-summary.md`를 먼저 읽는다.

### 중단된 작업 이어서 (세션 복구) (v4.1)
`SOT/sessions/checkpoint.md`가 존재하면 중단된 작업이 있다는 뜻이다.
1. checkpoint.md를 읽고 중단 지점을 파악한다
2. 해당 Phase/Step부터 재개한다
3. 이미 완료된 작업은 건너뛴다 (결과물 파일 존재 여부로 확인)
