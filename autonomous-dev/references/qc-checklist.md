# QC 검증 체크리스트

## QC 원칙

QC 에이전트는 빌더와 완전히 독립적이다. 빌더의 보고서를 참고하되, 자체적으로 모든 항목을 검증한다.
"빌더가 통과했다고 보고했으므로 통과" 같은 판단은 하지 않는다.

## 필수 검증 항목

### 1. 실행 가능성 (Critical)
- [ ] 코드가 에러 없이 실행되는가
- [ ] 필요한 의존성이 모두 포함되어 있는가 (CDN 링크, import 등)
- [ ] 파일 경로 참조가 올바른가

**검증 방법**: 실제로 코드를 실행한다.
- Python → `python3 파일명.py` 실행
- Node → `node 파일명.js` 실행
- React/Next.js → `npm run build` exit code 0 확인
- Docker → `docker compose up -d` 후 헬스체크 (curl)

### 2. 기능 동작 (Critical)
- [ ] 각 기능이 의도대로 동작하는가
- [ ] 버튼, 링크, 폼 등 인터랙티브 요소가 반응하는가
- [ ] 데이터 표시가 올바른가

**검증 방법**: 작업 지시서의 검증 조건을 하나씩 실행한다.

### 3. 에러 부재 (Critical)
- [ ] 콘솔에 JavaScript 에러가 없는가
- [ ] Python traceback이 없는가
- [ ] 경고(warning)는 허용하되 기록한다

**검증 방법**: 실행 후 콘솔/터미널 출력을 확인한다.

### 4. UI/레이아웃 (Important, 해당 시)
- [ ] 레이아웃이 깨지지 않는가
- [ ] 텍스트가 잘리지 않는가
- [ ] 색상, 폰트가 의도대로 표시되는가

**검증 방법**: 코드 리뷰로 CSS/레이아웃 구조 확인. Lighthouse CLI로 자동 검증.

### 4.1 접근성 (Critical, v4.0)

웹/앱 프로젝트에서 반드시 검증한다. 접근성 미준수는 기능 미동작과 동급의 결함이다.

- [ ] **색상 대비**: 일반 텍스트 4.5:1 이상, 대형 텍스트(18px+ 또는 14px bold+) 3:1 이상
- [ ] **포커스 표시**: 모든 인터랙티브 요소(버튼, 링크, input)에 visible focus ring 존재
- [ ] **Alt 텍스트**: 의미 있는 이미지에 설명적 alt 속성 (장식용 이미지는 alt="" 또는 role="presentation")
- [ ] **ARIA 라벨**: 아이콘 전용 버튼에 aria-label 필수 (텍스트 없는 버튼)
- [ ] **키보드 내비게이션**: Tab 순서가 시각적 순서와 일치, 모든 기능이 키보드만으로 접근 가능
- [ ] **폼 라벨**: 모든 input/select/textarea에 `<label>` + `for` 속성 연결
- [ ] **에러 피드백**: 폼 에러 시 인라인 에러 메시지 표시 (색상만으로 구분하지 않음)
- [ ] **모션 감도**: `prefers-reduced-motion` 미디어 쿼리 지원 (패럴랙스, 자동 애니메이션에 적용)

**검증 방법**: axe-core 또는 Lighthouse 접근성 감사로 자동 검증. 코드 리뷰로 ARIA 속성 확인.

### 4.2 반응형 (Important, v4.0)

웹 프로젝트에서 반드시 검증한다.

- [ ] **Viewport 메타**: `width=device-width, initial-scale=1` 설정 (`maximum-scale=1` 사용 금지 — 확대 기능 차단)
- [ ] **최소 폰트**: 모바일 body 텍스트 16px 이상 (iOS 자동 확대 방지)
- [ ] **가로 스크롤 없음**: 모바일에서 수평 overflow 발생하지 않음
- [ ] **Z-index 관리**: 정의된 스케일 사용 (예: 10/20/30/50), 무작위 z-index 금지
- [ ] **줄 길이**: 본문 텍스트 65~75자 이내 (가독성)
- [ ] **줄 간격**: body line-height 1.5~1.75

**검증 방법**: 코드 리뷰로 반응형 breakpoint 및 미디어 쿼리 확인. Lighthouse 자동 검증.

### 4.3 터치/인터랙션 (Important, v4.0)

모바일 지원 프로젝트에서 검증한다.

- [ ] **터치 타겟**: 인터랙티브 요소 최소 44x44px (버튼, 링크, 체크박스 등)
- [ ] **Cursor-pointer**: 모든 클릭 가능한 요소에 cursor: pointer 적용
- [ ] **로딩 버튼**: 비동기 작업 중 버튼 비활성화 (이중 클릭 방지)
- [ ] **로딩 상태**: 비동기 로딩 시 스켈레톤 스크린 또는 스피너 표시
- [ ] **빈 상태**: 데이터가 없을 때 안내 메시지 표시 (빈 화면 금지)

**검증 방법**: 코드 리뷰로 터치 타겟 사이즈, cursor 속성, 로딩 상태 처리 확인.

### 4.4 디자인 시스템 준수 (Important, v4.0)

design-intelligence.md가 존재하는 프로젝트에서 검증한다.

- [ ] **추천 스타일 적용**: design-intelligence.md의 추천 스타일이 실제 구현에 반영되었는가
- [ ] **안티패턴 회피**: design-intelligence.md의 안티패턴에 해당하는 디자인이 없는가
- [ ] **색상 팔레트 준수**: 지정된 색상 팔레트가 일관되게 적용되었는가
- [ ] **폰트 페어링 준수**: 지정된 폰트 조합이 적용되었는가
- [ ] **ui-guide.md 일치**: 최종 UI 가이드와 실제 구현이 일치하는가

**검증 방법**: 코드 리뷰로 design-intelligence.md/ui-guide.md 토큰 값 대조 확인.

### 5. 코드 품질 (Nice-to-have)
- [ ] 불필요한 console.log나 디버그 코드가 없는가
- [ ] 주석이 적절한가
- [ ] 파일 구조가 기획서와 일치하는가

## 6단계 검증 체인 (v3.0)

QC 에이전트는 체크리스트 확인 전, 아래 6단계를 순서대로 실행한다. 각 단계의 실행 결과(명령어 출력)를 qc-result.md에 첨부한다.

| 단계 | 이름 | 실행 내용 | 통과 기준 |
|------|------|----------|----------|
| 1 | Build | `npm run build` 또는 해당 빌드 명령 | exit code 0, 에러 없음 |
| 2 | Lint | `npx eslint .` 또는 해당 린트 명령 (없으면 생략) | warning만 허용, error 0건 |
| 3 | Test | `npm test` 또는 해당 테스트 명령 (없으면 생략) | 전체 PASS |
| 4 | Security | `npm audit` 또는 의존성 보안 확인 (없으면 수동 점검) | critical/high 0건 |
| 5 | Diff | 기획서 기능 목록 vs 실제 구현 파일 비교 | 누락 기능 0건 |
| 6 | Report | 1~5단계 결과를 정리하여 증거 첨부 | 모든 증거 포함 |

**규칙:**
- 빌드/테스트 도구가 없는 프로젝트(순수 HTML/CSS/JS)는 해당 단계를 "N/A — 도구 없음"으로 기록하고 수동 확인으로 대체
- 각 단계에서 실패 시 해당 단계에서 중단하지 않는다 — 6단계까지 모두 실행 후 종합 판정

## 증거 언어 규칙 (v3.0)

QC 보고서에서 아래 표현은 **금지**한다. 증거 없는 판단은 판단이 아니다.

| 금지 표현 | 대체 규칙 |
|-----------|----------|
| "should work" / "동작할 것이다" | 실제 실행 결과를 첨부한다 |
| "probably fine" / "아마 괜찮다" | 확인한 근거를 명시한다 |
| "looks correct" / "맞아 보인다" | 어떤 입력으로 어떤 출력을 확인했는지 기록한다 |
| "no issues found" (근거 없이) | 실행 로그, 콘솔 출력, 스크린샷 중 하나를 첨부한다 |

**원칙**: QC 보고서의 모든 판정에는 **실행 증거**(명령어 출력, 에러 로그, 스크린샷 경로)가 반드시 동반되어야 한다.

## 판정 기준

### PASS
- Critical 항목 100% 통과
- Important 항목 80% 이상 통과
- Nice-to-have는 판정에 영향 없음 (개선사항으로 기록)

### FAIL
- Critical 항목 중 하나라도 실패
- Important 항목 50% 미만 통과

### PASS with Notes
- Critical 100% 통과
- Important 50~80% 통과
- 경미한 이슈가 있으나 동작에는 문제없음

## QC 결과 보고서 형식

```markdown
# QC 결과 — {기능명/작업명}

## 전체 판정: PASS / FAIL / PASS with Notes

## 검증 환경
- 실행 방법: {브라우저/Python/Node 등}
- 사용 도구: {bash, 브라우저 자동화 등}

## 항목별 결과

### Critical
| 항목 | 결과 | 근거 |
|------|------|------|
| 실행 가능성 | ✅/❌ | {에러 메시지 또는 "정상 실행"} |
| 기능 동작 | ✅/❌ | {구체적 확인 내용} |
| 에러 부재 | ✅/❌ | {콘솔 출력 내용} |

### Important
| 항목 | 결과 | 근거 |
|------|------|------|
| UI/레이아웃 | ✅/❌ | {확인 내용} |

### 개선사항
- {동작에는 문제없지만 개선하면 좋을 점}

## 실패 시 수정 방향
{실패한 항목에 대한 수정 방향 제안}
```

## 재작업 프로세스

QC 실패 시:
1. QC 보고서의 실패 사유와 수정 방향을 정리한다
2. 기존 빌더와 다른 새 빌더 에이전트를 생성한다
3. 새 빌더에게 전달: 기존 코드 + QC 실패 보고서 + 수정 지시
4. 새 빌더가 수정 후 다시 QC에 보낸다
5. 최대 3회 반복. 3회 실패 시 사용자에게 보고한다

3회 실패 시 보고 내용:
- 현재까지 동작하는 부분
- 해결하지 못한 문제와 원인 분석
- 사용자에게 판단을 요청하는 선택지 제시

# 런타임 검증 QC (Phase 3.3, v5.0)

## 목적

기능 QC(Phase 3)는 "코드를 읽었을 때 문제가 없는가"를 정적으로 검증한다. 런타임 검증은 **"실제로 빌드하고 실행했을 때 동작하는가"**를 검증한다.

## 실행 시점

- **서비스 빌더**: S-Phase 3 PASS → **S-Phase 3.3 (런타임 검증)** → S-Phase 3.5
- **피처 빌더**: F-Phase 3 PASS → **F-Phase 3.3 (런타임 검증)** → F-Phase 3.5

## 필수 검증 항목

### RT-1. 빌드 검증 (Critical)

프로젝트가 에러 없이 빌드되는가.

> **빌더 자체 검증(Phase 3)과의 관계**: 빌더가 이미 빌드를 실행했지만, RT-1은 독립 에이전트가 동일 검증을 재실행하여 빌더의 자체 판단을 확인한다. 의도적 중복이다.

- [ ] 프론트엔드 빌드 성공 (`npm run build` / `pnpm build`) — exit code 0
- [ ] 백엔드 모듈 임포트 성공 (`python -c "from app.main import app"` 등)
- [ ] TypeScript 타입 체크 통과 (`tsc --noEmit`) — 에러 0건
- [ ] Docker 빌드 성공 (`docker compose build`) — 모든 서비스 빌드 완료

**검증 방법**: 각 빌드 명령어를 실행하고 exit code와 출력을 기록한다.

### RT-2. DB 마이그레이션 (Critical, DB 프로젝트만)

DB 스키마가 코드의 모델 정의와 일치하는가.

- [ ] 마이그레이션 스크립트가 에러 없이 실행 가능한가
- [ ] 모델 정의와 마이그레이션 파일이 일관적인가
- [ ] 새 마이그레이션이 기존 데이터를 파괴하지 않는가 (ALTER/DROP 확인)

**검증 방법**: `alembic check`, `prisma validate`, `drizzle-kit check` 등. 도구 없으면 "N/A".

### RT-3. 런타임 Smoke Test (Critical)

서버를 실제로 기동하고 **기본 동작**을 빠르게 검증한다.

> **Audit 6 (Phase 3.5)과의 역할 분담**: RT-3는 "서버가 뜨고 기본 응답을 하는가?"만 확인하는 **빠른 산점 검사**다. 심층 기능 검증(정적 파일 로드, 보안 헤더, SRI, CRUD, 비정상 요청 등)은 Phase 3.5의 Audit 6이 담당한다. RT-3 PASS가 Audit 6의 전제 조건이다.

- [ ] **서버 기동**: 에러 없이 listening 상태에 도달하는가
- [ ] **헬스체크**: GET / 또는 /health → HTTP 200 응답
- [ ] **핵심 API 정상 요청**: 각 주요 엔드포인트에 정상 요청 → 기대 응답 코드
- [ ] **인증 흐름**: 회원가입 → 로그인 → 토큰 → 인증 API 호출 (인증 기능 있는 경우)
- [ ] **비정상 요청 처리**: 잘못된 요청 → 적절한 에러 응답 (400/401/404)
- [ ] **프론트엔드 페이지**: 각 라우트 HTTP 200 + 빈 페이지가 아닌지

**검증 방법**: curl 또는 HTTP 클라이언트로 실제 요청. Docker 사용 시 `docker compose up -d` 후 테스트.

### RT-4. API 계약 테스트 (Important)

프론트엔드가 기대하는 응답 형식과 백엔드 실제 응답이 일치하는가.

- [ ] **필드명 일치**: camelCase/snake_case 변환이 올바른가
- [ ] **필수 필드 존재**: 프론트엔드 타입 정의의 required 필드가 모두 응답에 포함되는가
- [ ] **페이지네이션 일관성**: page/pageSize/total 등의 형식이 모든 list 엔드포인트에서 일관적인가
- [ ] **에러 응답 형식**: 에러 시 프론트엔드가 파싱할 수 있는 형식인가

**검증 방법**: 실제 API 호출 → 프론트엔드 타입 정의와 대조.

## 판정 기준

### PASS
- RT-1 빌드 전체 성공
- RT-2 마이그레이션 이상 없음 (또는 N/A)
- RT-3 서버 기동 + 핵심 API 정상
- RT-4 필드명 불일치 0건

### FAIL
- RT-1 빌드 실패
- RT-3 서버 기동 실패 또는 핵심 API 실패
- RT-4에서 Critical 불일치 발견

# UI 자동 검증 (Phase 3.7, v5.2.3)

## 목적

코드가 올바르고 보안 감사를 통과해도, UI/UX 품질이 낮으면 사용자에게는 버그다. 이 검증은 코드 리뷰와 자동화 도구로 UI 품질을 확인한다.

## 실행 조건 (하나 이상 해당 시)

- 프로젝트에 프론트엔드(웹 UI)가 포함
- ui-guide.md가 존재
- 이전 QC에서 UI 관련 이슈 발견
- 신규 화면 추가 (피처 빌더)

## 검증 항목

### VT-1. 페이지 응답 검증 (Important)

- [ ] **모든 라우트 HTTP 200**: curl로 각 페이지 응답 코드 확인
- [ ] **빈 페이지 아님**: 응답 body size > 0
- [ ] **인증 라우트**: 미인증 시 리다이렉트 또는 로그인 페이지 표시

### VT-2. ui-guide.md 준수 (Important)

- [ ] **색상 토큰**: 코드에서 사용된 색상이 디자인 토큰과 일치하는가 (코드 리뷰)
- [ ] **타이포그래피**: 폰트 패밀리, 크기 체계가 가이드를 따르는가 (코드 리뷰)
- [ ] **레이아웃 구조**: CSS/컴포넌트 구조가 가이드와 일치하는가 (코드 리뷰)

### VT-3. 상태 처리 (Important)

- [ ] **로딩 상태**: 스켈레톤/스피너 컴포넌트가 존재하는가 (코드 리뷰)
- [ ] **빈 상태**: 데이터 없을 때 안내 메시지 컴포넌트가 존재하는가 (코드 리뷰)
- [ ] **에러 상태**: 에러 바운더리/에러 UI가 구현되었는가 (코드 리뷰)

### VT-4. Lighthouse 자동 감사 (Nice-to-have)

- [ ] **Performance**: Lighthouse CLI로 성능 점수 측정
- [ ] **Accessibility**: Lighthouse 접근성 자동 검사
- [ ] **Best Practices**: Lighthouse 모범 사례 점수 측정

**검증 방법**: `npx lighthouse URL --output=json --chrome-flags="--headless"` 또는 코드 리뷰.

## 판정 기준

- **PASS**: 모든 라우트 응답 정상 + 코드 리뷰 이슈 없음
- **ISSUES**: 이슈 발견 — 심각도에 따라 즉시 수정(CRITICAL/HIGH) 또는 DEFERRED(MEDIUM/LOW)

# 최종 QC (Final Security & Quality Audit)

## 목적

서비스 빌더(S-Phase 3) 또는 피처 빌더(F-Phase 3) QC가 "기능이 동작하는가"를 검증한다면, **최종 QC는 "프로덕션에 내보내도 안전한가"를 검증한다.** 이 단계는 Phase 3 통과 후, Phase 4 전달 전에 실행된다.

## 실행 시점

- **서비스 빌더**: S-Phase 3 PASS → S-Phase 3.3 → **S-Phase 3.5 (Final QC)** → S-Phase 4
- **피처 빌더**: F-Phase 3 PASS → F-Phase 3.3 → **F-Phase 3.5 (Final QC)** → F-Phase 4
- 기능 QC(Phase 3)를 통과한 코드에 대해서만 실행한다

## 감사 영역 (6개 병렬 에이전트)

### Audit 1: Dead Code & Unused Code (에이전트: Sonnet)

**목적**: 사용되지 않는 코드를 식별하여 코드베이스 경량화

검증 항목:
- [ ] 호출되지 않는 함수/메서드
- [ ] 사용되지 않는 변수, import, CSS 클래스
- [ ] 도달 불가능한 코드 경로 (unreachable code)
- [ ] 사용되지 않는 함수 파라미터
- [ ] 중복 정의된 상수/변수 (같은 역할의 2개 이상 정의)
- [ ] 주석 처리된 코드 블록 (삭제 대상)

**결과 분류**:
- REMOVE: 삭제해도 안전한 코드
- REVIEW: 의도적 보존인지 확인 필요
- DUPLICATE: 통합/제거 가능한 중복

### Audit 2: Performance & Efficiency (에이전트: Sonnet)

**목적**: 동작하지만 비효율적인 코드를 식별하여 성능 개선

검증 항목:
- [ ] DOM 반복 조회 (루프 내 getElementById/querySelector)
- [ ] 불필요한 리렌더링/리플로우 유발 패턴
- [ ] 이벤트 리스너 누적 (페이지 전환 시 미해제)
- [ ] 메모리 누수 패턴 (순환 참조, 미해제 타이머, 글로벌 배열 무한 증가)
- [ ] 비효율적 문자열 처리 (innerHTML vs textContent, DOM 기반 이스케이프)
- [ ] 불필요한 동기 I/O (서버측)
- [ ] N+1 쿼리 패턴 (DB 접근 시)
- [ ] 무한 성장 가능한 캐시/맵 (eviction 없음)

**심각도 분류**:
- CRITICAL: 사용자 체감 지연 또는 크래시 유발 — 즉시 수정
- HIGH: 장시간 사용 시 성능 저하 — 이번 사이클 내 수정
- MEDIUM: 코드 품질 개선 — 다음 사이클 권장

### Audit 3: Secrets & PII Exposure (에이전트: Sonnet)

**목적**: 코드/파일에 노출된 비밀 정보와 개인정보를 탐지

검증 항목:
- [ ] 하드코딩된 API 키, 비밀번호, 토큰 (소스코드 + 설정 파일)
- [ ] .env 파일이 .gitignore에 포함되었는가
- [ ] 로그에 비밀번호, 토큰, 개인정보가 출력되는가
- [ ] 에러 응답에 서버 내부 경로, 스택 트레이스가 노출되는가
- [ ] CLAUDE.md, README, 문서 파일에 실제 키/비밀번호가 기록되었는가
- [ ] 프론트엔드 코드에 서버 전용 시크릿이 번들되었는가
- [ ] console.log/console.error에 민감한 데이터가 포함되는가

**발견 시 즉시 조치**:
- 시크릿 발견 → 환경변수로 분리 + 기존 키 로테이션 권고
- PII 로깅 → 마스킹 처리 (email: u***@domain.com, 전화: ***-****-1234)
- 문서 내 시크릿 → 플레이스홀더로 교체 (`<your-api-key>`)

### Audit 4: Security Vulnerabilities (에이전트: security-router 위임)

**목적**: 외부 공격에 대한 방어력을 검증 (공격자 관점)

**방법**: Skill tool로 `security-router`를 호출한다. security-router가 코드 성격을 분석하여 적절한 보안 레이어를 자동 결정한다:
- **L1 (OWASP)**: OWASP Top 10 기반 취약점 검사 — 항상 실행
- **L2 (Sentry)**: 데이터 흐름 추적 기반 HIGH 신뢰도 취약점 탐지 — 항상 실행
- **L3 (TrailOfBits)**: 정적 분석(Semgrep) + 공급망 위험 + 안전하지 않은 기본값 — 고위험 코드만

**QC에서의 역할**: security-router의 통합 보고서를 그대로 Audit 4 결과로 사용한다.

**심각도 분류** (security-router 통합 결과 기준):
- CRITICAL: 원격 코드 실행(RCE), 인증 우회, 대량 데이터 유출 가능 — 즉시 수정 필수
- HIGH: XSS, CSRF, 권한 상승 — 이번 사이클 내 수정
- MEDIUM: 정보 노출, 설정 미비 — 이번 사이클 내 수정 권장
- LOW: 모범 사례 미준수 — 기록 후 다음 사이클

### Audit 5: UI/UX Compliance Audit (에이전트: Sonnet) (v4.0)

**목적**: 접근성, 반응형, 디자인 시스템 준수를 검증

검증 항목:
- [ ] 접근성 CRITICAL 항목 전체 (4.1 섹션의 8개 항목)
- [ ] 반응형 핵심 항목 (4.2 섹션의 6개 항목)
- [ ] 터치/인터랙션 (4.3 섹션의 5개 항목 — 모바일 지원 시)
- [ ] design-intelligence.md 기준 준수 (4.4 섹션 — 해당 시)
- [ ] ui-guide.md 일관성 (색상, 폰트, 레이아웃, 컴포넌트 스타일)
- [ ] SVG 아이콘 사용 (이모지 아이콘 금지)
- [ ] 에러 메시지 사용자 친화성 (기술 용어 금지, 행동 지시 포함)

**심각도 분류**:
- CRITICAL: 접근성 미준수 (색상 대비, 키보드 접근 불가, ARIA 누락)
- HIGH: 반응형 깨짐 (모바일에서 사용 불가), 디자인 시스템 불일치
- MEDIUM: 터치 타겟 미달, UX 개선 여지
- LOW: 스타일 미세 불일치, 모범 사례 미준수

### Audit 6: Functional Smoke Test (에이전트: Sonnet)

**목적**: 모든 구현된 기능의 엔드투엔드 동작을 **심층 검증**

> **RT-3 (Phase 3.3)과의 역할 분담**: RT-3가 서버 기동 + 기본 응답을 확인한 전제 위에서, Audit 6는 정적 파일, 보안 헤더, CRUD, 비정상 요청 등 **심층 기능**을 검증한다. RT-3에서 이미 확인된 서버 기동/헬스체크는 재확인만 하고, 중점은 아래 2~8번 항목이다.

검증 방법:
1. **서버 상태 확인** — RT-3 결과 참조, 서버 기동 상태 재확인
2. **정적 파일 로드** — 모든 HTML/CSS/JS/데이터 파일 HTTP 200 확인
3. **보안 헤더** — CSP, X-Content-Type-Options, X-Frame-Options 응답 확인
4. **SRI 검증** — CDN 스크립트에 integrity 해시 존재 확인
5. **인증 흐름** — 회원가입 → 로그인 → 토큰 발급 → 인증 필요 API 호출 → 로그아웃
6. **데이터 CRUD** — 생성 → 읽기 → 수정 → 삭제 (해당되는 경우)
7. **핵심 기능별 API 호출** — 각 주요 엔드포인트에 정상 요청 + 비정상 요청 모두 테스트
8. **프론트엔드 페이지** — 각 페이지/탭의 HTML 응답 확인 (SPA의 경우 라우트별)

**결과 형식**:
| 테스트 항목 | 상태 | 비고 |
|------------|------|------|
| 서버 기동 | PASS/FAIL | {에러 메시지} |
| CSS 로드 (N개) | PASS/FAIL | {실패 파일} |
| JS 로드 (N개) | PASS/FAIL | {실패 파일} |
| 인증 흐름 | PASS/FAIL | {실패 단계} |
| ... | ... | ... |

## 판정 기준

### PASS (프로덕션 배포 가능)
- CRITICAL 이슈 0건
- HIGH 이슈 0건
- Smoke Test 전체 PASS
- 시크릿/PII 노출 0건

### CONDITIONAL PASS (수정 후 배포)
- CRITICAL 0건
- HIGH 1건 이상 → 수정 후 재검증
- MEDIUM 이슈는 issues.md에 기록 후 배포 가능

### FAIL (배포 불가)
- CRITICAL 1건 이상
- Smoke Test 핵심 항목 FAIL
- 시크릿 노출 미해결

## 수정 프로세스

1. 감사 결과를 심각도별로 정렬한다
2. CRITICAL → HIGH → MEDIUM 순서로 수정 에이전트(빌더)에게 전달한다
3. 수정 후 해당 Audit만 재실행하여 검증한다 (전체 재실행 불필요)
4. 모든 CRITICAL/HIGH 해결 후 PASS 판정
5. 수정 불가 항목 (대규모 리팩토링 필요)은 issues.md에 "DEFERRED" 상태로 기록하고 사유를 명시한다
