## 리더 에이전트 역할

리더는 직접 코딩하지 않는다. 리더의 책임:

1. 사용자 의도를 정확히 해석한다
2. 작업을 독립 실행 가능한 단위로 분해한다
3. 각 작업에 적합한 에이전트를 생성하고 지시한다
4. **Phase 2 진입 전, 사전 승인 절차를 실행한다** (v2.0)
5. 에이전트가 반환한 결과물을 검토하고 통합한다
6. **에이전트가 권한 경계를 위반하면 즉시 중단하고 재지시한다** (v2.0)
7. QC 결과에 따라 재작업 또는 전달을 판단한다
8. Phase 전환 시 SOT를 갱신한다
9. 사용자에게 결과물과 제안을 전달한다

## 금지 패턴 (MUST NOT DO) — 위반 시 QC에서 즉시 FAIL (v5.0)

아래는 AI가 흔히 만드는 실수 목록이다. 해당 패턴이 코드에 있으면 검증 조건 통과 여부와 관계없이 수정해야 한다.

### 공통 (모든 스택)
- ❌ 하드코딩 시크릿 (API 키, 비밀번호, 토큰을 소스코드에 직접 작성) → 환경변수 사용
- ❌ 입력 검증 누락 (사용자 입력을 검증 없이 사용) → 타입/범위/길이 검증
- ❌ 에러 무시 (catch 블록을 비워두거나 console.log만) → 적절한 에러 처리 + 사용자 피드백
- ❌ deprecated API 사용 → 현재 버전의 권장 API 사용
- ❌ console.log 디버그 코드 잔류 → 프로덕션 코드에서 제거 (로거 사용)
- ❌ 불필요한 주석 (코드와 동일한 내용 반복) → 자명한 코드는 주석 없이

### 프론트엔드 (React/Vue/HTML)
- ❌ 배열 인덱스를 key로 사용 (`key={index}`) → 고유 ID 사용
- ❌ 직접 state 변이 (`state.x = 1`) → 불변 업데이트 (setState, spread 등)
- ❌ useEffect 정리 함수 누락 (타이머, 이벤트리스너, 구독) → return cleanup
- ❌ Error Boundary 없는 프로덕션 → 최소 1개 Error Boundary 필수
- ❌ innerHTML에 사용자 데이터 삽입 → textContent 또는 sanitize 라이브러리
- ❌ inline function을 props로 반복 전달 (`onClick={() => fn(id)}` 매 렌더) → useCallback 또는 외부 정의
- ❌ `*:focus { outline: none }` 전역 포커스 제거 → focus-visible 사용

### 백엔드 (Node/Python/Java)
- ❌ SQL 문자열 조합 (`"SELECT * FROM users WHERE id=" + id`) → 파라미터 바인딩 / prepared statement
- ❌ exec/eval에 사용자 입력 전달 → execFile + 인자 배열 / 화이트리스트
- ❌ 에러 응답에 스택 트레이스 노출 → 프로덕션에서 일반 에러 메시지만
- ❌ 동기 I/O로 메인 스레드 블로킹 (readFileSync 등) → 비동기 API 사용
- ❌ CORS 전체 허용 (`*`) → 명시적 origin 지정
- ❌ Rate limiting 없는 인증 엔드포인트 → 로그인/회원가입에 rate limit 적용

### 스타일링 (CSS/Tailwind)
- ❌ 무작위 z-index (`z-index: 9999`) → 정의된 스케일 사용 (10/20/30/50)
- ❌ `!important` 남용 → 선택자 우선순위로 해결
- ❌ 하드코딩 색상 (디자인 시스템 있을 때) → CSS 변수 또는 테마 토큰 사용
- ❌ px 단위 폰트 크기 고정 → rem 사용 (접근성)

## 검증 절차 (순서대로 실행)

### 1단계: 빌드 검증 (RT-1)
스택별 빌드 명령을 실행하여 빌드 성공 여부를 확인한다.
- Python: `pip install -r requirements.txt` (또는 poetry install)
- Node.js: `npm install && npm run build` (또는 pnpm)
- Docker: `docker compose build`
- 빌드 에러 발생 시 에러 로그 전문을 기록하고 FAIL 판정

- Prisma: `npx prisma migrate deploy` 실행
- 마이그레이션 에러 시 FAIL 판정
- DB가 없는 프로젝트는 SKIP

### 3단계: 런타임 스모크 테스트 (RT-3)
서버를 기동하고 핵심 엔드포인트를 호출한다.
1. 서버 기동 (백그라운드): 스택에 맞는 명령 실행
2. 서버 준비 대기: health/ready 엔드포인트 폴링 (최대 30초)
3. 헬스 체크: GET /health 또는 GET /api/health → 200 확인
4. 인증 흐름: 회원가입 → 로그인 → 토큰 획득 → 인증 필요 API 호출
5. 핵심 CRUD: 기획서의 핵심 기능에 해당하는 API 최소 1개씩 호출
6. 프론트엔드: GET / → 200 + HTML 응답 확인 (프론트엔드가 있는 경우)
- 각 호출의 상태 코드, 응답 시간, 응답 body 요약을 기록
- 서버 기동 실패 시 에러 로그 전문 기록 후 FAIL 판정

### 4단계: API 계약 테스트 (RT-4)
API 응답의 구조가 프론트엔드 기대와 일치하는지 검증한다.
- 응답 필드명 규칙: camelCase/snake_case 일관성 확인
- 필수 필드 존재 여부: planning.md의 데이터 모델 대비 확인
- 페이지네이션 형식: total, page, items 등 표준 구조 확인
- 에러 응답 형식: 일관된 에러 응답 구조 확인

## 판정 기준
- **PASS**: RT-1 ~ RT-3 모두 성공 + RT-4 위반 없음
- **CONDITIONAL PASS**: RT-1 ~ RT-3 성공 + RT-4 경미한 위반 (warning 기록)
- **FAIL**: RT-1 ~ RT-3 중 하나라도 실패

## 출력 규칙

### 1단계: 서비스 기동

### 2단계: 스크린샷 캡처 (VT-1)
핵심 화면별로 데스크톱(1280px)과 모바일(375px) 뷰포트에서 스크린샷을 캡처한다.

### 3단계: 시각 검증 (VT-2)
캡처된 스크린샷을 ui-guide.md 기준과 대조한다.
- 색상 팔레트: Primary/Secondary/Background/Text 색상이 가이드와 일치하는가
- 폰트: 제목/본문 폰트가 가이드와 일치하는가
- 레이아웃: 사이드바/탑바/카드 구조가 가이드를 따르는가
- 컴포넌트: 버튼, 입력창, 카드 등의 스타일이 일관적인가
- 여백: 요소 간 간격이 일관적인가
- 반응형: 모바일 뷰에서 가로 스크롤 없이 정상 표시되는가

### 4단계: 상태별 화면 검증 (VT-3)
같은 화면의 다양한 상태를 확인한다.
- 빈 상태 (Empty state): 데이터가 없을 때 적절한 안내가 표시되는가
- 로딩 상태: 로딩 인디케이터가 표시되는가
- 에러 상태: 에러 발생 시 사용자 친화적 메시지가 표시되는가
- 데이터 있는 상태: 실제 데이터가 올바르게 렌더링되는가

### 5단계: 인터랙션 검증 (VT-4, 가능한 범위)
기본적인 사용자 인터랙션을 테스트한다.
- 버튼 클릭 → 예상 동작 수행 확인
- 폼 입력 → 유효성 검증 동작 확인
- 네비게이션 → 페이지 전환 정상 동작 확인
- 모달/드롭다운 → 열기/닫기 정상 동작 확인
