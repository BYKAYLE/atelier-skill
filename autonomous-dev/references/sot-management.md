## L1: 프로젝트 요약 (L1-project-summary.md)

항상 로드되는 최상위 문서. 새 에이전트가 읽으면 프로젝트 전체를 파악할 수 있어야 한다.

### 템플릿

```markdown
# {프로젝트명} — 프로젝트 요약

## 한줄 설명
{이 프로젝트가 무엇인지 한 문장으로}

## 현재 상태
- Phase: {현재 Phase}
- 버전: {v1.0, v1.1 등}
- 마지막 작업일: {날짜}

## 핵심 기능 (구현 완료)
- [ ] {기능1}: {간략 설명}
- [ ] {기능2}: {간략 설명}

## 기술 스택
- 프론트엔드: {React / HTML+CSS / Vue 등}
- 스타일링: {Tailwind / CSS / styled-components 등}
- 기타: {사용 중인 라이브러리}

## 파일 구조 요약
```
src/
├── index.html
├── components/
└── styles/
```

## 미해결 이슈
- {이슈1}

## 다음 작업 예정
- {예정 작업}
```

```markdown
- 핵심 로직: {간략 설명}

## 결정사항
- {결정1}: {이유}

## 알려진 이슈
- {이슈}
```

## CLAUDE.md: 실행 규칙

AI가 코드를 생성하고 작업할 때 참조하는 규칙 파일. SOT가 "무슨 일이 있었는지"를 기록하는 곳이라면, CLAUDE.md는 "어떻게 일해야 하는지"를 정의하는 곳이다.

### 초기 템플릿

```markdown
# {프로젝트명} — 실행 규칙

## 코딩 규칙
- 모든 파일은 UTF-8 인코딩
- HTML/CSS/JS는 단일 파일로 통합 (별도 분리하지 않음)
- 외부 라이브러리는 CDN으로 로드
- 주석은 한국어로 작성

## 네이밍 규칙
- 파일명: kebab-case (예: user-profile.html)
- CSS 클래스: kebab-case
- JavaScript 변수/함수: camelCase

## 금지 사항
- localStorage, sessionStorage 사용 금지 (Cowork 환경 제약)
- 인라인 스타일 최소화

## 프로젝트 특수 규칙
(Phase 1 이후 추가)

## 학습된 규칙 (자기 개선 루프에서 추가됨)
{SOT에서 발견한 문제를 분석하여 여기에 규칙으로 추가}
```

## 자기 개선 루프

이 루프가 시스템을 점진적으로 개선한다:

### 루프 단계

1. **기록**: 매 작업 후 SOT의 sessions/ 에 작업 로그 남기기
   - 무슨 작업을 했는가
   - 어떤 에러가 발생했는가
   - 어떻게 해결했는가
   - 어떤 자율 판단을 했는가

2. **분석**: Phase 4 완료 후 세션 로그 검토
   - 반복 에러 패턴이 있는가
   - 비효율적인 판단이 있었는가
   - 빌더 에이전트가 혼란스러워한 지시가 있었는가

3. **반영**: 발견한 문제를 CLAUDE.md에 규칙으로 추가 — **품질 게이트 통과 필수 (v3.0)**
   - 에러 패턴 → "금지 사항" 또는 "코딩 규칙"에 추가
   - 좋은 판단 → "권장 사항"에 추가
   - 새로운 기술 결정 → "기술 스택" 업데이트

   **규칙 추가 전 3중 게이트 (v3.0)**:
   | 게이트 | 질문 | No일 때 |
   |--------|------|---------|
   | 재현 가능성 | "다른 프로젝트/사용자에게도 이 상황이 생길 수 있는가?" | sessions/ 메모로만 기록, CLAUDE.md에 추가하지 않음 |
   | 일반화 가능성 | "이 프로젝트 특수 조건 없이도 적용되는 규칙인가?" | CLAUDE.md의 "프로젝트 특수 규칙" 섹션에만 추가 |
   | 명확성 | "에이전트가 이 규칙을 읽고 다음에 다르게 행동할 수 있는가?" | 재작성하여 행동 변화를 유도하는 문장으로 수정 후 추가 |

   **기존 규칙 충돌 확인**: 새 규칙이 기존 CLAUDE.md 규칙과 모순되면, 리더가 어느 쪽을 우선할지 판단하고 decisions.md에 근거를 기록한다.

4. **검증**: 다음 사이클에서 개선된 규칙이 적용되는지 확인

### 예시

**SOT 기록**: "빌더가 React useState를 import 없이 사용하여 에러 발생. QC에서 잡아서 수정."

**CLAUDE.md 반영**: 코딩 규칙에 "React Hooks 사용 시 반드시 import 문 포함 확인" 추가.

**다음 사이클**: 빌더 에이전트가 CLAUDE.md를 읽고 동일 실수를 사전 방지.

## Phase 전환 핸드오프 문서 (v3.0)

Phase 전환 시(Phase 1→2, 2→3, 3→3.5, 3.5→4) 리더가 작성하는 구조화된 핸드오프 문서. 세션 인수인계와 별도로, Phase 간 맥락 전달을 위해 사용한다.

### 핸드오프 템플릿

```markdown
# Phase 핸드오프 — Phase {N} → Phase {N+1}

## 결정사항
이번 Phase에서 내린 주요 결정:
- {결정1}: {이유} → {결과}
- {결정2}: {이유} → {결과}

## 거부사항
검토했으나 채택하지 않은 것:
- {거부1}: {왜 거부했는지}

## 리스크
다음 Phase에서 주의해야 할 위험 요소:
- {리스크1}: {발생 가능성} / {영향도} / {대응 방안}

## 다음 Phase 진입 조건
- [ ] {조건1 — 예: "기획서 사용자 승인 완료"}
- [ ] {조건2 — 예: "SOT 갱신 완료"}
```

### 핸드오프 작성 규칙
- Phase 전환 시 **필수** 작성 (게이트 — 작성 없이 다음 Phase 진행 불가)
- 저장 위치: `SOT/sessions/handoff-phase{N}-to-{N+1}.md`
- "결정사항"이 0건이면 안 된다 — 모든 Phase에는 최소 1건의 결정이 있다
- "거부사항"과 "리스크"는 0건 가능 (없으면 "없음"으로 명시)

## Auto-Checkpoint (v4.1) — 중단 대비 자동 저장

터미널 종료, 컨텍스트 소진 등으로 세션이 중단될 수 있다. 체크포인트는 중단 시 손실을 최소화한다.

### 체크포인트 파일

저장 위치: `SOT/sessions/checkpoint.md`

```markdown
# Checkpoint — {프로젝트명}

## 현재 위치
- 빌더: 서비스 빌더 / 피처 빌더
- Phase: {현재 Phase} (예: S-Phase 2)
- Step: {현재 Step} (예: 빌더 에이전트 3/5 완료)

## 완료된 Phase
- [x] S-Phase 0: 목적 정의 + 시장 리서치
- [x] S-Phase 1: 전체 기획
- [x] S-Phase 1.5: 기획 승인
- [x] S-Phase 1.7: UI 디자인 (Stage 2까지 완료)
- [ ] S-Phase 2: 전체 빌드 (진행 중)
- [ ] S-Phase 3: 기능 QC (정적 분석)
- [ ] S-Phase 3.3: 빌드 + 런타임 검증
- [ ] S-Phase 3.5: 최종 보안/품질 QC
- [ ] S-Phase 3.7: 브라우저 시각 검증 (선택)
- [ ] S-Phase 4: 전달

## 진행 중 작업 상세
- 현재 작업: {구체적 작업 내용}
- 완료된 빌더 작업: {목록}
- 미완료 빌더 작업: {목록}
- 생성된 파일: {목록}

## 재개 시 주의사항
- {이어서 할 때 알아야 할 컨텍스트}
```

### 체크포인트 갱신 타이밍

| 시점 | 담당 |
|------|------|
| 각 Phase 시작 시 | 리더 |
| 각 Phase 내 주요 Step 완료 시 | 리더 |
| 에이전트 작업 1건 완료마다 | 리더 |
| 사용자 승인 게이트 통과 후 | 리더 |
| UI 디자인 Stage 전환 시 | 리더 |

### 체크포인트 규칙

1. **덮어쓰기 방식** — checkpoint.md는 항상 최신 상태 1건만 유지 (히스토리는 sessions/에 별도 기록)
2. **Phase 완료 시 삭제** — Phase 4 전달 완료 후 checkpoint.md를 삭제한다 (정상 종료)
3. **새 세션 시작 시 확인** — SOT 폴더가 있으면 checkpoint.md 존재 여부를 먼저 확인한다
4. **복구 우선** — checkpoint.md가 있으면 "중단된 작업이 있습니다. 이어서 진행할까요?"를 사용자에게 묻는다

### 세션 복구 흐름

```
새 세션 시작
  │
  ├── SOT 없음 → 서비스 빌더 (새 프로젝트)
  │
  └── SOT 있음
        │
        ├── checkpoint.md 있음 → "중단된 작업 발견. 이어서 진행할까요?"
        │     │
        │     ├── Yes → checkpoint에서 Phase/Step 읽고 → 해당 지점부터 재개
        │     └── No → 사용자 요청에 따라 새 작업 시작
        │
        └── checkpoint.md 없음 → 정상 SOT → 피처 빌더 / 서비스 빌더 판별
```

## SOT 갱신 타이밍

| 시점 | 갱신 대상 | 담당 | 강제 수준 |
|------|----------|------|----------|
| 각 Phase 시작/Step 완료 시 (v4.1) | checkpoint.md | 리더 | **필수** — 중단 복구용 |
| Phase 1 완료 | L1, L2 초기 생성 | 문서 에이전트 | 필수 |
| Phase 전환 시 (v3.0) | 핸드오프 문서 (sessions/handoff-phaseN-to-M.md) | 리더 | **게이트** — 다음 Phase 진행 차단 |
| Phase 2 병렬 그룹 완료마다 | 해당 L2, decisions, changelog, sessions/ | 문서 에이전트 | **게이트** — 다음 그룹 진행 차단 |
| Phase 3 QC 완료 | issues.md, changelog.md | 문서 에이전트 | **게이트** — Phase 3.3 진행 차단 |
| Phase 3.3 런타임 검증 완료 (v5.0) | issues.md (런타임 이슈), changelog.md | 문서 에이전트 | **게이트** — Phase 3.5 진행 차단 |
| Phase 3.5 Final QC 완료 | issues.md, changelog.md (최종 검증 결과) | 문서 에이전트 | **게이트** — Phase 4 진행 차단 |
| Phase 4 전달 전 | L1 전체 갱신, decisions 통합, sessions 로그, L2 보충 | 문서 에이전트 | **게이트** — 사용자 전달 차단 |
| Phase 4 전달 전 | CLAUDE.md (자기 개선 루프) | 리더 | **게이트** — 사용자 전달 차단 |

### 게이트 규칙

**"게이트"는 사용자 승인 게이트(✋)와 동일한 강도의 필수 절차다.**

- 게이트로 표시된 SOT 갱신이 완료되지 않으면 다음 단계로 진행할 수 없다
- "시간이 없다", "컨텍스트가 부족하다"는 이유로 건너뛸 수 없다
- 문서 에이전트 호출이 실패하면 리더가 직접 해당 SOT 파일을 갱신한다
- Phase 4의 SOT 갱신 검증 체크리스트를 모두 통과해야 사용자에게 전달할 수 있다

### SOT 갱신 검증 체크리스트 (Phase 4 전달 전 필수 확인)

- [ ] L1의 "현재 상태"와 "핵심 기능" 목록이 실제 결과물과 일치하는가
- [ ] changelog에 이번 사이클이 기록되어 있는가
- [ ] decisions.md에 최소 1건 이상의 판단이 기록되어 있는가
- [ ] L2-features/에 구현된 주요 기능별 파일이 있는가
- [ ] issues.md가 QC 결과를 반영하고 있는가 (이슈가 없어도 "없음"으로 명시)
- [ ] sessions/에 이번 세션 로그가 있는가
- [ ] CLAUDE.md의 "학습된 규칙"이 검토되었는가 (추가할 것이 없어도 검토 자체는 필수)

미충족 항목이 있으면 문서 에이전트를 재호출하거나 리더가 직접 보충한다.
