# Phase 상세 절차

각 Phase의 구체적 수행 절차, 입출력, 에이전트 운용 방법을 정의한다.

## Phase 0: 수신

### 목적
사용자의 아이디어/요구사항을 수신하고 작업 환경을 준비한다.

### 절차

**서비스 빌더 (0→1) 일 때:**
1. 사용자 메시지에서 핵심 요구사항을 추출한다
2. **모호성 내부 게이트 (v3.0)** — 리더가 내부적으로 4항목을 평가한다 (사용자에게 점수를 보여주지 않는다):
   - Goal: "누구를 위해 어떤 문제를 해결하는가"를 한 문장으로 쓸 수 있는가?
   - Constraints: CLAUDE.md/SOT에서 제약이 파악되었는가?
   - Criteria: 완성 기준이 파악 가능한가?
   - Context: 사용 환경/대상 사용자가 파악 가능한가?
   - **판정**: Goal 명확 → 진행. Goal 불명확 → 1개 질문 후 진행. 2개 이상 질문 금지.
3. `scripts/init_project.py` 실행하여 SOT 폴더 구조 생성
4. L1-project-summary.md에 초기 정보 기입
5. CLAUDE.md에 기본 규칙 세팅
6. Phase 1로 진행

**피처 빌더 (1→N) 일 때:**
1. SOT 폴더의 L1-project-summary.md를 읽는다
2. changelog.md에서 최근 변경사항을 확인한다
3. issues.md에서 미해결 이슈를 확인한다
4. CLAUDE.md에서 현재 규칙을 로드한다
5. 사용자의 새 요구사항과 현재 상태를 매칭한다
6. Phase 1로 진행

### 입출력
- 입력: 사용자 메시지
- 출력: 초기화된 SOT (서비스 빌더) 또는 로드된 프로젝트 상태 (피처 빌더)

## Phase 1: 기획

### 목적
요구사항을 실행 가능한 작업 단위로 분해하고, 사용자 승인을 받는다.

### 절차
1. 기획 에이전트(Opus) 생성
2. 에이전트에게 전달: L1 문서 + market-research.md + proven-patterns.md + 사용자 요구사항 + CLAUDE.md 규칙
3. 에이전트가 반환: 기획서(planning.md) + 작업분해표(tasks.md)
4. 리더가 기획서를 검토하고 사용자에게 제시
5. **사용자 승인 대기**
6. 승인 후 → Phase 2 진행
7. 수정 요청 시 → 기획 에이전트 재생성하여 수정

### 기획서에 포함되는 것
- 프로젝트 개요
- 기능 목록 (필수/권장/선택 구분)
- 기술 스택 및 선정 이유
- 파일 구조
- 예상 결과물 형태

### 작업분해표 형식
| ID | 작업명 | 설명 | 복잡도 | 의존성 | 모델 | 병렬 그룹 |
|----|--------|------|--------|--------|------|----------|
| T1 | 기본 레이아웃 | HTML 구조 및 CSS | 낮음 | 없음 | Sonnet | G1 |
| T2 | 네비게이션 | 메뉴 바 구현 | 낮음 | 없음 | Sonnet | G1 |
| T3 | 데이터 로직 | 상태 관리 및 CRUD | 높음 | T1 | Opus | G2 |

병렬 그룹(G1, G2...)이 같은 작업은 동시에 진행할 수 있다.

### 사용자에게 보여주는 형식

```
📋 기획서 요약

[프로젝트 개요]
{한두 문장}

[구현할 기능]
✅ 필수: {기능1}, {기능2}, {기능3}
📌 권장: {기능4}, {기능5}
💡 선택: {기능6}

[기술 스택]
{선택한 기술과 간략한 이유}

[예상 작업량]
{작업 N개, 예상 소요 Phase 2 시간}

승인하시면 개발을 시작합니다. 수정하고 싶은 부분이 있으면 말씀해주세요.
```

## Phase 2: 자율 개발

### 목적
승인된 기획에 따라 사용자 개입 없이 코드를 작성하고 결과물을 생성한다.

### 절차

**Step 0. 사전 일관성 확인 (v3.0) — 각 병렬 그룹 시작 전 실행**

그룹 빌드를 시작하기 전에 리더가 아래를 확인한다:
- [ ] SOT의 L1-project-summary.md와 현재 코드 상태가 일치하는가
- [ ] 이전 그룹 빌드 결과물이 프로젝트에 정상 통합되었는가
- [ ] 이전 그룹에서 생성된 파일과 이번 그룹 작업 대상 파일 간 충돌 가능성이 없는가
- [ ] CLAUDE.md의 규칙이 이번 그룹 작업에 적용 가능한 상태인가

**불일치 발견 시**: 빌더 생성 전에 먼저 해결한다. SOT 갱신이 필요하면 문서 에이전트를 호출한다.

**Step 1~이후** (기존 절차):

1. 작업분해표에서 병렬 그룹별로 작업을 정렬한다
2. 각 그룹의 작업들에 대해 빌더 에이전트를 생성한다:
   - 복잡도 높음 → `model: "opus"`
   - 복잡도 보통/낮음 → `model: "sonnet"`
3. 빌더에게 전달하는 것:
   - L1-project-summary.md 내용
   - 해당 작업의 상세 사양 (L2 수준)
   - ui-guide.md (UI 디자인 가이드 — 반드시 준수)
   - CLAUDE.md의 코딩 규칙
   - 기존 코드 (있는 경우, 피처 빌더)
   - 검증 조건 (빌더 스스로 확인할 것)
4. 빌더 완료 후 결과물 수집:
   - 코드 파일들
   - report.md (작업 보고서)
5. **[필수] 병렬 그룹 완료 시 → 문서 에이전트(Haiku) 호출하여 SOT 즉시 갱신:**
   - 해당 기능의 L2 문서 생성/갱신 (L2-features/feature-{name}.md)
   - decisions.md에 빌더 report.md의 판단 기록 병합
   - changelog.md에 해당 그룹 완료 기록 추가
   - sessions/ 에 작업 로그 저장
   - **이 단계를 완료해야 다음 병렬 그룹으로 진행할 수 있다 (게이트)**
6. 다음 병렬 그룹의 작업이 이전 그룹에 의존하면, 이전 결과를 전달한다
7. 모든 작업 완료 후 통합:
   - 파일들을 프로젝트 구조에 합친다
   - 충돌이 있으면 리더가 판단하여 해결
8. Phase 3으로 진행

### 빌더 생성 예시 (Agent tool 사용)

```
Agent tool 호출:
- subagent_type: "general-purpose"
- model: "opus"  (또는 "sonnet")
- prompt: {agent-roles.md의 빌더 프롬프트 템플릿을 채운 것}
```

### 중요 규칙
- 빌더에게 질문하지 말고 판단하라고 지시한다
- 판단한 내용은 report.md에 기록하라고 지시한다
- 검증 조건을 빌더 스스로 확인하라고 지시한다 (1차 자체 QC)
- **문서 갱신 없이 다음 그룹으로 넘어가지 않는다 — 이것은 사용자 승인 게이트와 동일한 강도의 필수 절차다**

## Phase 3: 기능 QC (정적 분석)

### 목적
빌더가 만든 결과물이 실제로 동작하는지 독립적으로 검증한다.

### 절차
1. QC 에이전트(Sonnet) 생성
2. 에이전트에게 전달:
   - 통합된 결과물 전체 경로
   - 기획서의 기능 목록
   - 각 빌더의 검증 조건
   - QC 체크리스트 (`references/qc-checklist.md`)
   - issues.md의 기존 알려진 이슈 목록 (이미 알려진 이슈를 새 버그로 리포트하지 않기 위함)
3. QC 에이전트가 실행:
   - 코드를 실제로 실행한다
   - 에러 유무를 확인한다
   - 기능별 동작을 검증한다
   - 가능하면 브라우저에서 확인한다
4. 판정:
   - **PASS** → **[필수] 문서 갱신 후** Phase 3.5
   - **FAIL** → 재작업 프로세스 시작
   - **PASS with Notes** → **[필수] 문서 갱신 후** Phase 3.5 (경미한 이슈 보고와 함께)
5. **[필수] QC 완료 시 → 문서 에이전트(Haiku) 호출하여 SOT 즉시 갱신:**
   - issues.md에 QC에서 발견된 이슈 기록 (심각도, 상태, 재현 조건)
   - changelog.md에 QC 결과 기록 (PASS/FAIL, 재작업 횟수)
   - **이 단계를 완료해야 Phase 3.5로 진행할 수 있다 (게이트)**

### 재작업 프로세스
1. QC 보고서에서 실패 항목과 수정 방향을 추출한다
2. 새 빌더 에이전트를 생성한다 (기존 빌더와 다른 새 에이전트)
3. 새 빌더에게 전달: 현재 코드 + QC 실패 보고서 + 수정 지시
4. 수정된 코드를 다시 QC에 보낸다
5. 최대 3회 반복
6. 3회 실패 시 → 에스컬레이션 보고서 작성 후 사용자에게 보고
7. **재작업 시에도 매 라운드 후 issues.md 갱신 (해결된 이슈 상태 변경, 새 이슈 추가)**

### QC 차단 보고서 템플릿 (v3.0)

QC가 FAIL 판정 시, 아래 형식의 차단 보고서를 작성하여 재작업 빌더에게 전달한다:

```markdown
# QC 차단 보고서 — Round {N}/3

## 실패 항목
| 항목 | 심각도 | 실패 내용 | 근거 (로그/출력) |
|------|--------|----------|----------------|
| {항목1} | Critical | {구체적 실패 내용} | {에러 메시지 또는 실행 출력} |

## 재작업 지시사항
1. {구체적으로 무엇을 어떻게 수정해야 하는지}
2. {수정 후 확인해야 할 검증 조건}

## 이전 라운드 이력 (Round 2+에서)
- Round 1: {어떤 문제로 실패 → 어떻게 수정 시도 → 결과}
```

### 에스컬레이션 보고서 (3회 실패 시) (v3.0)

3-strike 도달 시 사용자에게 전달하는 보고서:

```markdown
# 에스컬레이션 보고서 — {작업명}

## 상황 요약
3회 재작업에도 해결되지 않은 문제가 있습니다.

## 현재 동작하는 부분
- {정상 동작하는 기능 목록}

## 미해결 문제
| 문제 | 3회 시도 결과 | 근본 원인 분석 |
|------|-------------|--------------|
| {문제1} | {시도한 방법과 실패 이유} | {왜 해결이 안 되는지} |

## 선택지
1. **현재 상태로 진행** — {동작하는 부분만 배포, 미해결 이슈는 다음 사이클}
2. **기획 수정** — {요구사항을 조정하여 다른 방식으로 구현}
3. **추가 조사** — {근본 원인을 더 파악한 후 재시도}
```

## Phase 3.3: 빌드 + 런타임 검증 (v5.0)

### 목적
Phase 3(정적 분석)이 "코드를 읽었을 때 문제가 없는가"를 검증했다면, Phase 3.3은 **"실제로 빌드하고 실행했을 때 동작하는가"**를 검증한다. 코드가 문법적으로 올바르고 정적 분석을 통과해도 런타임에서 실패할 수 있다 — 이것을 잡는 것이 Phase 3.3의 역할이다.

### 절차

**Step 1. 런타임 검증 에이전트(Sonnet)를 생성한다**

에이전트에게 전달하는 것:
- 프로젝트 전체 파일 경로
- CLAUDE.md (빌드/실행 방법)
- docker-compose.yml 또는 서버 실행 스크립트 경로
- 기획서의 API 엔드포인트 목록 (있는 경우)
- issues.md (기존 알려진 이슈)

**Step 2. 빌드 검증 (Build Verification)**

스택별 빌드 명령을 순서대로 실행한다:

| 스택 | 빌드 명령 | 통과 기준 |
|------|----------|----------|
| Node.js/React/Next.js | `npm run build` 또는 `pnpm build` | exit code 0, 에러 없음 |
| Python/FastAPI | `python -c "from app.main import app"` | import 성공, 에러 없음 |
| TypeScript | `tsc --noEmit` | 타입 에러 0건 |
| Docker | `docker compose build` | 모든 서비스 빌드 성공 |

**Step 3. DB 마이그레이션 검증 (DB 프로젝트만)**

| 도구 | 검증 명령 | 통과 기준 |
|------|----------|----------|
| Alembic (SQLAlchemy) | `alembic check` 또는 `alembic upgrade head --sql` | 에러 없음, 스키마 일치 |
| Prisma | `npx prisma validate` + `npx prisma migrate status` | 스키마 유효, 마이그레이션 동기화 |
| Drizzle | `npx drizzle-kit check` | 에러 없음 |

- 마이그레이션 도구가 없으면 "N/A"로 기록
- 실제 DB 연결이 불가능한 경우 `--sql` 모드(dry-run)로 대체

**Step 4. 런타임 Smoke Test**

서버를 실제로 기동하고 핵심 동작을 검증한다:

```
1. 서비스 기동
   - Docker: docker compose up -d → 모든 서비스 healthy 확인
   - 개발 서버: npm run dev / uvicorn 등 → listening 상태 확인
   - 타임아웃: 60초 (서비스 시작 대기)

2. 헬스체크
   - curl http://localhost:{port}/ → 200 OK
   - curl http://localhost:{port}/health → 200 OK (있는 경우)

3. 핵심 API 호출 (각 엔드포인트별)
   - 정상 요청 → 기대 응답 코드 확인 (200/201)
   - 인증 필요 엔드포인트 → 401 확인 (미인증 시)
   - 존재하지 않는 리소스 → 404 확인

4. 인증 흐름 (인증 기능이 있는 경우)
   - POST /register → 201 + 토큰 반환
   - POST /login → 200 + 토큰 반환
   - GET /protected → 200 (토큰 포함 시)
   - GET /protected → 401 (토큰 없이)

5. 프론트엔드 페이지 (웹 앱인 경우)
   - 각 라우트별 HTTP 200 확인
   - HTML 응답에 핵심 마크업 포함 여부 (빈 페이지가 아닌지)

6. 서비스 종료
   - docker compose down / 프로세스 종료
   - 포트 해제 확인
```

**Step 5. API 계약 테스트 (Contract Test)**

프론트엔드가 기대하는 응답 형식과 백엔드 실제 응답이 일치하는지 검증한다:

- 프론트엔드 타입 정의 (TypeScript interfaces) vs 백엔드 실제 응답 JSON
- camelCase/snake_case 변환이 올바른지
- 필수 필드가 누락되지 않았는지
- 페이지네이션 응답 형식 일관성

**Step 6. 판정**

| 판정 | 조건 | 다음 단계 |
|------|------|----------|
| **PASS** | 빌드 성공 + 서버 기동 + 핵심 API 정상 | Phase 3.5 진행 |
| **FAIL** | 빌드 실패 또는 서버 기동 실패 또는 핵심 API 실패 | 수정 후 재검증 |

**Step 7. 실패 시 수정 프로세스**

1. 런타임 QC 보고서에서 실패 항목과 에러 로그를 추출한다
2. 새 빌더 에이전트를 생성하여 수정을 지시한다
3. 수정 후 Step 2부터 재실행 (전체 재실행)
4. 최대 3회 반복. 3회 실패 시 에스컬레이션 보고서 작성

**Step 8. [필수] 문서 에이전트(Haiku) 호출하여 SOT 갱신**

- issues.md에 런타임 검증에서 발견된 이슈 기록

## Phase 3.5: 최종 보안/품질 QC (Final Security & Quality Audit)

### 목적
Phase 3이 "기능이 동작하는가"를 검증했다면, Phase 3.5는 **"프로덕션에 배포해도 안전한가"**를 검증한다. 보안 취약점, 성능 문제, 시크릿 노출, 미사용 코드를 발견하고 수정한다.

### 절차

**Step 1. 6개 감사 에이전트를 병렬 생성한다**

각 에이전트는 독립적으로 감사를 수행하고 결과를 반환한다:

| 에이전트 | 모델 | 감사 대상 |
|---------|------|----------|
| Dead Code 감사 | Sonnet | 미사용 함수, 변수, CSS, import, 도달 불가 코드 |
| Performance 감사 | Sonnet | DOM 반복 조회, 이벤트 누적, 메모리 누수, 무한 캐시, 동기 I/O |
| Secrets/PII 감사 | Sonnet | 하드코딩 키, 로그 내 민감정보, 문서 내 시크릿, 에러 응답 내부정보 |
| 보안 감사 (security-router) | Opus | `security-router` 스킬 호출 → 코드 성격에 따라 L1(OWASP)+L2(Sentry) 또는 L1+L2+L3(TrailOfBits) 자동 결정 |
| UI/UX Compliance 감사 (v4.0) | Sonnet | 접근성, 반응형, 디자인 시스템 준수, 터치/인터랙션 |
| Smoke Test | Sonnet | 서버 기동, 파일 로드, 보안 헤더, 인증 흐름, API 동작 |

**각 에이전트에게 전달하는 것:**
- 프로젝트 전체 파일 경로
- `references/qc-checklist.md`의 해당 감사 영역 체크리스트
- issues.md (기존 알려진 이슈 — 중복 리포트 방지)
- CLAUDE.md (프로젝트 보안/코딩 규칙)

**피처 빌더의 경우:** Dead Code/Performance/Security 감사는 변경된 파일 + 영향 파일로 스코프 제한. Secrets/PII는 전체 대상.

**Step 2. 감사 결과를 수집하고 심각도별로 정렬한다**

심각도 우선순위: CRITICAL > HIGH > MEDIUM > LOW

**Step 3. 판정한다**

| 판정 | 조건 | 다음 단계 |
|------|------|----------|
| **PASS** | CRITICAL 0건, HIGH 0건, Smoke Test 전체 PASS | Phase 4 진행 |
| **CONDITIONAL PASS** | CRITICAL 0건, HIGH 1건+ | Step 4 (수정) 후 Phase 4 |
| **FAIL** | CRITICAL 1건+ 또는 Smoke Test 핵심 FAIL | Step 4 (수정) 후 재판정 |

**Step 4. 수정 에이전트를 생성하여 이슈를 해결한다**

1. CRITICAL → HIGH 순서로 수정 에이전트(빌더)에게 전달
2. 수정 에이전트에게 전달: 감사 보고서 + 해당 코드 + 수정 지시
3. 수정 후 **해당 감사 영역만 재실행** (전체 재실행 불필요)
4. 대규모 리팩토링이 필요한 항목은 issues.md에 "DEFERRED" 상태로 기록:
   - 사유 명시 (예: "onclick→addEventListener 전체 마이그레이션 필요")
   - 영향 범위와 리스크 레벨 명시
   - 다음 사이클 권장 사항 명시

**Step 5. [필수] 문서 에이전트(Haiku) 호출하여 SOT 갱신**

- issues.md에 Final QC 발견 이슈 기록 (심각도, 상태: FIXED/DEFERRED, 수정 내용)
- changelog.md에 Final QC 결과 기록
- **이 단계를 완료해야 Phase 4로 진행할 수 있다 (게이트)**

## Phase 3.7: 브라우저 시각 검증 (v5.0, 선택)

### 목적
Phase 3.5까지가 "코드 레벨에서 안전한가"를 검증했다면, Phase 3.7은 **"사용자가 실제로 보는 화면이 의도대로인가"**를 검증한다. 코드가 올바르고 보안 감사를 통과해도, 화면에서 레이아웃이 깨지거나 색상이 틀리면 사용자에게는 버그다.

### 실행 조건 (하나 이상 해당 시 실행)
- 프로젝트에 프론트엔드(웹 UI)가 포함되어 있다
- ui-guide.md가 존재한다
- 이전 QC에서 UI 관련 이슈가 발견되었다
- 신규 화면이 추가되었다 (피처 빌더)

### 절차

**Step 1. 서비스 기동**
- Docker Compose 또는 개발 서버를 실행한다
- 모든 서비스가 healthy/ready 상태가 될 때까지 대기

**Step 2. 스크린샷 캡처**

각 핵심 페이지/라우트의 스크린샷을 캡처한다:
- **데스크톱 뷰** (1280px 너비)
- **모바일 뷰** (375px 너비)
- 로그인 전/후 화면을 구분하여 캡처

캡처 대상 (기획서의 화면 목록 기준):
```
1. 랜딩/메인 페이지
2. 로그인/회원가입 페이지
3. 대시보드 (로그인 후 메인)
4. 각 핵심 기능 페이지
5. 설정 페이지
6. 에러 페이지 (404 등)
7. 빈 상태 화면 (데이터 없을 때)
```

**Step 3. 시각 검증 (ui-guide.md 대조)**

스크린샷을 ui-guide.md와 대조하여 검증:

| 검증 항목 | 확인 내용 |
|-----------|----------|
| 색상 팔레트 | Primary/Secondary/Accent 색상이 가이드와 일치하는가 |
| 타이포그래피 | 폰트 패밀리, 크기 체계가 가이드를 따르는가 |
| 레이아웃 | 사이드바/탑바/그리드 구조가 가이드와 일치하는가 |
| 컴포넌트 스타일 | 버튼, 카드, 입력창 등이 가이드 스타일인가 |
| 반응형 | 모바일에서 가로 스크롤 없이 정상 표시되는가 |
| 빈 상태 | 데이터 없을 때 안내 메시지가 표시되는가 |
| 에러 상태 | 에러 시 사용자 친화적 메시지가 표시되는가 |

**Step 4. 인터랙션 검증**

주요 사용자 흐름을 수동으로 테스트:
- 폼 제출 → 성공/실패 피드백 확인
- 네비게이션 메뉴 동작
- 모달/드롭다운 열기/닫기
- 로딩 상태 표시 여부
- 버튼 클릭 → 결과 반영

**Step 5. 판정 및 보고**

| 판정 | 조건 | 다음 단계 |
|------|------|----------|
| **PASS** | 시각 이슈 없음 | Phase 4 진행 |
| **ISSUES** | 시각 이슈 발견 | issues.md에 기록 후 심각도에 따라 처리 |

시각 이슈 심각도:
- **CRITICAL**: 핵심 기능 화면이 완전히 깨짐 → 즉시 수정
- **HIGH**: 반응형 깨짐 (모바일에서 사용 불가) → 이번 사이클 수정
- **MEDIUM**: 색상/폰트 불일치 → issues.md 기록 후 Phase 4 진행 가능
- **LOW**: 미세 정렬 이슈 → 다음 사이클

## Phase 4: 전달 및 제안

### 목적
동작 확인된 결과물을 사용자에게 전달하고, 다음 단계를 제안한다.

### 절차

**Step 1. [필수] 최종 SOT 갱신 — 사용자에게 전달하기 전에 반드시 실행**

문서 에이전트(Haiku)를 생성하여 아래를 모두 갱신한다:
- L1-project-summary.md — 현재 상태, 버전, 구현 완료 기능 목록 전체 반영
- changelog.md — 이번 전체 사이클 요약 (Phase 0~4까지 무엇을 했는지)
- decisions.md — 전체 빌더 report.md에서 판단 기록을 수집하여 통합 기록
- sessions/ — 이번 세션 전체 로그 저장 (작업 내용, 에러, 해결 방법, 자율 판단)
- issues.md — 최종 상태 반영 (해결된 이슈 상태 변경, 미해결 이슈 정리)
- L2-features/ — Phase 2에서 생성되지 않은 L2 문서가 있으면 이 시점에서 보충 생성

**Step 2. [필수] 자기 개선 루프 — SOT 갱신 직후, 전달 직전에 실행**

리더가 직접 수행한다:
1. sessions/ 로그를 검토한다
2. 반복 에러 패턴이 있으면 → CLAUDE.md "학습된 규칙"에 추가
3. 비효율적인 판단이 있었으면 → CLAUDE.md에 가이드 추가
4. QC에서 발견된 패턴성 이슈가 있으면 → CLAUDE.md "금지 사항" 또는 "코딩 규칙"에 추가

**[v3.0] 규칙 추가 전 3중 게이트** — 2~4번에서 규칙을 추가하기 전에 아래를 통과해야 한다:
- **재현 가능성**: "다른 프로젝트에서도 발생할 수 있는가?" → No → sessions/ 메모로만 기록
- **일반화 가능성**: "프로젝트 특수 조건 없이도 적용되는가?" → No → "프로젝트 특수 규칙"에만 추가
- **명확성**: "에이전트가 읽고 다음에 다르게 행동할 수 있는가?" → No → 재작성 후 추가
- **충돌 확인**: 새 규칙이 기존 CLAUDE.md 규칙과 모순되면 리더가 판단, decisions.md에 근거 기록

**Step 3. SOT 갱신 검증 — 전달 전 체크리스트**

아래 항목을 모두 확인한 후에만 사용자에게 전달한다:
- [ ] L1의 "현재 상태"와 "핵심 기능" 목록이 실제 결과물과 일치하는가
- [ ] changelog에 이번 사이클이 기록되어 있는가
- [ ] decisions.md에 최소 1건 이상의 판단이 기록되어 있는가
- [ ] L2-features/에 구현된 기능 수만큼 파일이 있는가
- [ ] issues.md가 QC 결과를 반영하고 있는가
- [ ] sessions/에 이번 세션 로그가 있는가
- [ ] CLAUDE.md의 "학습된 규칙"이 검토되었는가 (추가할 것이 없어도 검토 자체는 필수)

**미충족 항목이 있으면 문서 에이전트를 재호출하여 보충한다. 모두 충족해야 Step 4로 진행.**

**Step 4. 사용자에게 전달**

1. **동작하는 결과물** (파일 + computer:// 링크)
2. **구현 완료 목록** — 무엇을 만들었는지
3. **자율 판단 보고** — 무엇을 왜 그렇게 결정했는지
4. **추가 기능 제안** — 우선순위와 난이도 표시, 사용자가 선택할 수 있도록

### 추가 기능 제안 형식

```
🚀 추가 가능한 기능

[우선순위 높음]
1. {기능A} — {설명} (난이도: ⭐⭐)
2. {기능B} — {설명} (난이도: ⭐)

[우선순위 보통]
3. {기능C} — {설명} (난이도: ⭐⭐⭐)
4. {기능D} — {설명} (난이도: ⭐⭐)

[선택 사항]
5. {기능E} — {설명} (난이도: ⭐)

원하시는 기능 번호를 선택해주시면 바로 개발을 시작합니다.
여러 개를 동시에 선택해도 됩니다.
```
