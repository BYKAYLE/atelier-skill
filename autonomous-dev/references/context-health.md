# 컨텍스트 건강 관리

## 왜 중요한가

AI 에이전트의 컨텍스트 윈도우는 유한하다. 대화가 길어지고 코드가 쌓이면:
- 초반 지시사항을 잊는다
- 같은 실수를 반복한다
- 결과물 품질이 저하된다
- 일관성이 떨어진다

이 문제를 방지하기 위해 세 가지 전략을 사용한다: 예방, 감지, 교체.

## 전략 1: 예방

### 리더의 역할 제한
리더(메인 에이전트)는 직접 코딩을 하지 않는다. 리더의 컨텍스트는 관리 업무에만 사용한다:
- 사용자 의도 해석
- 작업 분해 및 위임
- 결과물 검토 및 판단
- SOT 관리

코딩은 반드시 워커 에이전트에게 위임한다. 워커는 매 작업마다 새로 생성되므로 항상 깨끗한 컨텍스트로 시작한다.

### 워커에게 최소 정보 전달
워커에게 전달하는 정보를 최소화한다:
- L1 문서 전체 (필수, 1~2페이지)
- 해당 작업의 L2 문서 (필수, 1~3페이지)
- CLAUDE.md의 관련 규칙 (필수, 해당 부분만)
- 기존 코드 (필요한 파일만)

전달하지 않는 것:
- 전체 대화 이력
- 다른 작업의 상세 내용
- 전체 코드베이스

### Phase 전환 시 SOT 갱신
매 Phase가 끝날 때마다 현재 상태를 SOT에 기록한다. 이렇게 하면 리더의 컨텍스트가 커져도 SOT 파일이 진실의 원천 역할을 한다.

## 전략 2: 감지

### 워커 결과물 검증
워커에게 작업을 지시할 때 항상 검증 조건을 함께 전달한다.

```
검증 조건:
1. 코드가 에러 없이 실행되는가
2. {기능}이 동작하는가
3. {특정 조건}을 충족하는가
```

워커가 반환한 결과물에서 검증 조건 충족 여부를 확인한다. 미달 시 해당 워커의 결과를 폐기하고 새 워커를 생성한다.

### 리더 자기 점검
매 Phase 전환 시 리더가 스스로 점검한다:

1. SOT의 L1-project-summary.md를 다시 읽는다
2. 자신이 인식하고 있는 현재 상태와 비교한다
3. 불일치가 있으면 SOT 파일을 기준으로 자신의 인식을 교정한다

이 과정은 리더의 컨텍스트가 길어져서 초반 정보가 흐려졌을 때 SOT로 리셋하는 효과가 있다.

### 품질 저하 신호
아래 신호가 나타나면 에이전트 교체를 고려한다:
- 같은 에러를 두 번 이상 반복
- 이미 결정된 사항을 다시 질문
- 이전 작업과 모순되는 결과 생성
- 작업 지시의 일부를 누락

## 전략 3: 교체

### 워커 교체 (자동)
워커는 기본적으로 매 작업마다 새로 생성되므로 별도 교체 절차가 필요 없다.

QC 실패로 재작업 시에도 기존 워커가 아닌 새 워커를 생성한다. 새 워커에게는:
- 이전 워커의 코드 (수정 대상)
- QC 실패 보고서 (무엇이 잘못되었는지)
- 수정 방향 (어떻게 고쳐야 하는지)

를 전달한다.

### 리더 교체 (세션 전환)
리더(메인 에이전트)의 컨텍스트가 한계에 도달하면:

1. 문서 에이전트를 호출하여 인수인계서 생성
2. SOT가 최신 상태인지 확인
3. 사용자에게 "세션을 새로 시작하면 이어서 진행할 수 있습니다" 안내
4. 새 세션에서 리더가 SOT의 L1을 읽고 인수인계서를 읽으면 즉시 작업 재개 가능

### 인수인계 체크리스트
세션 전환 전 확인 사항:
- [ ] L1-project-summary.md가 현재 상태를 정확히 반영
- [ ] 진행 중이던 작업의 상태가 기록됨
- [ ] 미해결 이슈가 issues.md에 기록됨
- [ ] CLAUDE.md가 최신 규칙을 반영
- [ ] 인수인계서가 생성됨

## Compaction(압축) 기능 활용

Opus 4.6은 컨텍스트 한계에 가까워지면 자동으로 이전 내용을 요약/압축하는 Compaction 기능이 있다.

이것은 유용하지만 완전히 의존하면 안 된다:
- 압축 과정에서 세부 사항이 손실될 수 있다
- 기술적 결정의 이유 같은 것은 요약에서 빠질 수 있다
- 따라서 SOT 파일 기록이 여전히 필수다

Compaction은 "안전망"으로 활용하되, 주 전략은 SOT + 워커 교체로 유지한다.
