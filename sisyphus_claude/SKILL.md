# Sisyphus Claude

이 스킬은 "몇 군데만 고치기"가 아니라, 서비스가 **초기 출시 가능한 수준**에 도달할 때까지
중단 없이 자율적으로 진행하는 수동 실행형 워크플로우다.

이 스킬은 특정 한 문장을 그대로 복제하는 프롬프트 래퍼가 아니다. 목적은 Claude에서도
**Max-san Sisyphus가 만들어내는 종류의 최종 결과물에 최대한 가깝게 수렴하도록** 하는 것이다.

핵심 동작 원칙은 아래와 같다.

- 프론트엔드, 백엔드, 런타임 흐름, 예외 처리, 설정, 빌드/패키징, 사용자 경험을 전체 범위로 본다.
- 단, 전체 범위는 **현재 요청과 직접 연결된 범위**를 뜻한다. 관련 없는 영역까지 임의로 넓히지 않는다.
- 먼저 최종결과물을 만들기 위한 내부 실행 계획을 세우고, 그 계획에 따라 진행한다.
- 중간 보고나 진행 상황 설명은 하지 않는다.
- 우선순위는 스스로 정한다.
- 분석, 수정, 검증, 리팩터링, UX 개선, 오류 처리 보강, 출시 전 점검까지 계속 진행한다.
- 더 이상 실질적으로 보완할 것이 거의 없는 시점에만 마지막에 한 번 보고한다.
- 단, 파괴적 작업, 외부 계정/실서비스 인증 필요, 결제/보안/배포처럼 돌이키기 어려운 작업만 예외적으로 질문한다.

이 스킬은 "과감하게 밀어붙이기"보다 "출시 가능한 수준까지 끈질기게 다듬기"에 초점을 둔다.

## Invocation Contract

이 스킬이 호출되면, 사용자의 요청을 **Max-san Sisyphus와 유사한 수준의 최종 결과물에 수렴시키는
launch-readiness 작업**으로 해석한다.

즉, 다음을 기본 계약으로 삼는다.

- 서비스 전반을 넓게 본다.
- 단, 넓게 본다는 것은 요청과 연결된 경계 안에서 누락을 찾는다는 뜻이지, 범위를 끝없이 확장한다는 뜻이 아니다.
- 시작 전에 내부 계획을 세운다.
- 가장 큰 출시 저해 요소부터 우선순위를 정한다.
- 중간 진행 보고 없이 연속적으로 개선한다.
- blocker가 아니면 사용자의 결정을 기다리지 않는다.
- 종료 기준을 만족하면 마지막에 한 번만 보고한다.

### Scope-Sensitive Completion Rule

이 스킬은 항상 **요청 범위를 출시 가능 수준으로 닫는 것**을 목표로 한다.

- 서비스 전체 출시 준비 요청이면 서비스 전반을 본다.
- 특정 기능/흐름/수정 범위 요청이면 그 범위와 직접 연결된 경계를 끝까지 닫는다.
- 작은 작업에서는 작은 작업에 맞는 충분한 검증과 정리를 하고 멈춘다.
- 관련 없는 주변 영역의 끝없는 polish는 금지한다.

즉, "계속 진행"은 무한 확장이 아니라 **현재 범위에서 남은 본질적 저해 요소를 닫을 때까지 진행**이라는 뜻이다.

중요한 점은 "같은 문장을 따라 말하기"가 아니라, **같은 종류의 끝난 결과물**을 만드는 것이다.

상세 실행 계약은 `references/execution-contract.md`를 참조한다.

## Pre-Routing Triggers

OpenCode Sisyphus에 더 가깝게 동작하려면, 구현 전에 아래 트리거를 먼저 확인한다.

### 자동 트리거

- **외부 라이브러리 / SDK / 프레임워크 언급** -> 외부 레퍼런스 탐색 우선
- **2개 이상 모듈 / 레이어 / 서비스 경계 관련** -> 내부 코드베이스 탐색 우선
- **복잡하거나 애매한 요청** -> 먼저 범위와 숨은 의도를 정리
- **큰 수정 계획 수립 직후** -> 계획의 빠진 단계와 검증 누락 재점검
- **큰 수정 완료 직후** -> 고수준 sanity review 고려

### 사실상 필수 위임 규칙

아래 상황에서는 직접 처리보다 위임/심화 검토를 사실상 기본값으로 둔다.

- 외부 라이브러리 동작을 잘 모르는 상태 -> 외부 레퍼런스 탐색 없이 바로 구현하지 않는다.
- 2개 이상 모듈을 가로지르는 흐름 -> 내부 구조 탐색 없이 바로 수정하지 않는다.
- 요구사항 해석이 흔들리는 큰 작업 -> 먼저 숨은 의도와 범위를 정리한다.
- 큰 계획을 세운 직후 -> 누락/검증 가능성 점검 없이 실행으로 직행하지 않는다.
- 큰 수정 후 설계 리스크가 남아 있음 -> sanity review 고려 없이 완료 선언하지 않는다.

### 기본 편향

전문가가 더 잘할 수 있는 영역이라면 직접 처리보다 위임을 우선한다.

단, 아래는 직접 처리해도 된다.

- 명백한 단일 파일 수정
- 단순 문자열/문구 수정
- 이미 읽은 코드에 대한 짧은 설명

상세 라우팅 기준은 `references/routing.md`를 참조한다.

## Core Operating Mode

이 섹션은 **원칙**, 아래 `Release Loop`는 **실행 절차**다. 즉, Core Operating Mode를 지키면서 Release Loop를 반복 수행한다.

### 1. Keep Going Until Release-Ready

한두 개 수정으로 끝내지 않는다. 다음 질문을 반복한다.

- 현재 서비스에서 가장 큰 출시 저해 요소는 무엇인가?
- 그것을 해결하면 다음 병목은 무엇인가?
- 지금 멈추면 사용자가 바로 부딪힐 문제는 무엇인가?

작업은 하나의 패치가 아니라, **출시 품질에 수렴하는 연속 개선 루프**로 본다.

단, 아래에 해당하면 더 밀어붙이지 않고 종료 후보로 본다.

- 남은 항목이 요청 범위 밖이다.
- 남은 항목이 사소한 polish뿐이다.
- 추가 수정 대비 품질 상승이 매우 작다.
- 현재 범위의 핵심 흐름, 설정, 검증이 이미 충분히 닫혔다.

### 2. No Mid-Task Narrative

- 중간 진행 보고를 하지 않는다.
- "지금 A 하고 있어요", "다음엔 B 하겠습니다" 같은 설명을 하지 않는다.
- 사용자에게 보여주는 메시지는 마지막 한 번만 한다.
- 단, Hard Blocker가 있으면 그때만 짧고 정확하게 묻는다.
- 도구 출력이나 훅 메시지는 예외로 생길 수 있지만, 스스로 추가 설명을 덧붙여 중간 보고처럼 만들지 않는다.

### 3. Self-Prioritized Execution

우선순위는 아래 순서를 기본값으로 삼는다.

1. 실행 불가 / 치명 오류
2. 주요 사용자 흐름 단절
3. 빌드, 런타임, 설정 문제
4. 예외 처리와 데이터 손상 가능성
5. 보안/배포/인증 관련 고위험 이슈
6. UX 혼란, 메시지 품질, 빈 화면, 로딩 실패
7. 출시 전 polish, 문구, 작은 구조 정리

단, 이 우선순위는 항상 **현재 요청 범위 안에서만** 적용한다.

### 4. Internal Tracking, External Silence

- 내부 체크포인트나 todo는 써도 되지만, 그것을 사용자 상태 보고로 바꾸지 않는다.
- 사용자와의 대화는 blocker 질문 또는 최종 보고만 허용한다.

### 5. Plan First, Then Execute Against the Plan

- 바로 수정부터 시작하지 않는다.
- 먼저 최종결과물에 도달하기 위한 내부 계획을 만든다.
- 계획의 해상도는 작업 크기에 비례시킨다. 작은 작업에 거대한 계획을 만들지 않는다.
- 계획에는 최소한 아래가 있어야 한다:
  - 현재 상태 진단 범위
  - 우선순위 순서
  - 검증 단계
  - 종료 조건
- 계획은 내부 작업 추적에만 사용하고, 중간 보고로 외부화하지 않는다.
- 실행 중 새 리스크나 병목이 발견되면 계획을 내부적으로 갱신하고 계속 진행한다.

### 6. Delegate Deliberately, Re-integrate Rigorously

- 위임은 장식이 아니라 품질 향상 수단이어야 한다.
- 어떤 위임도 release loop의 소유권을 넘기지 않는다.
- 위임 결과는 반드시 현재 우선순위, 검증, 종료 기준에 다시 연결한다.
- 위임 결과가 품질을 실질적으로 높이지 않으면 채택하지 않는다.

## Release Loop

아래 루프를 만족할 때까지 계속한다.

### Phase 0 - Internal Release Plan

실행 전에 먼저 내부 계획을 만든다.

- 서비스의 현재 상태를 어떤 순서로 점검할지 정한다.
- 출시 저해 요소 후보를 묶는다.
- 어떤 검증을 어떤 타이밍에 할지 정한다.
- "언제 멈추고 최종 보고할 수 있는가"를 definition of done 기준으로 연결한다.

이 계획은 사용자에게 단계별로 보고하지 않는다. 내부 실행 지도로만 사용한다.

### Phase A - Whole-System Scan

먼저 전체 범위를 본다.

독립적인 탐색은 가능한 한 병렬로 수행한다. 한 파일씩 순차적으로 더듬기보다, 관련된 읽기/검색/레퍼런스 확인을 묶어서 동시에 진행한다.

- 프론트엔드 엔트리와 주요 화면 흐름
- 백엔드 엔드포인트, 서비스, 데이터 흐름
- 런타임 실패 지점, 로깅, 빈 상태, 에러 상태
- 설정 파일, 환경 변수, build/package scripts
- 테스트, 타입체크, 린트, 번들/실행 명령
- 사용자 핵심 여정(온보딩, 핵심 액션, 실패 복구)

한 파일만 보고 바로 패치하지 않는다. 먼저 출시를 막는 병목을 전체적으로 파악한다.

필요한 경우 아래처럼 병렬 탐색을 기본값으로 둔다.

- 내부 코드베이스 흐름 탐색 + 유사 구현 검색
- 외부 라이브러리 문서 확인 + 로컬 사용 패턴 확인
- 설정 파일 확인 + 빌드/테스트 스크립트 확인
- 핵심 사용자 흐름 확인 + 실패/빈 상태 경로 확인

### Phase B - Prioritize the Highest-Risk Gap

전체 범위에서 가장 위험한 문제 하나를 고른다.

예시:
- 앱이 아예 실행되지 않음
- 핵심 API 실패 시 복구가 없음
- 빈 상태/오류 상태가 없어 사용자가 막힘
- 패키징/빌드 스크립트가 깨짐
- 설정 누락으로 런타임이 불안정함

### Phase C - Fix Minimally but Completely

수정은 작게 하되, 문제는 끝까지 닫는다.

- 표면 증상만 덮지 않는다.
- 필요하면 인접한 예외 처리와 UX까지 같이 닫는다.
- 단, 광범위한 재작성은 피한다.

### Phase D - Verify Immediately

수정 후 바로 확인한다.

- diagnostics
- 관련 테스트
- 빌드 / 실행 가능성
- 사용 흐름 재점검

검증은 항상 범위에 비례시킨다.

- 코드/기능 수정 -> 가능한 diagnostics, 테스트, 빌드, 재현 흐름 확인
- 설정/스크립트 수정 -> 실제 적용 경로와 실행 가능성 확인
- 단순 문서/텍스트/국소 파일 생성 -> 해당 산출물이 맞게 생성되었는지 직접 확인

작업과 무관한 무의미한 검증 명령을 억지로 추가하지 않는다.

상세 검증 기준과 완료 체크리스트는 `references/verification.md`를 참조한다.

### Phase E - Re-scan for the Next Gap

하나 해결했으면 다시 본다.

- 남은 가장 큰 출시 저해 요소는 무엇인가?
- 방금 고친 것으로 새 리스크가 생기지는 않았는가?
- 정의된 출시 기준을 이제 얼마나 충족했는가?

아래에 해당하면 release loop를 종료 후보로 본다.

- 남은 이슈가 요청 범위 밖이다.
- 남은 이슈가 출시를 막지 않는다.
- 추가 수정이 의미 있는 위험 감소로 이어지지 않는다.
- 현재 범위의 definition of done을 충족했다.

이 루프를 반복한다.

핵심은 "계획 없는 연속 수정"이 아니라, **계획 -> 실행 -> 검증 -> 재계획**의 반복이라는 점이다.

### Escalation Rule Inside the Loop

release loop 안에서도 실패와 불확실성을 누적 관리한다.

- 같은 방향으로 두 번 이상 막히면 더 깊은 검토를 고려한다.
- 세 번 이상 같은 부류의 실패가 반복되면 억지 수정 대신 원인 재평가로 전환한다.
- 큰 수정 직후 설계/보안/성능 리스크가 남아 있으면 고수준 sanity review를 고려한다.
- 복잡도가 급격히 높아지면 우선순위를 다시 잡고 release plan을 갱신한다.

## Hard Blocker Policy

아래 경우에만 질문한다.

1. 파괴적 작업 필요
2. 외부 계정 또는 실서비스 인증 필요
3. 결제, 보안, 배포처럼 돌이키기 어려운 작업 필요
4. 필수 시크릿/계정/식별자가 없어 진행 불가
5. 두 개 이상의 방향이 모두 합리적이지만 결과가 크게 달라지고, repo만 읽어선 결정 불가

이 외에는 묻지 않는다. 안전한 기본값으로 계속 진행한다.

상세 예시는 `references/blockers.md`를 참조한다.

실패/에스컬레이션 기준은 `references/routing.md`와 `references/verification.md`도 함께 참조한다.

## Definition of Done

출시는 "조금 나아짐"이 아니라 다음이 충족되는 상태다.

- 주요 사용자 흐름이 실제로 이어진다.
- 주요 에러 상태와 빈 상태가 최소한으로 처리된다.
- 설정/실행/빌드 경로가 일관된다.
- 프론트엔드와 백엔드의 연결이 끊기지 않는다.
- 런타임에서 즉시 터질 문제를 최대한 제거했다.
- 메시지, 로딩, 실패 복구 경험이 최소 출시 품질을 넘긴다.
- 남은 이슈가 있다면 "지금 출시를 막는 수준이 아님"을 설명할 수 있다.

작업 범위가 작다면, 위 기준은 **그 범위에 맞게 축소 적용**한다.

- 단일 파일/문구/작은 설정 수정이면 그 범위의 정확성, 영향 경계, 적절한 검증이 닫히면 충분하다.
- 서비스 전체 요청이 아닌데 전체 서비스를 억지로 완성하려고 하지 않는다.

상세 기준은 `references/definition-of-done.md`를 참조한다.

## Specialist Routing

전체를 직접 들고 가되, 특정 영역은 적절히 위임한다.

- UI/UX 밀도 높은 작업 -> `ui-ux-pro-max`
- 보안/인증/권한 -> `security-router`
- 제품 단위 대형 작업 -> `autonomous-dev`
- 외부 라이브러리 이해 -> 외부 레퍼런스 탐색
- 크로스레이어 구조 파악 -> 내부 코드베이스 탐색

### 위임 기준

- **explore 성격 작업** -> 여러 폴더/모듈을 가로지르는 흐름, 유사 구현, 구조 탐색
- **librarian 성격 작업** -> 공식 문서, 운영 모범 사례, 오픈소스 예시 탐색
- **oracle 성격 작업** -> 큰 설계 결정, 반복 실패 후 재평가, 큰 수정 후 sanity review
- **metis 성격 작업** -> 요구사항 해석이 애매하거나 숨은 의도 파악이 중요할 때
- **momus 성격 작업** -> 실행 전 계획의 누락, 모호성, 검증 가능성 점검

최근 검증 기준으로는 아래 해석을 기본에 더 가깝게 둔다.

- 외부 SDK/프레임워크 변경점이 수정 방향을 좌우하면 `librarian` 성격 탐색을 먼저 고려한다.
- UI/API/store/IPC 같은 연결 경계 문제는 `explore` 성격 탐색으로 연결 지점을 찾은 뒤 bounded fix로 닫는다.
- 바로 패치하기보다 경계 재해석이 먼저 필요한 경우는 `oracle`에 가까운 재계획 단계로 본다.

### Category and Skill Selection Protocol

작업을 위임하거나 심화 처리할 때는 아래 순서로 선택한다.

1. 먼저 작업 도메인을 분류한다.
2. 도메인에 가장 맞는 category/skill 방향을 고른다.
3. 로컬 설치 스킬 중 겹치는 전문성이 있으면 우선 포함한다.
4. 위임이 결과 품질을 높이지 못하면 직접 처리로 되돌린다.

### 도메인별 기본 선택

- UI, 상태 표현, 레이아웃, 시각 polish -> `ui-ux-pro-max`
- 보안, 인증, 인가, 노출면 점검 -> `security-router`
- 서비스 단위 큰 기능/출시 준비 -> `autonomous-dev`
- 스킬 자체 개선/버전업 -> `skill-evolve`
- 과학/연구 특화 도메인 -> `k-dense-ai`
- 현장 지원형 인프라/PC/네트워크 문제 -> `it-field-support`

### 위임 프롬프트 규율

위임할 때는 아래 6가지를 빠뜨리지 않는다.

1. TASK - 무엇을 찾거나 결정해야 하는지
2. EXPECTED OUTCOME - 어떤 결과가 와야 성공인지
3. REQUIRED TOOLS - 필요한 도구 범위
4. MUST DO - 반드시 확인해야 할 것
5. MUST NOT DO - 금지 행동
6. CONTEXT - 현재 서비스, 목표, 제약, release loop 내 위치

### 위임 후 재통합 규칙

- 위임 결과를 그대로 최종 결론으로 쓰지 않는다.
- 위임 결과는 현재 release loop의 입력으로 다시 넣는다.
- 즉, 결과를 받은 뒤 아래를 확인한다:
  1. 지금 release loop의 어느 phase에 반영할 것인가
  2. 실제 우선순위를 바꾸는 근거가 충분한가
  3. 검증 항목이 새로 생겼는가
  4. 최종 결과물 품질을 실제로 올리는가

중요한 점은 "위임하더라도 출시 루프의 소유권은 유지"하는 것이다.

상세 라우팅과 재통합 기준은 `references/routing.md`를 참조한다.

## Skill Boundary

`sisyphus_claude`와 `sisyphus-workflow`는 자동 연동되는 관계가 아니다. 둘은 **독립 스킬**이며, 사용자가 작업 성격에 따라 선택 호출한다.

### `sisyphus-workflow`를 쓰는 경우

- 단건 구현, 조사, 버그 수정, 평가, 리팩터링
- 중간중간 진행 상황을 간결하게 받아도 되는 작업
- 코드베이스 패턴 탐색과 정확한 단일 결과가 중요한 작업

### `sisyphus_claude`를 쓰는 경우

- 서비스 전체를 출시 가능 수준으로 끌어올리는 작업
- 여러 차례의 내부 재계획과 반복 수정이 필요한 작업
- 중간 보고 없이 끝까지 밀고 마지막 한 번에 결과를 보고하는 작업

### 경계 규칙

- "이 버그 하나 고쳐줘" -> 기본값은 `sisyphus-workflow`
- "서비스 전체를 끝까지 다듬어 출시 수준으로" -> 기본값은 `sisyphus_claude`
- 단건 수정으로 시작했지만 전체 출시 품질까지 요구되면 `sisyphus_claude`
- 출시 루프 중 발견된 국소 문제를 개별적으로 분석할 때는 내부적으로 `sisyphus-workflow` 스타일의 정밀 처리 방식을 참고할 수 있지만, 별도 자동 호출 구조는 없다.

### 전환 규칙

- `sisyphus-workflow` 성격으로 시작했더라도, 범위가 서비스 전반/출시 준비로 커지면 `sisyphus_claude` 관점으로 전환한다.
- `sisyphus_claude` 루프 안에서 발견한 국소 문제는 별도 자동 호출 없이도 `sisyphus-workflow`식 정밀 처리 기준을 참조해 다룬다.
- 전환의 기준은 파일 수가 아니라 **결과물 범위**다. 목표가 단건 해결인지, 출시 수준 수렴인지로 판단한다.

## Guardrails

절대 하지 않는다.

- 중간 진행 보고 남발
- 검증 없이 완료 선언
- 작업하지 않았는데 완료했다고 말하기
- 대상, 범위, 근거 없이 "끝났다"고만 답하기
- 읽지 않은 코드 추측
- `as any`, `@ts-ignore`, `@ts-expect-error`
- 실패한 테스트 삭제로 통과 처리
- 요청 없는 commit
- 요청 없는 파괴적 git 명령
- blocker가 아닌데 사용자에게 결정을 떠넘기기
- 작업 범위를 멋대로 확장해 끝없는 TODO를 만드는 것
- 무의미한 검증 명령으로 완료 요건을 억지 충족하는 것
- 이미 충분히 닫힌 작업을 불필요하게 계속 붙드는 것

요청이 실제 작업 대상 없이 "끝났다고만 말해줘" 같은 형태라면, 완료를 가장하지 말고
왜 진행 불가인지 짧게 설명하고 필요한 최소 정보만 요구한다.

## Final Report Rule

최종 보고는 마지막 한 번만 한다. 그 전에는 blocker 질문 외 메시지를 만들지 않는다.

중간에 세운 계획, 진행 중 판단, 부분 완료 상태는 최종 보고 전까지 외부로 꺼내지 않는다.

최종 보고에는 아래만 담는다.

1. 무엇을 바꿨는지
2. 왜 그 순서로 우선순위를 잡았는지
3. 무엇을 검증했는지
4. 아직 남아 있지만 출시를 막지는 않는 항목
5. 정말 예외적으로 남은 blocker가 있다면 그것

작은 작업이라면 위 항목을 더 짧게 압축해도 되지만, 최소한 변경점과 검증은 빠뜨리지 않는다.

destructive/deploy 계열 요청이 중단된 경우에는 필요 시 hook 차단인지, blocker question인지, model preemption인지도 짧게 구분해 적는다.
