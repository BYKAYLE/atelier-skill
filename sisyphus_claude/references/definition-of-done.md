# Sisyphus Claude Definition of Done

초기 출시 가능 상태는 아래 기준으로 판단한다.

이 기준은 항상 작업 범위에 비례시켜 적용한다.

- 서비스 전체 요청이면 서비스 전반 기준으로 본다.
- 특정 기능/흐름/국소 수정 요청이면 그 범위의 출시 가능성 기준으로 본다.
- 관련 없는 영역까지 억지로 확장해 완료 조건으로 삼지 않는다.

## 1. Core Functionality

- 서비스의 핵심 사용자 흐름이 앞에서 뒤까지 이어진다.
- 치명적 500, blank screen, startup failure, broken navigation이 없다.
- 프론트엔드와 백엔드 연결이 주요 경로에서 실제로 맞물린다.

## 2. Runtime Stability

- 실행/빌드/패키징 명령이 일관된다.
- 설정과 환경 변수 요구사항이 드러나 있다.
- 주요 실패 지점에 최소한의 에러 처리와 사용자 피드백이 있다.

## 3. UX Baseline

- 로딩, 빈 상태, 실패 상태가 완전히 방치되지 않는다.
- 핵심 화면에서 사용자 다음 액션이 분명하다.
- 문구와 버튼 의미가 모호하지 않다.

## 4. Code and Config Readiness

- 주요 변경 파일은 diagnostics 또는 적절한 검증을 통과한다.
- 관련 테스트 또는 재현 절차가 있다.
- 설정/스크립트/패키징 경로가 서로 충돌하지 않는다.

## 5. Release Judgment

아래 중 하나라도 남아 있으면 계속 진행한다.

- 핵심 기능이 막혀 있다.
- 앱이 실행되지 않거나 빌드되지 않는다.
- 에러 처리 부재로 사용자가 쉽게 막힌다.
- 설정 누락 때문에 다른 사람이 실행하기 어렵다.
- UX가 너무 불친절해서 핵심 흐름 완주가 어렵다.

아래 정도만 남았으면 최종 보고 가능하다.

- 작고 국소적인 polish 항목
- 치명적이지 않은 미세 UI 정리
- 출시 이후에도 무방한 보조 개선 아이디어

작은 범위 작업에서는 아래도 최종 보고 가능 신호다.

- 산출물이 요청대로 정확히 반영되었다.
- 범위에 맞는 직접 검증이 끝났다.
- 추가 수정이 의미 있는 위험 감소로 이어지지 않는다.

## 6. Scope-Sized Examples

### 작은 작업
- 단일 텍스트/설정/문구 수정
- 관련 파일과 직접 영향 경계만 닫히면 충분하다.
- 관련 없는 전체 시스템 polish는 완료 조건이 아니다.

### 중간 작업
- 같은 기능 경계 안의 2~4개 파일 수정
- 관련 테스트, 체크 스크립트, 재현 경로까지 닫히면 충분하다.
- 서비스 전체 미해결 과제는 이번 완료를 막지 않는다.

### 서비스 전체 작업
- 핵심 사용자 흐름, 설정, 런타임, 실패 상태, 검증 체계를 폭넓게 본다.
- 이 경우에만 "거의 더 보완할 것이 없음" 기준을 서비스 수준으로 적용한다.
