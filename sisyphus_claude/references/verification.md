# Sisyphus Claude Verification Reference

이 문서는 `sisyphus_claude`가 완료를 선언하기 전에 확인해야 할 증거와 보고 규칙을 정리한다.

## 1. 기본 원칙

- 수정 자체는 완료가 아니다.
- 증거가 있어야 완료다.
- 관련 없는 기존 실패는 따로 분리해 설명한다.
- 검증은 항상 작업 범위와 변경 크기에 비례시킨다.
- 무의미한 검증 명령으로 완료 근거를 억지로 만들지 않는다.

## 2. Evidence Requirements

| 작업 유형 | 필요한 증거 |
|---|---|
| 파일 편집 | 변경 파일 diagnostics 또는 구조 검토 |
| 기능 변경 | 관련 테스트 또는 재현 절차 확인 |
| 빌드 영향 변경 | 빌드 성공 또는 적용 불필요 사유 |
| 위임 결과 사용 | 결과가 요구사항과 맞는지 검증 |
| 조사/리서치 | 근거 파일, 경로, 문서 출처 |

### 작은 범위 작업 예시

- 단일 텍스트/문서 수정 -> 결과 내용 직접 확인
- 단일 파일 생성 -> 파일 존재와 내용 확인
- 국소 설정 수정 -> 수정된 값과 적용 경로 확인

반대로, 단일 텍스트 파일 생성 같은 작업에 프로젝트 전체 빌드/테스트를 억지로 요구하지 않는다.

### 구체 예시

#### 예시 A - 단일 텍스트 파일 생성
- 요청: `hello.txt` 생성 후 `hello` 기록
- 충분한 검증:
  - 파일 존재 확인
  - 파일 내용 직접 확인
- 불필요한 검증:
  - 관련 없는 `npm test`
  - 관련 없는 전체 프로젝트 빌드

#### 예시 B - Node 프로젝트의 문자열 마커 변경
- 요청: `fixture` -> `release` 변경, 관련 검사/테스트 통과
- 충분한 검증:
  - 변경된 파일 확인
  - `npm run check`
  - `npm test`
- 종료 가능 조건:
  - 관련 스크립트와 테스트가 통과하고 범위 밖 추가 polish만 남음

#### 예시 C - Python 프로젝트의 국소 수정
- 요청: 메시지 문자열 변경과 관련 테스트 정합성 유지
- 충분한 검증:
  - 변경 파일 확인
  - 환경에서 가능한 테스트 명령 실행
  - 대체 검증 경로가 있으면 그 결과 명시
- 주의:
  - 없는 도구(`pytest` 미설치)를 억지 전제하지 말고 가능한 검증 경로로 전환

## 3. 완료 체크리스트

### 구현/수정
- 내부 계획의 핵심 항목이 실제로 소화되었는가
- 변경 파일이 읽혀지고 내용이 확인되었는가
- diagnostics를 확인했거나, 해당 파일 타입에서 불가능한 이유를 설명할 수 있는가
- 관련 테스트를 실행했거나, 없는 이유를 설명할 수 있는가
- 필요 시 빌드를 실행했거나, 범위상 불필요함을 설명할 수 있는가
- 출시를 막는 주요 문제를 실제로 닫았는가

### 조사/설명
- 근거가 되는 파일이나 문서를 실제로 읽었는가
- 추측이 아니라 읽은 내용 기준으로 설명하는가
- 추가 구현이 필요한 경우와 아닌 경우를 구분하는가

## 4. 실패 처리

- 내 변경으로 생긴 문제를 먼저 수정한다.
- 관련 없는 선행 문제는 분리 보고한다.
- 같은 방향으로 세 번 이상 실패하면 더 밀어붙이지 말고 재평가한다.

## 5. 최종 보고 체크리스트

최종 메시지에는 가능하면 아래가 있어야 한다.

1. 무엇을 바꿨는지 또는 무엇을 찾았는지
2. 어디를 우선순위 1순위로 봤는지
3. 어떤 검증을 했는지
4. 남아 있지만 출시를 막지는 않는 항목
5. 남은 blocker가 있다면 그것이 왜 blocker인지

위험 요청이 중단된 경우에는 아래 셋 중 무엇이었는지도 필요 시 구분한다.

- hook 차단
- blocker question 전환
- model preemption

### 최종 보고 예시

#### 작은 작업
- 변경: `hello.txt` 생성 및 내용 기록
- 검증: 파일 존재와 내용 직접 확인
- 남은 항목: 없음

#### 프로젝트 범위 작업
- 변경: 관련 파일 2~4개 수정, 범위 밖 모듈은 유지
- 검증: 관련 check/test 통과
- 남은 항목: 범위 밖 추가 polish만 존재

## 6. Stop Policy Notes

- 현재 기본 정책은 "첫 stop 시도에서만 검증을 한 번 유도"하는 안정형 정책이다.
- 목적은 검증 없는 즉시 종료를 줄이되, 무한 stop loop를 만들지 않는 것이다.
- 더 엄격한 운영이 필요하면 `profiles.md`의 Strict 방향을 참고한다.

### 6.5 Replanning Notes

- 검증 과정에서 문제의 원인이 단일 라인이 아니라 경계 해석 불일치로 드러나면 바로 패치보다 재계획이 우선이다.
- oracle-like replanning의 핵심은 큰 설계 문서를 만드는 것이 아니라, 현재 release loop에서 무엇을 먼저 다시 해석할지 좁히는 것이다.
- public sign flow, updater, settings save 사례처럼 connected boundary 버그는 재계획 후 bounded fix로 내려오는 흐름이 바람직하다.

## 6. 금지 사항

- 검증 없는 완료 선언
- 테스트 실패를 숨기기
- 타입 에러 억지 무시
- 읽지 않은 코드 추측
- 근거 없는 완료 가장
