## FP-001: 설계는 있으나 실행 루프 끊김

**증상**:
- SKILL.md에 자가 성장 Phase가 설계되어 있음
- 그러나 SOT에 자가 감지 데이터가 0건
- evolution-signals/ 비어있음
- meta-rules의 모든 규칙이 사용자 피드백 기반

**근본 원인**:
1. 자가 성장 Phase의 실행 우선순위가 낮음 (토큰/컨텍스트 압박 시 스킵)
2. 실행 트리거가 불명확 ("매 세션"이라고만 쓰고, 구체적 실행 시점 미지정)
3. 컨텍스트 한계로 세션 후반부에 Phase 6까지 도달하지 못함
4. 자가 성장의 산출물이 명시되지 않아 "실행했는지" 검증 불가

**해결 전략**:
- 자가 성장 Phase에 **필수 산출물** 정의 (예: "세션 로그 파일 생성 필수")
- Phase 스킵 방지: "Express 모드 외 스킵 금지" 같은 강제 규칙
- 자가 감지 신호 추출을 **다른 Phase 내에 인라인으로 삽입** (별도 Phase 대신)
- 최소 실행 보장: "meta-rules 1건 이상 점검" 같은 최소 기준

**실제 사례**: release v2.0 — Phase 6이 17세션 동안 미실행

## FP-002: SOT 비어있음 증후군

**증상**:
- SOT/ 디렉토리와 파일은 존재
- 그러나 대부분 초기 상태 또는 빈 파일
- sessions/ 로그가 performance.md 기록 대비 부족

**근본 원인**:
1. SOT 갱신 지시가 SKILL.md에 있지만, 실제 실행 경로에서 도달하지 못함
2. "기록" Phase가 "실행" Phase보다 후순위라 토큰 부족 시 생략
3. SOT 파일의 초기 템플릿만 생성하고 실제 데이터 갱신은 안 함

**해결 전략**:
- 기록을 별도 Phase 대신 **실행 Phase 종료 직후 인라인으로 삽입**
- SOT 갱신을 Phase 완료 조건에 포함 ("세션 로그 미작성 = Phase 미완료")
- 최소 기록: 세션 시작/종료 시각 + 사용 스킬 목록 (1줄이라도)

**실제 사례**: release — evolution-signals/, project-absorptions/ 빈 디렉토리

## FP-003: Phase 간 데이터 전달 끊김

**증상**:
- Phase A의 산출물이 Phase B에서 사용되지 않음
- 에이전트에게 위임 시 이전 Phase의 맥락이 누락

**근본 원인**:
1. Phase 간 데이터 계약(입력/출력)이 명시되지 않음
2. 에이전트 프롬프트에 이전 산출물 경로를 포함하지 않음
3. 산출물 형식이 비표준이라 다음 Phase에서 파싱 실패

**해결 전략**:
- 각 Phase의 **입력 요구사항**과 **출력 산출물**을 SKILL.md에 명시
- 에이전트 위임 프롬프트 템플릿에 `artifacts` 필드 필수
- 산출물 형식 표준화 (JSON/Markdown 택일, 스키마 정의)

## FP-004: 자가 참조 무한 루프

**증상**:
- 자가 성장 규칙이 자기 자신을 수정하는 규칙을 생성
- 수정 → 재수정 → 재재수정의 무한 루프

**근본 원인**:
1. 자가 수정 대상에 자가 수정 프로토콜 자체가 포함
2. 필터 게이트가 없어 모든 신호가 규칙으로 전환
3. 규칙 간 충돌 감지 메커니즘 부재

**해결 전략**:
- **SKILL.md 수동 수정 원칙**: 자가 수정은 references/SOT만, SKILL.md는 사람만
- 세션당 자가 수정 **최대 N건 제한** (예: 3건)
- 규칙 추가 전 **기존 규칙과 충돌 검사** 필수
- 자가 수정 전 반드시 **백업** 생성

**실제 사례**: 이론적 패턴 (release에서 MR-007로 사전 방지)

## FP-005: 컨텍스트 한계 도달 시 Phase 절단

**증상**:
- 세션이 컨텍스트 한계에 도달하면 후반 Phase가 실행되지 않음
- 특히 자가 성장(Phase 6), 보고(Phase 7) 등 후반부 Phase가 피해

**근본 원인**:
1. 오케스트레이터의 Phase 수가 너무 많음 (8+ Phase)
2. 전반 Phase에서 토큰을 과다 소비
3. Resume 프로토콜이 없거나 불완전

**해결 전략**:
- **핵심 Phase 우선**: 자가 성장을 맨 뒤가 아닌 실행 직후로 이동
- **토큰 예산 관리**: Phase별 토큰 상한 설정
- **Resume 프로토콜**: 중단 시 상태 저장 → 다음 세션에서 이어서 실행
- **인라인 기록**: 별도 Phase 대신 실행 Phase 내에서 최소 기록

## FP-006: SOT 갱신 주체 충돌

**증상**:
- 같은 SOT 파일을 여러 Phase가 동시에 갱신
- 갱신 내용이 서로 덮어쓰기

**근본 원인**:
1. SOT 파일의 갱신 주체(Owner Phase)가 미정의
2. 여러 Phase에서 "필요하면 갱신"이라고만 기술

**해결 전략**:
- 각 SOT 파일에 **단일 Owner Phase** 지정
- 다른 Phase에서 갱신 필요 시 Owner Phase를 통해 간접 갱신
- SOT 스키마에 `last_updated_by` 필드 포함

## FP-007: 위임 프롬프트 품질 저하

**증상**:
- 에이전트에게 위임했으나 결과물 품질이 기대 이하
- 같은 스킬인데 직접 호출과 위임 호출의 결과 차이가 큼

**근본 원인**:
1. 위임 프롬프트에 필수 컨텍스트 누락
2. 프롬프트 템플릿이 일반적이라 프로젝트 특성 미반영
3. 에이전트 모델 선택 부적절 (단순 작업에 opus, 복잡 작업에 haiku)

**해결 전략**:
- 위임 프롬프트 템플릿에 **필수 필드** 정의 (목표, 산출물, 품질 기준, 참조 파일)
- 프로젝트 흡수 문서를 프롬프트에 포함
- 모델 선택 가이드라인 명문화
- 위임 결과 품질을 **performance.md에 기록**하여 패턴 학습

## 진단 시 사용법

Step 3에서 scanner gap-report를 받으면:

1. 각 갭의 카테고리 확인
2. 해당 FP-NNN 패턴과 매칭
3. 근본 원인 중 해당하는 항목 식별
4. 해결 전략에서 적용 가능한 것 선택
5. Step 4 수정 제안에 반영
